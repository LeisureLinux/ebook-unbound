# 加密与隐私 RFC 族

第 15 章把 DNS 基础的线格式与语义、第 16 章把 DNSSEC 的信任链与验证状态讲完了；这一章处理第三条线：**谁看见了查询**。它与前两条线不重叠，也不互相替代——DNSSEC 提供数据完整性与来源认证，查询名最小化（QNAME minimisation，QMIN）减少发给上级的元数据，DoT / DoH / DoQ / ODoH 提供传输加密与隐私。第三篇第 11–14 章已经给出端口、证书、转发、fail-closed 与 DDR 压制的落地配置，本章不贴配置块，只回答"条文为什么这么写、实现因此被约束在哪、以及哪些读法是错的"。

全章对每份 RFC 采用统一的四段式：**它要解决什么 → 关键条文 → 对实现的约束 → 常见误读**。第四篇统一按 `[RFC XXXX]` 形式引用编号，不写完整 URL；可核验链接集中在章末《参考资料》。涉及具体发布年份、版本状态与实现默认值时，一律以 RFC Editor 索引与所用版本的官方手册对应章节为准，本章不猜测。书中出现的地址只取 [RFC 5737] 的 `192.0.2.0/24`、`198.51.100.0/24`、`203.0.113.0/24` 与 `2001:db8::/32`，域名只用 `example.net` / `example.org` 及其子名，均为教学用示例。

## 查询名最小化的两版规范：[RFC 7816] → [RFC 9156]

### 它要解决什么

未开 QMIN 时，递归解析器解析 `assets.cdn.example.org A` 会把完整 QNAME 依次送给根、TLD、以及每一级权威服务器。这些服务器各自只负责命名空间的一小段，本不需要知道完整名字；但完整名字让它们能长期积累"谁在查什么"的元数据，且不同层的运营者可以把日志拼起来。[RFC 7816] 提出的是**数据最小化**：向每一级只发送推进解析所必需的最少标签数，把"必须知道"限制在区切（zone cut）这一层。

[RFC 9156] 废弃 [RFC 7816]，不是推翻目标，而是修正算法：第一版的固定 QTYPE 策略在真实权威服务器上引发了足够的兼容问题，需要重新规定；同时把"遇到异常应答怎么办"写成明确的两种模式。具体发布年份见 RFC Editor 索引。

### 关键条文

- [RFC 7816] 的算法是：QNAME 逐标签增长，每次只问到当前已知的区切；**中间查询把 QTYPE 固定为 NS**，理由是解析到区切时本来就想要委派信息，且固定类型可以避免把原始 QTYPE 暴露给上级。
- [RFC 9156] 改为**保留原始 QTYPE**：中间查询只缩短 QNAME，不再替换 QTYPE。判断"这是引用（referral）还是最终应答"依据的是 Answer 段为空、Authority 段给出下级 NS 这一组合，与 QTYPE 无关。
- 为什么要改回去：NS 是**被特殊对待的类型**。不少权威服务器收到对某个中间名的 NS 查询时，会直接把本区 apex 的 NS RRset 放进 Answer 段并置 AA 位，而不是给引用；最小化解析器若把这种应答当成"已经到了最终区"，就会在错误的层级停下。此外 CNAME / DNAME、通配符、以及某些运营者按 QTYPE 做的限速与过滤，对不同 QTYPE 的答案并不一致，固定 NS 会让中间层看到的世界与最终查询要的答案脱节。保留原始 QTYPE 的代价是上级多知道一个类型，换来的是应答语义一致。
- [RFC 9156] 把回退策略分成 **relaxed** 与 **strict**：relaxed 在中间查询返回非预期的 RCODE（NXDOMAIN、REFUSED、SERVFAIL 等）或非引用式应答时，退回发送完整 QNAME 与原始 QTYPE 重新问一次；strict 不回退，直接依据 [RFC 8020] 的 NXDOMAIN cut 断言"该名字及其下所有名字都不存在"并结束解析。
- 两版都明确：最小化只作用于**解析器到权威侧**的迭代查询，不改变存根解析器到递归解析器这一跳，也不改变报文的明文属性。

### 对实现的约束

实现必须把"已知区切"作为状态维护：每收到一次引用，才把 QNAME 往下推进一个标签；不能靠预先猜域名有几段。对 CNAME / DNAME 链、通配符命中、以及权威侧返回 NODATA 的情形，要有明确的推进或回退规则，否则会停在半路。

strict 模式的正确性建立在"所有权威都遵守 [RFC 8020]"这个前提上。现实里存在违反它的区：父名返回 NXDOMAIN、更深的子名却挂着数据（某些大型 CDN 的 CNAME 区是典型）。最小化恰好先问中间那个"空父名"，strict 拿到 NXDOMAIN 就断定整条链不存在，于是整站的资源域名解析失败，页面样式与脚本全丢。更麻烦的是这个错误结论会被 [RFC 2308] 的负缓存按 SOA minimum 记住，改回 relaxed 之后**链路上的每一层缓存都要单独刷**才恢复。第三篇第 13 章记录的是参数处理，这里的条文结论是：出问题的是权威侧违反 [RFC 8020]，不是解析器多疑。

还有一条边界必须写清：**QMIN 不是加密**。它减少的是发给上级的标签数，抗的是"多个权威运营者长期聚合元数据"；最终那个权威服务器仍然必须看到完整 QNAME 才能给出答案，解析器自己也看到全部。若本地做了根区镜像，根这一跳本来就不出口，收益主要落在 TLD 与二级权威层——这与第三篇的实测观察一致。

### 常见误读

**误读一：QMIN 让查询内容保密。** 它只缩短 QNAME，QTYPE、源地址、时序、报文长度都还在，链路上任何能看到这一跳的观察者都不受影响。

**误读二：strict 更严格所以更隐私。** strict 的差别是"不回退"，不是"发得更少"；它以兼容性换掉了一次回退机会，遇到不守规矩的权威反而会把整条查询判死。

**误读三：改回原始 QTYPE 是倒退。** 固定 NS 的初衷是少泄露一点类型信息，但它让应答语义失真；[RFC 9156] 是拿这一点理论收益换实现正确性。

**误读四：relaxed 等于没开 QMIN。** 只在异常路径上回退，正常路径仍然是最小化的；把偶发回退当成"机制失效"，会误判观测日志。

## DoT：[RFC 7858]

### 它要解决什么

存根解析器到递归解析器这一跳长期是明文 UDP/TCP 53：同一局域网、同一接入链路上的被动观察者能读到全部查询，主动观察者还能改写应答。[RFC 7858] 给出最小改动的答案——把 [RFC 1035] 的 DNS 线格式**原样**放进 TLS 记录，用专用端口承载，不引入 HTTP 层、不重新定义报文。

### 关键条文

- 传输是 TCP 上的 TLS，专用端口 853；DNS 报文沿用 [RFC 1035] 为 TCP 定义的两字节长度前缀分帧，首部、段结构与压缩指针原样保留，仅由 TLS 提供机密性、完整性与服务器认证。
- 客户端**必须**按 PKIX 校验服务器证书与其身份（主机名或预先约定的 SPKI 指纹）；不满足校验即连接失败，不允许"先加密起来再说"。
- 连接可以复用、可以会话恢复；多个查询可共用一个 TLS 连接，应答**不必按请求顺序返回**，接收方靠 DNS 报文首部的 ID 匹配。实现需要处理超时、半开连接与重连，以及一条连接上的并发上限。
- 报文长度会暴露查询规模，[RFC 7858] 因此指向 EDNS(0) 填充选项（填充策略见官方手册对应章节），让填充成为可用手段而非必选行为。
- 规范只定义**这一跳**；解析器拿到查询后如何向权威服务器迭代，不在本文范围内。

### 对实现的约束

服务端与客户端都要把"认证失败"当作硬失败，而不是把 TLS 握手失败降级成明文 53。第三篇反复强调的静默明文降级，条文对应就在这里：一旦允许回退，[RFC 7858] 提供的保护面归零，而应用侧几乎察觉不到。实现还需要为长连接设定空闲超时与并发上限，否则一个 TLS 连接就能占住解析器的一条工作槽。

填充不是免费的：它增加带宽，且填充长度要与 EDNS(0) 通告的载荷上限、以及所用承载的 MTU 一起算。DoT 本身跑在 TCP 上，不存在 UDP 分片问题，但填充后的报文若被同一实现复用于 UDP 侧承载（DTLS、DoQ），仍可能触发分片被丢 → 等超时 → 重试。填充是缓解长度画像的手段，不是必选项。

### 常见误读

**误读一：853 上跑的就是"加密 DNS"，所以数据可信。** 加密与认证的是链路对端，DNS 应答数据的来源认证仍要靠 DNSSEC（第 16 章）。

**误读二：连上 TLS 就完成了 [RFC 7858]。** 不校验证书等于只防被动嗅探、不防主动中间人；规范把身份认证写成了必须项。

**误读三：DoT 保护整条解析路径。** 它只覆盖存根到这一台解析器；解析器往权威侧发出的迭代查询仍可能是明文 53。

## DoH：[RFC 8484]

### 它要解决什么

[RFC 7858] 的专用端口易于被按端口识别、限速或阻断。[RFC 8484] 把 DNS 报文作为 HTTP 消息体、经 HTTPS 送出，使其能与普通 Web 流量共用 443 端口，降低"仅因是 DNS 就被区别对待"的概率。代价是把 HTTP 层的元数据一起带进了 DNS 的信任模型。

### 关键条文

- DNS 线格式报文作为 `application/dns-message` 的实体：POST 放在请求体，GET 用 base64url 编码的 `dns` 查询参数；URI 模板形式（常见 `/dns-query`）由服务自行声明。
- 使用 HTTP/2 及以上更为合适；HTTP 缓存语义可用，但缓存键必须考虑 DNS 应答自身的 TTL，不能让 HTTP 缓存把短 TTL 的记录留得更久。
- 服务器认证沿用 HTTPS 的 PKIX 体系；规范没有另外定义一套 DNS 专用的身份模型。
- 与 DoT 一样，规范只定义**存根到端点**这一跳，端点之后的递归与迭代不在范围内。

### 对实现的约束

端点运营者同时掌握查询内容、客户端 IP、以及 HTTP 层信息（SNI、ALPN、User-Agent、可能的 Cookie 与鉴权头）。因此实现侧必须允许"不写这些字段"：不注入 Cookie、不把鉴权 token 当成跟踪标识、不把客户端指纹写进长期日志。第三篇把 DoH 前端与 Unbound 后端分开，条文理由就在这里——HTTP 层能收集的东西远多于 DNS 层，日志归属要在架构上切清楚。

同一 443 上 Web 与 DoH 共存，也让"按 IP 或按端口封禁"既容易误伤又容易漏：端点可能挂在共享 IP、CDN 或 anycast 之后，IP 与"这是不是一个 DoH 端点"不再一一对应。这一点在 17.11 会展开。

### 常见误读

**误读一：DoH 是匿名。** 它把查询从本地网络观察者手里移到了端点运营者手里，并且新增了 HTTP 元数据；谁被信任变了，被收集的量没变少。

**误读二：混在 443 里就查不出来。** SNI、目标 IP、连接时序、报文长度与 HTTP 特征仍可观测，"与 Web 同形"降低的是分类的确定性，不是可见性。

**误读三：DoH 端点天然不记日志。** 记不记是运营策略，不是协议保证；[RFC 8932] 整份文档都在处理这个问题。

## DoQ：[RFC 9250]

### 它要解决什么

DoT 的 TCP + TLS 在丢包、握手往返与队头阻塞上有成本；DoH 又背了 HTTP 层的复杂度。[RFC 9250] 用 QUIC 承载 DNS：保留 TLS 1.3 的加密与认证，换用 UDP 之上的多路复用流，让多个查询互不阻塞，并支持连接迁移与更快的连接建立。

### 关键条文

- 使用**专用 QUIC 连接**，ALPN 标识与 IANA 分配的 UDP 端口见 RFC Editor 原文（具体编号以官方手册对应章节为准）；不复用 HTTP/3 的语义。
- 每个 DNS 查询映射到一条 QUIC 双向流，流本身提供顺序与对应关系；同一连接可并发多条流，DNS 报文首部里的 ID **必须置 0**，不再承担匹配职责。
- QUIC 内置 TLS 1.3，加密与服务器认证是强制的；没有"不加密的 DoQ"这一档，也没有明文回退档。
- 0-RTT 数据、空闲超时、流数与流量控制都有对应约束；实现要按 QUIC 的资源模型做限额，防止一条连接独占解析器。
- 与 DoT / DoH 相同，只覆盖存根到解析器这一跳。

### 对实现的约束

fail-closed 在这里不是可选项：QUIC 握手失败、被中间设备丢弃、或端口不可达时，客户端若自动退回明文 53，等于把 [RFC 9250] 的保护整段撤掉。第三篇记录的实测结论也指向同一方向：跨境链路上 UDP / QUIC 被 QoS 时，同一路径 TCP 承载更稳（实测 1MB 下载差距在三个数量级附近），因此"加密传输选哪条承载"是链路实测问题，不是协议优劣的口号。

服务端需要把"一条 QUIC 连接上的并发流数"纳入与 DoT 长连接同等的资源预算；连接迁移让基于五元组的限速与会话绑定失效，策略要按连接 ID 而不是按源端口来做。

### 常见误读

**误读一：QUIC 用 UDP 所以更快、一定更好。** 在丢包或被限速的 UDP 路径上，它可能比 TCP 承载更差；协议特性不等于链路实测结果。

**误读二：0-RTT 等于零风险。** 0-RTT 数据有重放语义上的限制，实现要按 QUIC 的约束处理，不能把任何查询都塞进早期数据。

**误读三：DoQ 是"DoH over QUIC"。** 它是独立的专用 QUIC 映射，不经过 HTTP 层，也没有 HTTP 方法、路径与状态码。

## 使用配置：[RFC 8310]

### 它要解决什么

[RFC 7858] 定义了"怎么把 DNS 装进 TLS"，但没回答一个部署问题：**当加密连不上时该怎么办**。现实中证书过期、端口被封、对端只支持旧版本都会发生；若每个实现自己决定"要不要退回明文"，用户以为自己开着加密，实际却在裸奔。[RFC 8310] 把使用方式收敛成两份可声明的 profile，并明确谁该对身份负责。

### 关键条文

- **Strict Privacy（严格隐私）**：要求加密且要求服务器认证；认证或握手失败即失败，不允许回退到明文，也不允许"先连上再补校验"。
- **Opportunistic Privacy（机会隐私）**：尽可能使用加密，连不上时允许退回明文；它明确不承诺隐私，只承诺"条件允许时比明文好一点"，认证要求也相应放宽。
- 身份验证方式包括常规 PKIX 证书校验（对端点主机名）与 SPKI 指纹固定（pin），供无法或不想依赖公共 CA 体系的部署使用。
- 文档同时覆盖 DNS-over-TLS 与 DNS-over-DTLS 两类承载（DTLS 侧的规范编号见官方手册对应章节），并要求配置方能**明确声明**自己采用哪一档 profile。

### 对实现的约束

实现必须把 profile 作为**可观测、不可静默改变**的状态：严格档下任何失败都要以连接失败或 SERVFAIL 呈现，不能悄悄换端口、换协议、换证书校验策略。第三篇里 `forward-first: no`、fail-closed、"两波都失败就 SERVFAIL"的工程做法，条文依据是这一条——降级不是一种容错策略，而是把安全声明改写了。

运营侧还要区分"客户端声明的 profile"与"服务端实际提供的能力"：服务端只支持 opportunistic，客户端却以为自己在 strict，是配置审计里最常见的错配。

### 常见误读

**误读一：opportunistic 是"轻量版严格档"。** 它不承诺隐私，只是可用性优先的尽力而为；把它写进"已启用加密传输"的清单会造成虚假结论。

**误读二：证书校验可以等连上以后再做。** 严格档要求先认证再使用，认证失败的连接不能被拿来发查询。

**误读三：[RFC 8310] 只管 DoH。** 它面向的是 DNS-over-TLS / DNS-over-DTLS 的使用配置；DoH 沿用 HTTPS 的 PKIX 体系，不在这份 profile 的定义范围内。

## 两跳分离：[RFC 9230]

### 它要解决什么

DoH 把查询从本地观察者手里交给了端点运营者：端点同时看到**客户端 IP** 与**查询内容**。换一个公共端点只是换一个信任对象。[RFC 9230] 想做的是把这两样信息拆到两个不同的参与方手里，使得单看任何一方的日志都无法把"谁"和"查了什么"关联起来。

### 关键条文

- 引入 **client → relay → target** 两跳。客户端用 target 的公钥（HPKE）把 DNS 报文封装成密文，连同一个加密后的应答密钥一起交给 relay；relay 只负责转发，看不到明文查询。
- **relay 见 IP 不见查询**：它知道客户端 IP、知道 target 是谁、能看到报文长度与时序，但拿不到查询内容。
- **target 见查询不见 IP**：它解密、执行解析、把应答封装回密文经 relay 交回客户端；它看到的是 relay 的 IP，不是原始客户端的。
- 分离成立的前提是 **relay 与 target 不共谋、不由同一主体控制**，且两者之间不能通过时序、长度、连接复用把请求重新配对；规范也明确这类流量分析不在密码学保护范围内。
- 与 DoH 一样，只解决存根到 target 这一跳；target 之后向权威服务器的迭代依然按普通 DNS 进行。

```text
（示意图，非配置；涉及地址均为 [RFC 5737] 的教学用示例）
[client]
   │  ① 密文查询 + 客户端 IP
   ▼
[relay]   见 IP、见 target、不见 QNAME；只见密文长度与时序
   │  ② 同一份密文，源 IP 换成 relay
   ▼
[target]  见 QNAME、不见客户端 IP；解密后执行解析
```

### 对实现的约束

客户端需要取得并校验 target 的公钥配置（密钥如何分发、如何轮换、如何撤销是部署问题，见官方手册对应章节）；relay 必须不解密、不改写、不按查询内容做路由；target 必须不依赖客户端 IP 做应答策略，否则"看不到 IP"只是纸面说法。任何一方记录可关联的元数据（精确时间戳、稳定连接标识、长度序列），都会把两跳重新拼成一跳。

还有一条常被忽略的约束，值得单独论证：**自建可信 target 时收益约等于零**。ODoH 的收益定义在"target 是你不信任的第三方"这一场景——你用它解析，但不愿让它知道你是谁。若 target 是你自己搭建并完全信任的解析器，你本来就把全部查询交给了它，隐藏客户端 IP 对它没有意义；而为了让 relay 与 target 不共谋，relay 必须另找独立主体，可这个外部 relay 反而成了新的、能看到你 IP 的第三方。若为了省事把 relay 也建在自己这边，两跳就落在同一管理域里，日志一关联即还原，"分离"只剩名义。与此同时你多付了一跳延迟、一套密钥分发、一处新的失败点，还失去了本地解析器直接可观测的查询流。结论不是"ODoH 无用"，而是**它的适用前提是把查询交给一个你不愿暴露身份的第三方解析器**；自建可信解析器用 DoT / DoQ 加 QMIN 已经能拿到该拿的东西。

### 常见误读

**误读一：ODoH 是 DoH 的加密加强版。** 它多出来的是**参与方分离**，不是更强的密码；DoH 的链路本来就由 TLS 加密。

**误读二：relay 看不到查询，所以 relay 可以随意选。** relay 仍看到客户端 IP 与 target 身份，且能通过时序做关联；选一个与 target 有共同运营主体的 relay，等于把两跳合并。

**误读三：ODoH 防流量分析。** 长度、时序、并发模式仍在，[RFC 9230] 并不承诺抗全局被动观察者；填充只能缓解。

## 发现与压制：[RFC 9462]

### 它要解决什么

加密传输普及后，客户端仍卡在第一步：怎么知道**眼前这台**解析器（通常是网络自动分配的明文 53 地址）有没有对应的加密端点、端点叫什么、支持哪种协议。[RFC 9462] 的 DDR（Discovery of Designated Resolvers）让客户端向已配置的解析器自己发一个特殊名字的查询，从应答里拿到它声明的加密解析器信息，从而在不改网络配置的情况下升级到加密传输。

### 关键条文

- 保留名 `_dns.resolver.arpa.` 用于发现；客户端向**当前已配置的解析器**查询该名字的 SVCB / HTTPS RRset（借 [RFC 3597] 建立的未知类型透明转发能力，见第 15 章）。
- 应答里携带端点主机名、端口、ALPN、以及 DoH 的 URI 路径模板之类的参数，客户端据此选择自己支持的加密协议并验证指定解析器的身份。
- 规范要求客户端确认"指定解析器"与"当前解析器"之间存在可验证的关联（同一运营方、同一网络授权），并保留回退到原解析器的路径；发现结果是**声明**，不是强制切换指令。
- 特殊用途域名的本地处理框架来自 [RFC 6761]（第 15 章）；`resolver.arpa` 的语义由本 RFC 及 IANA 注册表确定。

```text
（示意图，非配置；端点名均为 example.net / example.org 教学用示例）
[客户端] --① 查 _dns.resolver.arpa. SVCB--------> [当前解析器]
[客户端] <--② 声明的加密端点参数----------------- [当前解析器]
[客户端] --③ 按参数连接并校验身份--------------> [resolver.example.net]
```

### 对实现的约束

发现机制给客户端一条**自动绕过本地解析器**的路径，这正是本书在第三篇压制它的原因。本地解析器承担过滤、分流、DNSSEC 验证、QMIN、负缓存控制、dnstap 审计与 canary 判定；一旦客户端按 DDR 声明直连外部加密端点，这些策略全部落空，而且落空得悄无声息——网络侧只看到 443 流量，看不到查询。

压制手段是语义层的：让本地解析器对 `_dns.resolver.arpa.` 的发现查询返回 NODATA（本地服务区策略），客户端得不到声明就不会升级；浏览器侧再配合 canary 域（Firefox 的 `use-application-dns.net` 回 NXDOMAIN、Chrome 靠系统解析器匹配不到已知 DoH 提供商）让应用退回系统解析器。**这两者都是按名字做判定，不是按 IP 封 443**；后者的局限在 17.11 展开。注意压制的是"自动发现绕过"，不是"禁止用户显式配置加密解析器"——显式配置、且指向自己信任的端点，属于正常用法。

### 常见误读

**误读一：DDR 会强制客户端改用加密解析器。** 它提供的是可验证的声明与升级路径，客户端有策略决定权，网络运营者也可以选择不提供声明。

**误读二：压掉 DDR 就等于禁用了 DoH。** 只挡住了"由当前解析器自动发现"这一条路；用户手动配置的端点、应用内置的端点列表不受影响，所以还需要 canary 与出向策略配合。

**误读三：`_dns.resolver.arpa.` 是某厂商的私有域名。** 它是注册过的特殊用途名，语义由规范与 IANA 注册表给定，本地处理依据是 [RFC 6761] 一类框架，不是"公网恰好没这个区"。

## 运营者视角：[RFC 8932]

### 它要解决什么

前面几份 RFC 都在定义"两个端点之间怎么传"。加密 DNS 一旦作为服务对外提供，一个新的汇聚点就出现了：服务运营者同时握有客户端 IP、查询内容、精确时间与连接特征，而且用户往往误以为"用了加密就不用管日志了"。[RFC 8932] 是写给**运营者**的建议集，处理的是协议条文管不到的策略面。

### 关键条文

- **数据最小化与保留期**：默认不收集可识别客户端的字段；确需收集时明确目的、范围与保留时长，并让外部可核验（隐私声明、透明报告）。
- **不要引入新的标识符**：慎用或不用 ECS；不注入 Cookie、不用 User-Agent / 鉴权头做长期关联；DoH 层的 HTTP 元数据要与 DNS 层一样受最小化约束。
- **传输与协议选择**：使用当前版本的 TLS、支持填充、支持 QMIN、不提供静默明文回退；对 DoH 端点还要注意 HTTP 缓存与 CDN 会不会把身份信息带到第三方。
- **可核查性**：把"记什么、留多久、谁能看、如何删除"写成公开策略，而不是只写在内部运维手册里。
- 文档性质是建议（具体类别与状态见 RFC Editor 索引），但其中多条与 [RFC 8310] 的严格档、[RFC 9076] 的威胁模型直接互为支撑。

### 对实现的约束

对自建解析器同样适用：**dnstap 之类的全量查询日志就是自己查询流的一份副本**。开全量日志却不写保留期（例如 30 天）、不限制访问，等于在"抗元数据聚合"这件事上于自己门口破功——上级权威少拿了一份元数据，本地却攒了一份更完整的。日志字段裁减、聚合统计优先、明确保留期与销毁动作，是同一套最小化的落地。

另一条约束是"信任边界要写进设计文档"：端点运营者是谁、日志落在哪个运维域、是否有第三方 CDN 参与，决定了用户实际把隐私交给了谁；这些问题不是 TLS 版本能回答的。

### 常见误读

**误读一：加密 DNS 服务天然不记录。** 记录与否是策略；协议只保证传输不被路径观察者读到。

**误读二：只要关掉访问日志就符合建议。** 还要处理保留期、字段最小化、填充、ECS、以及 DoH 侧的 HTTP 指纹与第三方参与方。

**误读三：这份文档只约束公共大厂。** 自建一台给家里或机房用的解析器，同样会成为该范围内所有查询的汇聚点；范围小不等于责任小。

## 客户端子网：[RFC 7871]

### 它要解决什么

递归解析器代很多客户端查询时，权威服务器（尤其 CDN）看到的是**解析器的 IP**，于是按解析器位置选节点，客户端可能被指到很远的边缘。[RFC 7871] 定义 EDNS(0) 的 Client Subnet 选项：解析器在出向查询里附带客户端源地址的一个**截断前缀**，让权威侧按客户端大致位置做调度，同时用应答里的 scope 前缀长度约束缓存复用范围。

### 关键条文

- 选项携带地址族、源前缀长度（source prefix-length）与 scope 前缀长度（scope prefix-length）；请求里放的是截断后的前缀，不是完整地址。
- 应答里的 scope 告知"这个答案适用于多宽的前缀"，解析器必须按它构造缓存键；scope 越窄，缓存命中率越低。
- 权威服务器未表明支持时不应发送；解析器对来自不可信客户端的 ECS 选项不应原样透传，也不应把前缀加长到超出自己策略允许的范围。
- 规范给出的是可互操作的机制与部署建议，不是"所有解析器必须开启"的要求（类别与状态见 RFC Editor 索引）。

### 对实现的约束

ECS 与 QMIN 的目标**直接冲突**：QMIN 在减少对上级暴露的元数据，ECS 却在同一个出向报文里主动加入一个按客户端划分的标识。每多一个权威服务器收到该前缀，就多一处能长期按前缀聚合"某网段在查什么"的日志；路径上能读到这一跳的观察者同样拿得到。IPv4 常见的 /24 或 IPv6 常见的 /56 看起来"不精确"，但在小网段、家宽前缀、固定 ULA 环境里足以构成稳定准标识。

运维约束有三条：能不开就不开，把启用范围限制在确实需要地理位置调度的权威服务器白名单内；按 scope 严格分缓存，避免把带 ECS 的应答错误复用到别的客户端；明确记录哪些上游收到了 ECS、保留多久。第三篇把 ECS 列为隐私代价项，条文依据在这里。

### 常见误读

**误读一：只给前缀，所以不算个人信息。** 稳定的前缀加时间加查询内容足以做关联，"截断"不等于"匿名"。

**误读二：不开 ECS，CDN 就完全不工作了。** 调度还有 anycast、解析器自身位置、以及应用侧的其他信号；ECS 是提高精度的选项，不是解析的前提。

**误读三：ECS 是 [RFC 6891] 的一部分所以必须支持。** 它是 EDNS(0) 的一个可选选项，支持与否、转发与否都是策略决定。

## 整体隐私考量：[RFC 9076]

### 它要解决什么

前面每份 RFC 各补一段：QMIN 补元数据最小化、DoT / DoH / DoQ 补一跳加密、ODoH 补参与方分离、ECS 补调度精度、[RFC 8932] 补运营策略。但"DNS 隐私"作为一个整体问题，需要一份把**所有位置、所有参与方、所有非加密维度**列全的威胁模型。[RFC 9076] 承担的就是这个横向梳理：它不定义新协议，而是说明加密之后还剩哪些泄露面。

### 关键条文

- 泄露点遍布全链路：存根到解析器、解析器到各级权威、缓存与转发链、区传送、被动 DNS 采集、日志系统、以及解析器运营者与权威运营者各自的数据留存。
- 可见的不止 QNAME：QTYPE、EDNS 选项、源 / 目的 IP、报文长度、时序、并发模式、失败与重试模式，都能被用于关联与画像；DNSSEC 增加的是可验证的数据，不是保密性。
- 加密一跳会把信任**转移**而不是消除：从路径观察者转移到端点运营者；若端点之后的迭代仍是明文，泄露面只是挪了个位置。
- 参与方数量本身是风险：多个层级的运营者若共享或交换日志，单点的最小化措施会被聚合抵消；共谋与全局被动观察者属于更强的对手，很多机制并不承诺抵御它们。
- 因此文档强调数据最小化、保留期、日志访问控制和可审计的策略，而不是把"是否用了 TLS"当作隐私结论。

### 对实现的约束

对自建部署，最实用的一条是**先画数据流图再谈加密**：列出每个实例各自能看到什么、记什么、留多久、谁能读，然后才决定哪一跳需要 DoT / DoQ、哪一跳可以靠本地根区镜像根本不出网。否则很容易出现"客户端到网关加密了、网关到上游明文、上游又开了全量 dnstap"的组合，而配置审计表上每一格都写着"已加密"。

另一条是明确写出不承诺：QMIN 不承诺抗全路径嗅探，ODoH 不承诺抗流量分析，填充不承诺抗长度画像，DNSSEC 不承诺保密。把承诺边界写进设计文档，比事后解释"为什么还是会泄露"省事得多。

### 常见误读

**误读一：这份文档是某一份协议的实施细则。** 它是横向的隐私考量梳理，用来检查其它 RFC 的覆盖面，不提供开关或参数。

**误读二：只要全网都上加密传输，DNS 隐私问题就解决了。** 端点运营者、权威服务器、日志留存与流量分析仍在模型里。

**误读三：隐私与可观测性二选一，只能牺牲一边。** 真实取舍是"最小化 + 明确保留期 + 聚合优先"，而不是关掉全部日志或全量留存两个极端。

## 两个收尾判断

### denylist 不是证明

第三篇里"按 IP 封 443 不如 canary 域准"这条实测结论，值得在理论层说透。把已知 DoH 端点 IP 收进一张拒绝列表，得到的是一个**枚举型否定**："匹配到列表里的地址时才拦截"。它既覆盖不全——新端点、共享 IP、CDN 与 anycast 之后的同一地址、以及和 Web 共端口的自建端点，都可以不在表里；也容易过度——同一个 IP 上跑着别的服务时，封禁会误伤。更关键的是，**"没有被列表命中"不是"查询确实经过了本地解析器"的证据**：客户端可以直连一个表里没有的端点，网络侧只看到 443，什么也证明不了。

能称为证据的是**肯定性的观测**：本地解析器自己的查询日志或 dnstap 流里出现了这条查询；canary 域按预期返回了规定的 NXDOMAIN / NODATA；或者受控客户端的连接目标与解析器地址一致。名字层的本地服务区判定（`_dns.resolver.arpa.` 返回 NODATA、浏览器 canary 回 NXDOMAIN）之所以比封 IP 更可靠，是因为它作用于**客户端的决策逻辑**，而不是试图穷举客户端可能连到哪里。这一区分在加密流量里尤其重要：报文不可读之后，唯一可靠的观测点就只剩自己这一侧的日志。

一句话：**denylist 是一种拦截手段，不是一种证明方法**。把它写进合规或验收结论里，等于用"没抓到"代替"没发生"。

### 抗聚合 ≠ 抗全路径嗅探

QMIN 的收益要放在正确的对手模型下衡量。它把完整 QNAME 从根、TLD 等"本不需要知道"的层级上拿掉，使这些运营者难以长期按完整域名聚合"谁在查什么"；这是**抗元数据聚合**，对手是分散在多个层级、各自只看一段、但会把日志留很久的运营者。它不改变任何一跳的明文属性，也不改变最终权威服务器必须看到完整 QNAME 这一事实。

而一个在解析器出向链路上的被动观察者，看到的是**全部**迭代查询：每一次最小化后的中间名、最后一次完整 QNAME、QTYPE、时序、长度、目的地址。本地根区镜像能把根这一跳从出向链路里消掉，收益落在 TLD 与二级权威层；但链路其余部分仍在该观察者的视野里。这就是"抗聚合"与"抗全路径嗅探"的差别：

| 维度 | 抗元数据聚合（QMIN 等） | 抗全路径嗅探 |
|---|---|---|
| 对手 | 多个只看见局部的权威运营者 | 单一链路上看见全部报文的观察者 |
| 手段 | 减少每跳携带的标签、限制留存 | 该跳的传输加密，或让该跳根本不出网 |
| 覆盖 | 解析器到各级权威（部分层级） | 某一跳的全部字节与元数据 |
| 剩余可见 | 最终权威仍见完整 QNAME、解析器见全部 | 加密后仍见长度、时序、目的 IP |
| 与 DNSSEC 关系 | 无关 | 无关（DNSSEC 不提供保密性） |

因此全书反复用两句话收口：**QMIN 不是加密**；**加密传输只覆盖它被部署的那一跳**。把"上级少拿了一份元数据"读成"链路上没人能看见"，会把威胁模型里的一个对手换成另一个，却以为已经赢了。同理，ODoH 的两跳分离对付的是"端点同时看到 IP 与查询"，不是"有人能看到全部流量"；自建可信 target 时收益约等于零，也是同一个道理——对手模型没变，加一跳不会凭空产生保护。

## 本章要点

- [RFC 7816] 用固定 NS 类型问中间层；[RFC 9156] 废弃它并**改回保留原始 QTYPE**，因为 NS 被权威服务器特殊对待、会让应答语义失真。relaxed 遇异常回退完整 QNAME，strict 依 [RFC 8020] 不回退，因此会撞上"父名 NXDOMAIN、子名却存在"的违规区，且错误结论被 [RFC 2308] 负缓存逐层记住。
- DoT（[RFC 7858]，TCP 853）、DoH（[RFC 8484]，HTTPS 443）、DoQ（[RFC 9250]，专用 QUIC）都只保护**存根到解析器这一跳**；[RFC 8310] 的 Strict / Opportunistic 两档决定认证或握手失败时能否静默退回明文，严格档必须 fail-closed。
- [RFC 9230] 的 ODoH 靠 relay 与 target 分离实现"见 IP 不见查询 / 见查询不见 IP"；**自建可信 target 时收益约等于零**——你本来就信任它，而独立 relay 又成为新的 IP 观察者，两跳自建则日志一关联即还原。
- [RFC 9462] 的 `_dns.resolver.arpa.` 发现机制给客户端一条自动绕过本地解析器的路径，本书以本地 NODATA 与浏览器 canary 域压制它；[RFC 7871] 的 ECS 与 QMIN 目标直接冲突，[RFC 8932] 与 [RFC 9076] 则把日志、保留期、流量分析与运营者责任补进威胁模型。
- **denylist 不是证明**：按 IP 封禁是枚举型否定，"没命中"不等于"查询走了本地解析器"，证据只能来自自己这一侧的肯定性观测。**抗聚合 ≠ 抗全路径嗅探**：QMIN 抗的是多个权威运营者的元数据聚合，不加密任何一跳，链路上一个被动观察者仍看到全部迭代查询。
