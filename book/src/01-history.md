# 第一篇 认识 DNS 与 Unbound {.unnumbered}

# Unbound 的历史演进

Unbound 不是某家厂商为了补齐产品线而做的 DNS 组件，它是带着一个明确问题出生的：当互联网上绝大多数递归解析器都跑着同一套代码时，一个解析器自身的漏洞就不再是"某台机器的故障"，而是全局性的单点风险。理解这条设计动机，比记住版本号更重要——它解释了为什么一个只做递归验证的实现会刻意把边界收得那么窄。

## 两个名字：BIND 是什么，Unbound 又是什么

先把名字说清楚，后面十几章才不会含混。

**BIND = Berkeley Internet Name Domain**。1980 年代初诞生于加州大学伯克利分校的计算机系统研究组（CSRG），由 DARPA 资助，Douglas Terry、Mark Painter、David Riggle、Songnian Zhou 四名研究生完成，随 4.3BSD 发行。它的主进程叫 `named`（name daemon），`dig`、`nsupdate` 与 resolver 库都出自同一套软件包。ISC 的《The History of BIND》与 BIND 9 官方文档都这么写。

**Unbound 的名字与 BIND 没有词源关系**。2008 年 5 月 20 日的官方发布新闻稿给出的定位是「a secure, high-performance **alternative to** BIND」—— 是**作为 BIND 的替代方案**，不是从 BIND 这个词拆出来的。官方历史页只说它是一个「开发独立开源 DNS 软件与文档」的项目，**没有公布过命名故事**。因此「unbound 取『不受束缚』之意、不被权威与递归双重职责绑住」是常见解读，本书按**推断**标注，不作为官方词源引用。

后来 Unbound 在 FreeBSD、OpenBSD 里取代 BIND 成为 base system 默认解析器，那是**结果**，也不是命名原因。把这两件事分开，才看得清第 1 章后面那条主线：Unbound 的取舍不是「比 BIND 多几个功能」，而是**主动把职责收窄**。

## 起点：解析器单一化带来的系统性风险

2000 年代中期，需要自己搭一台递归解析器的运维人员，可选项实际上不多。BIND 9 几乎等同于"DNS 服务器"这个词的默认实现：它既能做权威服务器，也能做递归解析器，还能做转发、区域传送、动态更新、视图（view）、访问控制列表，以及后来加入的 DNSSEC 全套能力。功能齐全是优点，但代价是代码体量、配置语法的规模，以及一个不那么直观的事实：

- 一台只想要"帮我查域名并验证签名"的机器，也必须承载一整套权威服务器的代码路径；
- 配置面越大，运维误配的概率越高，审计时需要读完的代码也越多；
- 更关键的是，如果绝大多数解析器共享同一个实现，那么该实现的一个远程漏洞会同时影响整个互联网，这就是所谓的**解析器单一化（resolver monoculture）**风险。

Unbound 项目自身的早期需求文档把这一点写成了明确的工程目标，原文列出的目标里包括"code diversity in the DNS resolver monoculture"（在递归解析器的单一化格局中提供代码多样性）、"drop-in replacement for BIND apart from config"（除配置语法外可作为 BIND 的替代）、以及"smallest as possible component that does the job"（尽可能小的、刚好够用的组件）。同一份文档的 non-goals 只有两条，值得原样记住：**不做权威服务器**、**不要过多特性**。

这两条约束决定了后面十几年的所有取舍。Unbound 的"小"不是功能少，而是**边界清晰**：递归、缓存、DNSSEC 验证是它的职责，权威应答、DHCP、服务发现、Web 界面不是。第二篇第 4–7 章会看到，正是这个清晰的边界让"按角色拆成多个实例"成为一种可维护的部署方式，而不是被迫的权宜之计。

### 为什么「可审计」和「安全」是同一件事

需求文档里把设计拆成三个可替换的模块：验证器（validator）、迭代器（iterator）、缓存（cache），网络与查询管理代码只负责把它们串起来。这个划分不是软件工程洁癖，它有直接的安全含义：

- **迭代器**只负责向层级中的权威服务器发问，它不信任应答里的附加内容；
- **验证器**只负责检查 DNSSEC 签名链，它不参与发包；
- **缓存**只存放被前两者认可的数据。

于是"一个伪造的应答能不能进缓存"这个问题，可以被收敛到一条明确的路径上审查，而不是散落在几万行代码的各个分支里。Unbound 后来把清理应答、丢弃不该进缓存的附加数据的组件叫 **scrubber**（清理器）。2008 年缓存投毒事件爆发时，官方历史文档给出的结论正是：由于设计时已经采用了最大程度的查询端口与查询 ID 随机化、并且清理器不会把不信任的数据写入缓存，Unbound 不需要为这次漏洞紧急打补丁来补齐抗 forged-reply 能力。

这不是说 Unbound 天然免疫一切攻击。同一份文档明确写着：对 Kaminsky 所描述的那类缓存投毒，**只有 DNSSEC 是完整的解决方案**，端口随机化、0x20 大小写编码等手段只是提高伪造难度。把这个边界讲清楚很重要：DNSSEC 提供的是**数据完整性与来源认证**，而后面章节提到的 DoT、DoH、DoQ 提供的是**传输加密与隐私**，两者不互相替代。历史章节里最容易犯的错，就是把「抗投毒」和「加密传输」当成同一件事来叙述。

## BIND 的体量、安全史与「可审计」的含义

谈「为什么需要一个只做递归验证、小而可审计的实现」，绕不开 BIND。BIND 是 DNS 协议最早的参考实现，从 BIND 4、BIND 8 到后来重写的 BIND 9（重写年份见 ISC 官方资料），长期承担双重角色：既是互联网上多数权威服务器（authoritative server）的运行环境，也是多数递归解析器的运行环境。ISC 的公开公告与 CVE 记录里，BIND 9 多年间出现过远程拒绝服务、缓存投毒、断言失败、动态更新与区域传送路径上的问题；2008 年的补丁公告由多家厂商同时发布，说明这不是某一家的配置失误，而是**同一类递归逻辑在多个实现里同时存在的缺陷**。

这里要避免一个不严谨的推论：「CVE 多 = 质量差」。更准确的说法是三条：

- 部署面越广、代码路径越多，被研究者审视得越充分，公开漏洞数量自然更多；
- 权威 + 递归 + 动态更新 + 视图（view） + 区域传送都在一个进程里，任何一条路径的缺陷都可能影响另一条路径上的数据；
- 对运维而言，**能被完整读完并审计的代码量**，直接决定了「这次升级到底改了什么」能不能自己判断，而不是只能相信发布公告。

第三条才是 Unbound 需求文档里 `code diversity` 与 `smallest as possible component` 的真实指向。代码多样性不是为了证明谁更安全，而是为了让一次实现层面的漏洞不至于同时打穿所有解析器；小而专注的实现，则是让运维在出事时能沿着一条明确路径把因果链走完。2008 年那次事件里，Unbound 因清理器不把不信任的附加数据写入缓存、且端口熵从设计之日就取满，得以在不紧急改架构的前提下应对——这是**边界清晰带来的红利**，不是「代码少所以没 bug」。

顺带说明本书的立场：BIND 至今仍是权威服务器与复杂企业场景里成熟、可靠、文档完备的选择，第 2 章会按角色做取舍对照。这里讨论的是**当需求被限定为「只做递归验证」时，全能实现的额外代码路径是否还值得承担**，而不是给产品排座次。

### 2008 年的外部冲击：一次全行业压力测试

2008 年，Dan Kaminsky 披露了一类影响广泛的 DNS 缓存投毒漏洞（CVE-2008-1447 相关公告）。攻击者不需要猜中某个特定域名的应答，而是可以通过反复触发对同一父域下随机子名的查询，制造大量"在途查询"，从而在较短时间里撞中 16 位查询 ID 与源端口的组合，把伪造的权威应答塞进缓存。伪造数据一旦带上很长的 TTL，会把后续所有访问导向攻击者指定的地址。

把攻击面拆开看，会更清楚为什么「代码体量」是个安全指标：

- 查询 ID 只有 16 位，若出向源端口固定或可预测，攻击者需要撞中的空间只剩下 65536；
- 攻击者可以自己发起对目标域下大量随机子名的查询，制造许多在途请求，从而同时尝试多组伪造应答；
- 一旦有一次命中，伪造应答里可以夹带指向目标域的 NS 与胶水记录（glue record），把整个域的后续解析都引到攻击者控制的地址；
- 伪造记录通常带很长的 TTL，清掉它不是重启进程就一定能解决，链路上每一层缓存都要处理。

最后两条在本书后面的故障案例里会再次出现：一是**域外夹带的 glue 是经典缓存投毒面**，二是**负缓存（negative caching）与长 TTL 会放大一次瞬时故障**。它们不是配置细节，而是 DNS 数据模型本身的性质。

对本书读者而言，这件事的意义不在于复现攻击，而在于它把两条结论钉死了：

1. 递归解析器的**熵来源**（查询 ID、源端口、0x20 大小写）是安全边界的一部分，不是性能细节；
2. 只要签名验证链没有铺开，缓解措施就只是提高成本，不是消除风险。

Unbound 的 1.0 恰好在这段时间内发布。它在 1.0 中实现了基于 ARC4 随机例程的查询 ID 与端口随机化，并从"未分配端口池"中随机选取出向端口；1.0.2 的补丁公告里又追加了一批此前为避免被逆向推导而暂缓公开的对抗措施。也就是说，Unbound 的"默认安全"不是后来营销出来的定位，而是它在第一次公开亮相时就带着的设计前提。

## 从 Java 原型到 C 实现

### 2004：架构与资助

按通行记载，Unbound 的设计工作始于 2004 年，由 **Jakob Schlyter（Kirei）** 与 **Roy Arends（Nominet）** 提出架构，项目由 **VeriSign** 与 **EP.NET** 资助，早期的 Java 原型由 **David Blacka、Matt Larson** 等人实现。原型采用 BSD 许可，目标是做一台"full-service, iterative-mode, validating DNS resolver"——完整的、迭代模式的、带验证的解析器。

Nominet 与 VeriSign 的参与不是偶然：前者运营国家级顶级域，后者运营根与顶级域基础设施，双方都对"递归侧不能被单一实现垄断"有直接利益。关于早期参与者名单，不同史料的表述略有出入——官方需求文档把项目的起始归为 Bill Manning、David Blacka、Matt Larson，并记载 Java 原型获得了 Geoff Sisson 与 Roy Arends（Nominet）的贡献；Java 原型页面则写明项目由 VeriSign 与南加州大学信息科学研究所（USC/ISI）共同资助。**年份与参与者在不同来源间不完全一致时，请见官方手册的历史章节与 NLnet Labs 发布说明**，本书不为具体人名与年份做超出来源的断言。

### 原型到底验证了什么

Java 原型不是"先写个能跑的版本再说"。原型页面明确说明：Java 被选中的理由是 **dnsjava** 库质量好、且主要开发者熟悉它，而最终实现语言从一开始就定为 C。原型的目的是**验证一种设计**：把解析器拆成一条模块链，既可以组装成完整的递归解析器，也可以只取出其中几段，组装成一个"带 DNSSEC 验证的存根解析器"。缓存等少数关键组件还允许替换实现。

这段历史直接解释了 Unbound 后来两个长期特征：

- `libunbound` 能把解析能力嵌进应用程序，而不是必须起一个守护进程——这是"模块链可裁剪"的遗产；
- 配置文件里 `module-config` 这一行的存在感很强——模块次序（例如验证器、迭代器、缓存类模块的先后）是设计层面的概念，不是后来加的补丁。

原型本身是事件驱动、异步的服务器：每个收到的报文被转成一个事件，定时器与内部生成的查询也是事件。这个模型在 C 版本里被保留下来，也是 Unbound 能用少量线程承载大量在途查询的原因。

### 2006 年底：NLnet Labs 加入并用 C 重写

大约 2006 年，项目产生了"做一个可部署的、完整的 C 实现"的想法，**NLnet Labs** 承担了这次实现。官方需求文档的原文是"Around 2006 the idea came to create a full-fledged C implementation ready for deployed use. NLnet Labs volunteered to write this implementation."

NLnet Labs 当时已有 **NSD**（一个只做权威服务器的实现）的开发经验，把"只做一件事、把它做干净"的工程习惯带到了 Unbound：C 实现延续了 BSD 许可、模块划分与"不做权威服务器"的边界，同时也复用了不少底层库与构建经验。**Wouter Wijngaards** 是这一阶段及之后长期的主要开发者。

值得注意的是方向上的对称：NSD 把"权威"这一半从 BIND 式全能服务器里切出来，Unbound 把"递归 + 验证"这一半切出来。两者都不试图覆盖对方。本书第二篇第 6 章讲本地根区镜像时会再碰到这个分工，但那里是配置问题；此处只需记住，**Unbound 从来不是"半个 BIND"，而是一个边界先定好、再填功能的实现**。

### 2008-05-20：1.0 公开发布

**2008 年 5 月 20 日**，Unbound 1.0 随一份联合新闻稿公开发布，参与方为 NLnet Labs、VeriSign、Nominet 与 Kirei，采用 **BSD 许可**。官方历史页的表述是"It was released in May 2008 with this press release"，并说明 C 实现基于一份 Java 原型。具体的发布日期与联合发布方名单，以官方手册与 NLnet Labs 发布说明为准；不同二手资料在"5 月"内部的具体日子上偶有差异，本书采用 5 月 20 日这一通行记载，不据此派生其他日期。

1.0 已经具备：迭代解析、缓存、DNSSEC 验证、端口与查询 ID 随机化、清理器、存根区域（stub zone）支持。换句话说，1.0 不是「能跑起来的骨架」，而是**带着完整安全模型的第一个版本**。官方历史文档里还保留了 1.0.2 的补丁公告、2008 年缓存投毒说明、超时与服务器选择算法说明、信任锚说明等技术文档，这些是研究早期设计取舍的一手材料。

### 许可与治理：BSD 与「谁在维护」

从 Java 原型到 C 实现，许可始终是 **BSD**。这件事对运维的实际影响比想象中大：

- 发行版可以无阻碍地打包，嵌入式与路由器固件可以集成，也允许被其他项目以库形式链接（`libunbound`）；
- 没有 copyleft 的传染性要求，商业设备与内部工具可以按需修改；
- 反过来，BSD 也意味着**没有人为你的部署兜底**：安全公告、升级节奏、默认值变更都要自己跟。

治理结构上，NLnet Labs 承担主要开发与文档维护，开发讨论与用户支持通过公开的邮件列表与代码仓库进行。对本书读者更实用的一条经验是：**发行版仓库里的 Unbound 版本常常明显滞后于上游**，而 `unbound -V` 与 `unbound-control status` 才是判断本机实际能力的依据。第三篇讨论某个参数是否可用时，先确认版本，再查该版本的手册，不要拿最新版文档的默认值去套旧包。

### 一条需求，三种读法

把「只做递归验证」这句口号落到运维语言里，可以拆成三个可验证的判断，后面各章的配置选择都会回到它们：

| 判断 | 具体含义 | 违反了会怎样 |
|---|---|---|
| 只做递归 | 不承载权威区域、不做区域传送、不做动态更新 | 权威侧的配置复杂度与故障半径被带进递归侧 |
| 默认验证 | 信任锚就位时按签名链判断应答，坏签名返回 SERVFAIL | 无锚或 permissive 模式下，坏签名应答也会被放行 |
| 小而可审计 | 处理链由少数几个模块组成、行为可由日志与统计复现 | 出事时只能靠重启和猜，无法定位是哪一层缓存 |

第三条在本书后续章节里最容易被低估。运维真正需要的不是「代码行数少」这个事实，而是**故障时可复现的因果链**：一次 SERVFAIL 究竟是上游超时、验证失败、负缓存命中、还是过期缓存应答的刷新超时，必须能从日志与统计里读出来。第 1 章讲历史，第 2 章讲角色，第三篇讲验证命令，都是围绕这条能力展开的。

| 见官方手册 | DoT 相关能力、libunbound、pythonmod、QMIN、cachedb | 传输加密、嵌入式调用、模块扩展、元数据与共享缓存 |
| 见官方手册 | `edns-buffer-size` 默认 1232 | 分片导致 TCP 回退的默认值修正 |

### 读版本说明的正确姿势

在逐条看特性之前，先约定一条方法，避免把「大致时期」写成「确定事实」：

- 官方手册里标注为 `New in version X.Y.Z` / `Changed in version X.Y.Z` 的，才写成确定版本；
- 其他只在任务描述、邮件列表或新闻稿里出现过的时期，一律写成「见官方手册与 NLnet Labs 发布说明」；
- 发行版打包版本与上游版本不是一回事，能力判断以本机 `unbound -V` 为准；
- 默认是「当前默认」而非「历代默认」，例如 `edns-buffer-size` 的 1232 来自 DNS Flag Day 2020 推荐，早期默认值不同。

这条约定也解释了为什么本章的速查表里有几行故意留白：宁可让读者去查一手来源，也不要生产一个看似精确、实际无法核验的版本号。

### DLV：根尚未签名时的过渡方案

DNSSEC 的验证链需要一个信任锚（trust anchor）。在根区尚未签署、或信任链上端不完整的年代，**DLV（DNSSEC Lookaside Validation，[RFC 4431]）** 提供了一个"旁路信任仓库"：把本来应该从根逐级验证的锚，改为从一个 DLV 仓库查询。Unbound 1.1 加入了 DLV 支持（官方历史页在介绍 1.1 时明确提到 "Unbound 1.1 has DLV support and improved statistics"）。

DLV 的历史意义是**过渡性**的：它让验证器在根签名空窗期仍然有活可干。随着根区完成签名、[RFC 5011] 定义的信任锚自动更新机制成为常态，DLV 退出主流配置。今天再提它，是为了说明"信任锚从哪来"这个问题曾经有过别的答案——第三篇第 10 章讲信任锚时，会看到为什么转发器上配自动信任锚是行不通的。

### 信任锚的三种状态

DLV 之所以存在，是因为「验证」这件事有一个容易被忽略的前提：**验证器必须先有一个可信的起点**。这个起点叫信任锚（trust anchor），通常就是根区的密钥。围绕它，解析器实际会呈现三种状态，第三篇会详细展开，此处先建立词汇：

| 状态 | 行为 | 运维可见的现象 |
|---|---|---|
| 无信任锚 | 透传应答，不验证签名 | 坏签名域照样返回答案，看起来一切正常 |
| permissive 模式 | 记录日志但放行 | 日志里有验证失败，客户端仍拿到应答 |
| 真验证 | 坏签名 → SERVFAIL；好签名 → 应答带 AD 标志 | 坏签名域整体失败，好签名域可凭 AD 位确认 |

注意第三种状态里的 AD 位：它是**解析器向客户端声明「我验证过了」**的标志，不是数据本身自带的属性。第 3 章会把 AD、CD 与 RD、RA 放在同一张报文位表里讲清楚。历史章节只需记住：DLV 与 [RFC 5011] 都是在解决「起点从哪来、怎么更新」，而不是在解决「传输路上有没有被偷看」。

### DNSSEC 默认验证：从可选到基线

早期 DNSSEC 验证常被视为"要显式打开的高级特性"。Unbound 的演进方向相反：**验证成为默认假设**，运维要操心的是"锚是否就位""验证失败要不要放行"，而不是"要不要启用验证"。与之配套的是三种可观测的状态：无信任锚时透传不验证坏签名、permissive 模式记录日志但放行、真正验证时坏签名直接返回 SERVFAIL 且好签名带 AD 标志。

这个转变把安全责任从"运维记得勾选"移到了"实现默认如此"。它也是本书反复强调"验证状态必须可验证"的原因：默认开着不等于真的在验证，锚缺失或被显式降级时，解析器看起来一切正常。

### libunbound 与 pythonmod：把能力交给应用程序

**libunbound** 让应用程序以库的形式调用解析能力（同步与异步接口、线程上下文、DNSSEC 结果检查），不必自己起守护进程，也不必依赖系统存根解析器的行为。**pythonmod**（官方手册称 Pyunbound / Python 模块）则允许用 Python 编写 Unbound 的模块，插入到处理链里做定制逻辑。

这两项是"模块链可裁剪"设计的直接兑现。它们的取舍也很清楚：库接口把信任边界移到了进程内，适合做专门的探测、校验或嵌入工具；Python 模块带来灵活性，但也把一段自定义代码放进了解析热路径，性能与故障半径都要自己承担。第一篇只交代它们为何存在，配置与调用放到后续实战章节。

### 模块链与配置的对应关系

`libunbound` 与 pythonmod 不是两个孤立特性，它们是同一套模块链设计的两种出口。官方手册的配置参考里，`module-config` 一行决定处理链上有哪些模块、按什么顺序排列；例如子网缓存模块要求排在迭代器之前，cachedb 模块则给出 `validator cachedb iterator` 这样的次序示例。

对运维的含义是：**功能不是开关，而是链上的位置**。插错位置会表现为「参数明明写了却不生效」，而不是报错。这个现象在第二篇第 4–7 章按角色配置时会反复出现，本篇只把它作为历史遗产记录下来：2004 年的原型为了「能组装成不同形态的解析器」而设计了模块链，二十年后它依然决定了配置文件的写法。

### 加密传输：DoT、DoH、DoQ

**DoT（DNS-over-TLS，[RFC 7858]）** 用专用端口 853 把 DNS 报文直接装在 TLS 里；**DoH（DNS-over-HTTPS，[RFC 8484]）** 在 DNS 报文与 TLS 之间加了一层 HTTP（Unbound 的下游 DoH 要求 HTTP/2，靠 ALPN 协商，以满足流水线与乱序处理的性能需要）；**DoQ（DNS-over-QUIC，[RFC 9250]）** 走 QUIC，用加密的多路复用承载 DNS。

时间线上有两个容易被混淆的点，值得写清：

- 官方手册的 DoH 章节记载，Unbound **早在 2011 年就能处理 TLS 加密的 DNS 报文**，远早于 IETF DPRIVE 工作组启动 DoT 规范工作；而作为正式配置能力的下游 DoT/DoH 支持是后来的事。把"代码里出现过 TLS 处理"和"作为标准特性发布"混为一谈，是常见的年份错误来源。
- 下游 DoH 在官方手册中标注为 "New in version 1.12.0"，下游 DoQ 标注为 "New in version 1.22.0"（且早期需要带 QUIC 支持的 OpenSSL 分支，1.24.0 起可用 OpenSSL 3.5.0 及以上）。任务描述里提到的"1.7 前后"可视为 DoT 相关能力趋于可用的大致时期，**确切版本以官方手册对应章节为准**。

三者解决的问题是**传输加密与隐私**（链路上的观察者、客户端对解析器的身份认证），不解决"应答数据是否被伪造"——那是 DNSSEC 的职责。第三篇第 11、12 章会分别落地 DoT 与 DoH 的服务端/客户端配置，第四篇第 17 章才做 [RFC 7858] / [RFC 8484] / [RFC 9250] 的协议层对比，本篇不展开配置。

### 三种加密传输的角色边界

把三者并列时，最容易写错的是「谁在服务端、谁在客户端」：

| 协议 | 承载 | 端口 | 在本章语境里的定位 |
|---|---|---|---|
| DoT | DNS 报文直接装在 TLS 里 | 853 | 专用端口，链路边界清晰，便于策略管控 |
| DoH | DNS 报文经 HTTP/2 再经 TLS | 443 | 与 Web 流量共存，穿透性好但边界模糊 |
| DoQ | DNS 报文经 QUIC | UDP 853 类专用端口 | 加密 + 多路复用，依赖库较新 |

三者都只覆盖**客户端 ↔ 解析器**或**解析器 ↔ 上游**这一段链路，都不改变「解析器仍需自己做迭代、缓存与验证」这一事实。第 1 章交代它们出现的顺序与动机，第三篇第 11、12 章分别落地 DoT 与 DoH 的服务端/客户端，第四篇第 17 章做协议层对比。

### 过滤能力：RPZ 与本地策略

Unbound 一直有 `local-zone` / `local-data`（对指定名字直接给本地应答）与 `respip`（改写含指定地址的应答）这两类本地手段，但它们都是 Unbound 专有语法。**RPZ（Response Policy Zones）** 的意义在于用一种跨实现通用、且可由外部源通过区域传送直接加载的格式表达过滤策略，运维不必为不同厂商的解析器各维护一份策略、也不必手工转换格式。

官方手册标注 RPZ 于 1.10.0 首次引入（仅 QNAME 与 Response IP Address 触发器），1.14.0 补齐完整的触发器与动作集合。它的取舍和过滤本身一样：策略越集中，误拦时的排查面越大；而本地策略直答与递归验证之间的优先级，也会直接影响故障现象。

### 过滤与验证的优先级

过滤策略一旦介入，就会和「递归验证」这个默认职责产生张力：本地直答的名字没有签名链可验，改写过的应答也不再是权威服务器原样给出的数据。因此 RPZ、`local-zone` / `local-data`、`respip` 这类能力在工程上必须明确两件事：

1. 这条策略作用于**哪个信任域**（是只对内网客户端生效，还是对所有经过本实例的查询生效）；
2. 策略命中时，客户端**能不能分辨**这是本地策略而非权威数据。

第二篇会用「一台机器上跑多个实例」来隔离不同过滤表，第 3 章给出动机。历史章节只需指出：RPZ 解决的是策略表达与分发的标准化问题，它不替代验证，也不改变验证器的位置。

### 过期缓存应答：serve-stale 与 [RFC 8767]

缓存的 TTL 是权威服务器与缓存解析器之间的契约：过期就不该再用。**过期缓存应答（serve-stale）** 是对这份契约的有条件例外：[RFC 8767] 规定，当 TTL 到期后数据无法从权威侧刷新时，可以把它当作未过期来使用，目的是在权威或链路不可用时提高韧性。

Unbound 的 `serve-expired` 早于该 RFC 存在，最初目的是提高缓存命中率；官方手册记载 1.6.0 引入、1.11.0 引入 [RFC 8767] 行为、1.23.0 起 RFC 行为成为新的默认。这里有一个在实战中反复被误读的细节：`serve-expired-client-timeout` 的单位是**毫秒**（默认 1800，即 1.8 秒），语义是"先尝试刷新，超过这个时间才回过期缓存"，不是 1800 秒。第三篇第 10 章与第五篇第 22 章会把它与负缓存放大故障的现象放在一起讲。

### 可用性与正确性的交换

过期缓存应答是把「正确性」换「可用性」：TTL 到期意味着权威服务器不再授权你使用这份数据，[RFC 8767] 给的例外是「刷不到就用旧的」。这个交换有一个常被忽略的放大效应——**负缓存（negative caching）也会放大故障**。上游一次瞬时 NXDOMAIN 会按 SOA minimum 被缓存（常见 3600 秒），权威侧修好之后客户端仍在失败；若链路上有多个实例，每一层的缓存都要刷，只刷最靠近客户端那一层没用。

因此读 [RFC 8767] 时，要把它和 [RFC 2308] 的负缓存一起读：一个决定「旧数据能不能用」，一个决定「不存在这件事能被记多久」。第五篇第 22 章的故障案例会把这两种现象放在同一条排查链里。

### 查询名最小化：从 [RFC 7816] 到 [RFC 9156]

**查询名最小化（QNAME minimisation）** 的想法很朴素：向顶级域服务器询问时，没必要把完整的 `www.example.org` 都发过去，只需要问到定位下一级委派所必需的标签数。它减少的是发给上级的 QNAME 标签数量，从而限制元数据聚合的范围。[RFC 7816] 是早期的实验性描述，[RFC 9156] 是后续修订。

必须与加密传输划清界限：**查询名最小化不是加密**，它不抗全路径嗅探；如果根这一跳本来就走本地根区镜像、不出本机，收益主要落在 TLD 层。另一个方向上的教训是严格模式的兼容性：某些大型 CDN 的 CNAME 区违反 [RFC 8020]（父名返回 NXDOMAIN、子名却存在），`qname-minimisation-strict: yes` 会在中间层拿到 NXDOMAIN 就直接收工，导致整站静态资源解析失败。第三篇第 13 章讲参数与兼容坑，第四篇第 17 章讲 [RFC 7816] → [RFC 9156] 的演进，本篇只交代它在历史里的位置。

### 隐私特性之间的分工

把查询名最小化、加密传输、DNSSEC 三者的边界画成一张表，比反复用文字强调更不容易混淆：

| 机制 | 防的是谁 | 不防的是谁 | 相关 RFC |
|---|---|---|---|
| DNSSEC 验证 | 伪造/篡改应答的中介 | 链路上看得到查询内容的观察者 | [RFC 4033] 等 |
| 查询名最小化 | 上级服务器对完整查询名的元数据聚合 | 全路径嗅探者、本机解析器本身 | [RFC 7816] / [RFC 9156] |
| DoT / DoH / DoQ | 客户端与解析器之间的链路观察者 | 解析器向权威侧发出的迭代查询 | [RFC 7858] / [RFC 8484] / [RFC 9250] |

最后一列尤其重要：**加密传输保护的是一段链路，不是整条解析路径**。一台本地递归解析器即使对客户端提供 DoH，向上游权威服务器发出的迭代查询依然可能走明文 53。这正是「为什么需要一个自己做迭代与验证的本地实现」在隐私语境下的答案——只有把递归放在自己可控的机器上，才谈得上整条链路的策略。

### EDNS 1232：被 MTU 教育出来的一次默认值变更

EDNS(0)（[RFC 6891]）允许在 UDP 报文里通告"我能重组多大的应答"。早期运维习惯把 `edns-buffer-size` 调大到 1472 甚至更高，以减少 TCP 回退。但当链路上存在 MTU 1280（IPv6 最小 MTU、部分隧道）或 PPPoE 1492 时，大报文会分片；分片一旦被丢弃，表现不是"报文变小"，而是**等超时再重试 TCP**，延迟陡增。

Unbound 当前官方默认值为 **1232**，来源是 DNS Flag Day 2020 的推荐；`max-udp-size` 同样默认 1232，但两者方向不同：`edns-buffer-size` 是**出向**通告给对端的重组缓冲大小，`max-udp-size` 只管**入向**应答的最大 UDP 尺寸。把入向调小却期望出向不分片，是这类故障里最常见的误判。这个数字看起来只是个默认值，实际上是"协议设计向真实链路条件让步"的一个标本。

### 两个方向，别调反

`edns-buffer-size` 与 `max-udp-size` 的默认值同为 1232，但方向相反，是实战中最容易调反的一对：

| 参数 | 作用方向 | 管的是什么 |
|---|---|---|
| `edns-buffer-size` | 出向 | 向权威服务器通告「我能重组多大的 UDP 应答」 |
| `max-udp-size` | 入向 | 本实例返回给客户端的 UDP 应答最大尺寸 |

把入向调小、却期望出向不分片，不会有任何效果；反过来把出向调到 1472，在 MTU 1280 的隧道或 PPPoE 1492 链路上会产生分片，分片被丢后表现是**等超时再重试 TCP**，而不是「报文自动变小」。这也是为什么本书把 1232 当作默认基线，而不是一个可随意调大的性能旋钮。

### cachedb / Redis 与 ECS 取舍

**cachedb** 模块允许把缓存放到外部后端：官方手册说明，编译时使用 `--with-libhiredis` 且系统装有 hiredis 时，可用 **Redis** 作为持久或共享的缓存后端。它解决的是"多个实例如何共享一份缓存""重启后缓存不丢"这类运维问题，代价也写在同一段文档里：Redis 后端是同步通信，后端变慢会拖住查询处理；缓存有效性由管理员负责，模块不会替你判断数据是否还该用。

**EDNS Client Subnet（ECS，[RFC 7871]）** 则是 Unbound 明确"取舍"而非"拥抱"的领域。它的动机是让权威服务器按客户端所在网段返回更近的 CDN 节点，但代价是把客户端地址信息向上游扩散，同时把缓存从"按查询名"变成"按查询名 + 网段"，命中率与隐私都受损。官方手册的子网缓存模块说明因此把发送范围做成显式白名单（`send-client-subnet` / `client-subnet-zone`），并提醒启用后缓存与性能会受影响。

把这两项和前面的查询名最小化、加密传输放在一起看，能看到一条贯穿十几年的主线：**Unbound 对"多泄露一点信息换一点便利"的功能，默认倾向是关掉或收窄，而不是默认打开**。这不是性能判断，是隐私与安全基线上的选择。

### 一条贯穿十几年的默认立场

把 ECS、cachedb、查询名最小化、加密传输放在一起看，会发现一条一致的设计倾向：**凡是「多泄露一点信息、或多引入一个外部依赖，换一点便利」的功能，默认都关着或收得很窄**。ECS 需要显式白名单，cachedb 需要显式编译并启用模块，查询名最小化的严格模式默认不咬人，加密传输需要自己配证书与端口。

这不是保守，而是把「信任域」的判断留给部署者：ECS 与 cachedb 需要显式启用，加密传输需要自己配证书与端口，查询名最小化的严格模式要按自身兼容性评估后再决定是否打开，默认值与适用条件均见官方手册。不同上游、不同过滤表、不同信任域本就应该由不同实例承担，而不是在一个实例里用一堆开关互相覆盖——第 3 章会把这个动机展开成四种角色的串联图。

## 书目史料：第一本记录 Unbound 的书

早期可查的书目材料里，第一本系统记录 Unbound 的是 **Jan-Piet Mens 的《Alternative DNS Servers》**（UIT Cambridge，2008/2009）。NLnet Labs 的历史页保存了一篇 2008 年 12 月的短文，记录收到作者赠书、并评价其中 Unbound 与 NSD 的章节；文中还引用了书里一组多产品性能对比数据，并说明该书评述的是 Unbound 1.0，而 1.1 已发布且加入了 DLV 支持与改进统计。

作者于 **2010 年**放出了该书的 DRM-free PDF。本书只把它当作**历史与横评的史料来源**使用：用于确认"Unbound 在 1.0 时代就已被纳入多实现横评""当时的性能对比是怎么做的"，**不节录、不翻译其正文，也不把书里的性能数字当作今天的结论**。二十年前用 queryperf 打出来的每秒查询数，与今天的硬件、加密传输、DNSSEC 验证开销不具可比性。

需要提醒的是史料的可核验性：官方手册的历史章节、发布说明、以及各版本 man page 是版本事实的第一来源；书籍与新闻稿适合用来还原"当时的人怎么想"，不适合用来确定某个参数从哪个版本开始生效。

## 从历史里带走的三条工程判断

历史本身不构成配置建议，但它解释了本书后面所有加固动作背后的默认立场：

1. **边界先定，再填功能。**"不做权威服务器、不要过多特性"写在最早的需求文档里。部署时把不同职责拆给不同实例（第二篇）之所以自然，是因为实现从一开始就按这个边界设计。
2. **默认安全要靠机制，不靠记得勾选项。**端口随机化、清理器、DNSSEC 默认验证、EDNS 1232 都是"实现默认如此"的结果。反过来，任何需要显式关闭才能变安全的开关（如信任锚相关的降级选项）都属于高危配置面。
3. **别把两类保护混为一谈。**DNSSEC 保证数据来源与完整性，DoT/DoH/DoQ 保证传输加密与隐私，查询名最小化减少元数据外泄，[RFC 8767] 保证可用性。它们各自补一块，互相不能替代；把其中任何一项当成"已经加密了所以数据可信"，会在排查时得出完全错误的结论。

## 本章要点

- Unbound 的核心动机是打破递归解析器的**单一化风险**：需求文档把"代码多样性""除配置外可替代 BIND""尽可能小的够用组件"列为目标，并把"不做权威服务器""不要过多特性"列为明确的非目标。
- 2004 年由 Jakob Schlyter（Kirei）与 Roy Arends（Nominet）提出架构、VeriSign 与 EP.NET 资助 Java 原型（David Blacka、Matt Larson 等）；约 2006 年 NLnet Labs 加入并承担 C 实现（借鉴 NSD 经验，Wouter Wijngaards 主开发）；2008-05-20 随 1.0 公开发布，BSD 许可。早期参与者与年份在不同史料中表述略有出入，以官方手册历史章节与 NLnet Labs 发布说明为准。
- 2008 年 Kaminsky 缓存投毒事件把"查询熵是安全边界"和"只有 DNSSEC 能彻底解决伪造"钉死；Unbound 1.0 因端口/查询 ID 随机化与清理器设计，无需为该漏洞紧急补打抗伪造补丁。
- 里程碑按问题归类：DLV（根未签名时的过渡锚）、DNSSEC 默认验证、libunbound/pythonmod（模块链可裁剪）、DoT/DoH/DoQ（传输加密）、RPZ（跨实现过滤策略）、serve-stale（[RFC 8767] 可用性）、QMIN（[RFC 7816] → [RFC 9156] 元数据）、EDNS 1232（MTU/分片）、cachedb/Redis 与 ECS（共享缓存与隐私取舍）。
- DNSSEC 是**数据完整性/来源认证**，DoT/DoH/DoQ 是**传输加密/隐私**，查询名最小化不是加密；三类机制互不替代，这是全书一致口径。
- Jan-Piet Mens《Alternative DNS Servers》（UIT Cambridge, 2008/2009；2010 年放出 DRM-free PDF）是第一本记录 Unbound 的书，仅作史料来源，不节录正文、不引用其性能数字作为今日结论。
