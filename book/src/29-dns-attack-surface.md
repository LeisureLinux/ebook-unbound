# DNS 作为攻击面：隧道、扫描与资产暴露

把 DNS 只当成「把名字换成地址」的服务，会漏掉它的另一面：它是几乎所有网络都默认放行的一条双向通道，也是一份公开可读、长期缓存、跨组织消费的资产清单。前者让 DNS 成为数据外泄与命令控制（command and control，C2）的载体，让递归解析器成为可被滥用的公共资源；后者让一条忘记删除的记录变成别人的入口。这两件事共用同一套观测手段，所以放在一章里讲。


## DNS 隧道：把数据编码进查询名

### 一次查询就是一封信

隧道的核心不是「偷偷发一个包」，而是把数据塞进本来就要发出去的查询名（QNAME）里。被控主机把待传数据切成块、做 base32/base64url 一类的编码，当作最左侧的子域标签拼上去：

```text
[被控主机 192.0.2.20]
   |  A?  <编码块>.exfil.example.net
   v
[内部递归解析器 gw-01] -- 出向 53 --> [互联网] --> [攻击者权威服务器 ns.exfil.example.net]
   ^                                                     |
   |  TXT / NULL / CNAME 应答 <----------------- 下行指令 --+
```

由于 `exfil.example.net` 的权威服务器由攻击者控制，每一个查询都会把最左标签写进他的权威日志里——**即使应答是 NXDOMAIN，上行也已完成**。下行则靠 TXT、NULL、CNAME 的 RDATA 携带确认、分片序号与指令，于是形成双向 C2。公开工具形态包括 iodine、dnscat2、dns2tcp 一类，区别主要在编码方式、承载 QTYPE 与会话管理，不在原理。

单标签上限 63 字节、完整 QNAME 约 253 字节，所以每次查询只能带走几十字节；但几 KB/s 到几十 KB/s 的低吞吐已经足够偷凭据、配置文件与少量数据库记录。低速恰恰是它的优势：不容易触发带宽告警，也不像大流量外传那样显眼。

### 为什么常规防线看不见

- **出站策略通常放行 UDP/53**。很多网络允许任意主机直连公网解析器，防火墙看不到「这是 DNS 还是隧道」。
- **DNS 日志常被忽略**。默认 `verbosity: 1` 且 `log-queries: no` 时（第 9 章基线），查询名根本不落盘；只留 SERVFAIL 日志等于只记失败、不记成功的外泄。
- **域名会轮换**。DGA（domain generation algorithm）或预置域池按时间/种子换域，让「封掉几个域名」在小时级就失效。
- **承载可以换**。明文 53 被收敛后，客户端仍可能改用加密传输端点绕过，所以出向策略要同时覆盖明文 53 与加密传输发现机制（第 12、13 章）。这里要守住全书的关键区分：DNSSEC 提供数据完整性与来源认证，DoT / DoH / DoQ 提供传输加密与隐私，二者互不替代。

### Payload 分析：看一条查询长什么样

Payload 分析针对**单条查询**的内容特征，对已知隧道工具最有效：

- 超长 QNAME（接近 253 字节上限）、单标签接近 63 字节；
- 高熵 / 随机字符串、异常字符分布（大小写混排的 base32、连续的十六进制串）；
- 罕见 QTYPE：TXT、NULL、CNAME 在普通客户端查询里占比很低；
- 编码模式正则，以及同一域下标签长度高度一致（分片定长的痕迹）。

局限也很明确：换一种编码或把块切短就绕过了；而且 ACME DNS-01 的长 token、CDN 健康检查、服务发现类长名字都会产生高熵长标签。第 31 章会讲告警误报治理与白名单，这里先记住**特征命中只触发人工复核，不自动阻断**。

### 流量分析：看一批查询呈什么形状

流量分析针对**一段时间内的聚合行为**，能覆盖未知隧道：

- **单域唯一 FQDN 数**：最通用的信号。隧道必须不断换名字来传新数据、并避开缓存命中，因此「同一个注册域下出现了大量互不重复的名字」几乎与编码方式、QTYPE、长度无关。
- qps 突增，尤其是单客户端对某个新域的持续查询；
- NXDOMAIN 比例升高（编造子域 / DGA 的副产物）；
- 低 TTL（便于复用名字、避免被长时间缓存）；
- 单源集中查询某新域、地理异常（客户端位置与该域权威侧历史分布不符，需要 IP 归属数据支撑）。

GIAC / SANS 一类资料把它归成 payload 分析与流量分析两类；两类检测要一起用：payload 分析给出「这条像不像隧道」的可解释证据，流量分析给出「这个域该不该进复核队列」的排序依据。公开学术工作（Ben-Gurion University 关于低吞吐 DNS 外泄检测）走的是更长的观察窗口 + 按域聚合特征 + Isolation Forest 一类异常检测；具体实现与数据集见论文原文，本书不据此宣称任何检测率。

### 可复制的 dnstap / jq 巡检骨架

dnstap 是自己的查询流副本，落的是二进制帧。下面的骨架假设 consumer 已把帧转成 JSON Lines，每行含 `ts` / `type` / `client_address` / `qname` / `qtype` / `rcode`；**字段名随 consumer 实现而变，先跑 `head -1 /var/log/dnstap/queries.jsonl | jq 'keys'` 对齐**。全量查询日志本身就是隐私数据，保留期与访问范围按第 7、31 章的边界执行，不要无条件推给第三方 SaaS。

```bash
#!/bin/sh
# dns-tunnel-triage.sh —— 教学用巡检骨架，不是即插即用的检测产品
LOG=${1:-/var/log/dnstap/queries.jsonl}
WINDOW=${2:-3600}                          # 观察窗口（秒）
SINCE=$(date -u -d "-${WINDOW} seconds" +%s)

# ① 按「客户端 + 注册域」聚合：唯一 FQDN 数 / qps / NXDOMAIN / 罕见 QTYPE / 长 QNAME
#   输出首列是纯数字的排序键，后面才是带标签的指标列
jq -r --argjson since "$SINCE" '
    select(.type == "CLIENT_QUERY" and (.ts >= $since))
    | [(.client_address // "unknown"),
       ((.qname // "") | ascii_downcase | sub("\\.$"; "")),
       (.qtype // ""), (.rcode // "")] | @tsv' "$LOG" \
| awk -F'\t' '
    function reg2(name,   n, a) {
      n = split(name, a, ".");
      return (n >= 2) ? a[n-1] "." a[n] : name;
    }
    {
      client = $1; fqdn = $2; qtype = $3; rcode = $4;
      key = client "\t" reg2(fqdn);
      uniq[key "\t" fqdn] = 1;             # 去重集合，不是查询计数
      q[key]++;
      if (rcode == "NXDOMAIN") nx[key]++;
      if (qtype == "TXT" || qtype == "NULL" || qtype == "CNAME") rare[key]++;
      if (length(fqdn) > 120) longq[key]++;
    }
    END {
      for (u in uniq) { split(u, b, "\t"); cnt[b[1] "\t" b[2]]++ }
      for (k in q)
        printf "%d\t%s\tqueries=%d\tnxdomain=%d\trare_qtype=%d\tlong_qname=%d\n", \
          cnt[k], k, q[k], nx[k], rare[k], longq[k];
    }' \
| sort -k1,1nr | head -30          # 不加 -t：$'\t' 是 bash 专有写法，#!/bin/sh 下会报错

# ② payload 钻取：把最长的 QNAME 打出来人工看编码形态
jq -r --argjson since "$SINCE" '
    select(.type == "CLIENT_QUERY" and (.ts >= $since))
    | select((.qname | length) > 120)
    | [.client_address, .qname, .qtype] | @tsv' "$LOG" \
| awk -F'\t' '{ n = split($2, a, "."); print length($2), n, $3, $1, $2 }' \
| sort -k1,1nr | head -20
```

**为什么这么设**：首列是纯数字的 `uniq_fqdn` 值，专门给 `sort -n` 用；把它写成 `uniq_fqdn=NNN` 这种带前后缀的字符串会让数值排序失效。`uniq` 用「客户端 + 注册域 + FQDN」做去重后再计数，正是流量分析里最抗规避的那一项；`q` 同时给出体量，避免把「一次性批量导入」误读成持续外泄。`rare` / `longq` 只是把 payload 信号并到同一行，方便一次排序决定先看谁。`reg2` 取最后两个标签只是教学近似，正式系统必须换成公共后缀表（Public Suffix List），否则 `co.uk` 一类后缀会把大量无关域并成一行。

**怎么验证**：`bash dns-tunnel-triage.sh /var/log/dnstap/queries.jsonl 3600 | head -5` 应能列出你网络里的正常域；再向自己的解析器发一批教学用高熵查询制造已知信号——把 `exfil.example.net` 换成你有授权的实验子域后执行 `for i in $(seq 1 50); do dig @192.0.2.1 "$(openssl rand -hex 24).exfil.example.net" A +short >/dev/null; done`，重跑脚本时该域的 `uniq_fqdn` 应上升约 50。骨架只读日志、不改配置，验证过程不会产生阻断动作。

**失败模式 / 回滚点**：字段不对齐会输出空表，先查 `jq 'keys'`；consumer 断流时表是陈旧的，别把「没告警」当「没外泄」，dnstap 断流本身要在第 31 章单独告警。最大误报源是证书续期与 CDN 健康探测，所以脚本只产出排序、不自动写 RPZ。骨架无状态，停跑即回滚；若后续人工加了 RPZ 条目，必须同时登记复核日期，否则过期 IOC 会长期误伤。

### 检测阈值表

所有数字都是**触发人工复核的起点值，不是阻断阈值**，且**需按你自己 7 天同时段基线调整**；不同网络的客户端数量、CDN 用量差异极大，照抄会淹没在误报里。

| 信号 | 计算口径 | 起始观察值（需按基线调整） | 常见误报源 |
|---|---|---|---|
| 单域唯一 FQDN 数 | 每客户端、每注册域、每小时去重后的 FQDN 数 | 大于 200 或超过基线 P99 | CDN 多级 CNAME 探测、大规模服务发现 |
| QNAME 长度 | 长度大于 120 字节的查询占比 | 大于 1% | ACME DNS-01 token、长 SRV / SVCB 名字 |
| 单标签长度 | 最左标签大于等于 50 字节（上限 63） | 出现即进复核队列 | 一次性验证值、遥测上报名字 |
| 罕见 QTYPE 占比 | TXT、NULL、CNAME 合计占该域查询比例 | 大于 5% | 邮件策略查询、SPF / DKIM 查询 |
| qps 倍率 | 相对 7 天同时段基线的倍数 | 大于 3 倍且持续 5 分钟 | 发布、批处理、缓存冷启动 |
| NXDOMAIN 比例 | 该域 NXDOMAIN 数 / 该域查询数 | 大于 30% | 拼写纠错、已下线业务、search 域追加 |
| 低 TTL | 应答 TTL 小于 60 秒的占比 | 明显偏离基线 | 灰度发布、故障切换期 |
| 地理异常 | 客户端归属与历史分布的偏离 | 出现新地区即复核 | 出差、VPN 出口变化 |

高熵与编码正则属于 payload 分析的第二层，骨架只给了长度与字符形态的近似；正式系统再补香农熵与编码正则，并把白名单放在**聚合之后**（第 31 章）。

### 缓解：收敛出向 53，而不是封几个域名

缓解的顺序是「先关掉通道，再看得见，最后处置已确认的 IOC」：

1. **客户端不能直连公网 53**，出向只允许内部解析器；内部解析器只向受控上游发查询（第 5 章单上游 + fail-closed，第 9 章已插入的出向收敛节）。本机解析器进程自己的出向 53 要按 uid 豁免，否则会被自己的劫持规则吃掉（第 14 章）。
2. **把加密传输端点纳入同一策略**：压制 DDR 自动发现、管住 DoH 端点，否则客户端换一条承载就绕过去了（第 11–13 章）。
3. **dnstap 全量日志 + 明确保留期**（第 7 章的 30 天），这是上面所有检测的来源；没有查询名，payload 与唯一 FQDN 都无从计算。
4. **RPZ 只用于阻断已确认的域**（官方 RPZ 用法见参考资料），配合 `ratelimit` 一类限速（第 9 章）。RPZ 是事后处置，不是控制措施。
5. **不要写「封几个域名」当结论**：DGA 会轮换，新域注册成本极低，黑名单永远慢一步。真正的控制面是「谁能向哪里发起 DNS 解析」；域名清单只是这条控制面上的临时补丁。

## 高速扫描与开放解析器：不提供可被滥用的能力

### Unbound 能不能当「污染源」或红队工具

先给结论：**Unbound 不是投毒工具，也不会替你把伪造应答注入别人的解析器**。它是递归验证器，设计前提恰恰是「只接受能按 DNSSEC 签名链、或按自身清理规则核验的数据」（第 1 章的 2008 年案例、第 10 章的三态验证）。把一台 Unbound 配成向第三方解析器**主动发送伪造应答**，既不属它的功能，也不是这里会写的做法——那需要自己构造 DNS 报文并按对端在途查询的 TXID/端口抢答，属于 [RFC 5452] 讨论的伪造应答范畴，与「配置一台解析器」是两回事。

但有三条**机理上的边界**值得防守方知道，它们决定了「自己手里的 Unbound 会被怎么用」：

| 能力 | Unbound 是否具备 | 防守含义 |
|---|---|---|
| 改写**自己**应答给客户端（`local-zone` / `local-data` / RPZ / `respip`） | 具备 | 这是正常的本地策略。一旦该实例被未授权的人控制、或错误地对全网开放递归，策略就能把**信任它的客户端**导向任意地址——所以第 9 章把 `access-control` 默认拒绝放在第一位。 |
| 作为**开放解析器**被第三方当反射器 / 扫描器 | 配错时具备 | 不是「投毒」，而是放大与免费算力滥用（见下节 [RFC 5358]）。 |
| 向**别人的**缓存注入伪造应答 | 不具备 | 缓存投毒依赖伪造源、抢在真应答前到达、猜中 TXID/端口；Unbound 没有这个功能面。防守侧靠源端口随机化、0x20、`harden-glue` 与 DNSSEC 验证（第 1、10 章）。 |

授权的红队测试里，Unbound 更常见的角色反而是**观测点**：用 dnstap 记录自己网络里的查询流、验证 DNS 隧道与随机子域信号是否可见（第 31、34 章），或在自建实验拓扑里做一台**受控的**权威/递归来验证防守规则是否生效。这些都不触碰第三方资产。本书不提供任何针对外部解析器的伪造、抢答或规避检测流程；涉及应答改写的章节（第 24 章过滤表、第 9 章 `respip`）一律限定在「自己持有、自己授权的解析器」上。

### 一套工具，两种用法

massdns、dnsx、subfinder 一类工具原本用于资产发现：拿一份字典高速枚举子域、批量查 ANY 或随机子域、从应答里挑出存活名字。同一套能力换一个发起者，就是对一个域的高速探测，或把一批解析器当成免费扫描器用。这里讨论防护时，重点不是识别工具指纹，而是**让本地服务不具备被滥用的能力**。

### [RFC 5358] 与开放反射器

开放递归解析器是放大攻击与扫描的公共资源。[RFC 5358] 明确反对开放反射器：UDP 源地址可伪造，几十字节的小查询能换回上千字节的大应答，攻击者把源伪造成受害者即可把流量打过去。第 9 章已算过放大倍数并给了 `access-control` / 报文尺寸 / 限速的完整基线，本章只补一层视角：开放解析器的问题不只是「自己被打」，更是「自己被打的同时成为打别人的枪」，因此它属于对外责任，不能只按本地可用性评估。

### 限速与退避

- `access-control` **默认拒绝**，无匹配即 `refuse`，只给已登记的客户端网段放行（第 9 章）；
- `ratelimit` / `ip-ratelimit` 官方标注为 **experimental**，手册说明前者按目标域回 SERVFAIL、后者按源静默丢弃；**按 `stats_noreset` 的基线调，不要把任何数字当通用结论**。这里不重复第 9 章的配置块。
- **权威侧 RRL**（response rate limiting）：权威服务器对同一查询/源组合的应答限速，压住反射放大与随机子域洪泛。
- **递归侧对失败应答限速与指数退避**：SERVFAIL / 超时引来的重试会自我放大，Verisign 的公开观测里出现过百倍量级的重试放大；负缓存（[RFC 2308]）既是抑制手段也是故障放大器（第 4、22 章）。工程上要让重复失败退避、聚合，而不是无限重试。
- **禁止 AXFR 给未授权源**：AXFR 走 TCP/53，一次就能拿走整区；只在已登记的从服务器之间允许，并单独验证 TCP 而不是只测 UDP。
- **日志里识别单源高速**：按「源地址 + 秒」聚合查询数，和上面的隧道骨架共用同一份 JSON Lines。

```bash
# 单源高速：按「源地址 + 秒」统计，找持续的高 qps 源
LOG=/var/log/dnstap/queries.jsonl
SINCE=$(date -u -d "-3600 seconds" +%s)
jq -r --argjson since "$SINCE" '
    select(.type == "CLIENT_QUERY" and (.ts >= $since))
    | [(.ts | tostring), (.client_address // "unknown")] | @tsv' "$LOG" \
| awk -F'\t' '{ c[$2 "\t" int($1)]++ }
    END { for (k in c) print k "\t" c[k] }' \
| sort -k3,3nr | head -20
```

**为什么这么设**：按秒分桶能区分「持续高速」与「一次性突发」，后者常见于发布或缓存冷启动；只按总量排序会把一次性大客户排到最前面，掩盖真正的扫描源。

**怎么验证**：`unbound-control stats_noreset | grep -iE 'queries|ratelimit|unwanted|discard'` 对照限速相关计数是否随压测上升（计数器名以官方手册为准，不要照抄本行的关键字当结论）；从自家授权网段用 `dig` 造一小批查询，确认脚本能看到该源且限速计数变化。

**失败模式 / 回滚点**：反射场景里看到的「源」可能是被伪造成的受害者，据此封禁等于帮攻击者完成二次伤害；分布式扫描又会摊薄单源计数，所以这一项只作为复核线索。脚本只读日志，停跑即回滚。

### 为什么不是「封 IP 就行」

源可以是分布式的（僵尸网络、多出口），UDP 源还可以伪造；封 IP 是 denylist，既不证明服务能力已收紧，也挡不住换一批源再来（第 13 章讨论加密解析器发现时给过同一条判据：封 IP 是 denylist，不是证明）。临时止血可以封，但整改要落在四件事上：**默认拒绝递归、限速与退避、压小应答、收敛出向路径**，让这台机器对未授权源「无服务可滥用」。长期告警交给第 31 章的观测栈，而不是靠人工维护一张 IP 表。

## 互联网暴露面排查：只查自己有授权的名字

### 数据来源

| 来源 | 能看到什么 | 局限 |
|---|---|---|
| Certificate Transparency 日志 | 新签发证书里的 SAN，含通配符名、早已下线的名字 | 只覆盖申请过证书的名字，不覆盖纯内部或未签发证书的子域 |
| 被动 DNS | 历史上被解析过的名字与 RDATA、首次/末次见到的时间 | 覆盖取决于采集点位置，看不到未被采集的查询 |
| 公开区数据、搜索引擎索引 | 区文件、页面与链接里出现的主机名 | 陈旧，且「搜不到」不等于「不存在」 |
| WHOIS / RDAP | 注册人、注册商、NS、域状态 | 描述注册关系，不描述当前解析结果 |
| 自己的权威区文件与变更单 | 设计上应该有哪些记录、谁建的 | 常与实际运行的 DNS 不一致 |

把这张表读成一句话：**以运行中的区为准**。CT 与被动 DNS 负责找出「你以为没有、其实有」的名字，权威区与变更单负责解释「它为什么在」。

### 自查清单

| 检查项 | 命令形态 | 期望结果 | 异常含义 |
|---|---|---|---|
| NS 委派一致性 | `dig +nssearch` | 父区委派与区自身 NS 一致 | 存在旧 NS、未清理的委派 |
| AXFR 是否误开 | `dig AXFR ... @<自己权威>` | 未授权源被拒绝 | 整区可被未授权源取走 |
| CNAME / NS / MX / TXT 目标 | `dig +short <name> <type>` | 目标仍在服务、仍属自己 | 指向已下线资源（下一节） |
| `_acme-challenge` 残留 | `dig +short _acme-challenge... TXT` | 无残留或仅当前续期中的值 | 验证记录与旧自动化凭据长期存在 |
| DS 是否匹配 | `dig +short <zone> DS @<父区权威>` | 与当前 KSK 对应 | 整个区被判 bogus（第 10 章） |

```bash
# 执行前把 ZONE / AUTH 换成你自己已授权的区与权威服务器
ZONE=example.org
AUTH=192.0.2.53    # [RFC 5737] 文档地址，勿直接用于生产

dig +short NS "$ZONE"
dig +nssearch "$ZONE"
dig +short "_acme-challenge.$ZONE" TXT
dig +short "svc.$ZONE" CNAME
dig +short "$ZONE" DS @"$AUTH"
dig AXFR "$ZONE" @"$AUTH" +time=2 +tries=1 | head -30    # 只对自己有授权的区域执行
```

最后一条的期望是**未授权源拿到拒绝**（transfer failed / REFUSED），只有已登记的从服务器才应看到区内容；把 UDP 与 TCP/53 都测一遍，很多「AXFR 已关」的结论只测了 UDP。DS 一项只做匹配核对，信任锚与验证状态见第 10 章。

**失败模式**：`dig +short` 输出为空有多种含义（记录不存在、名字不存在、应答被过滤），不能据此判定「资源已下线」；补一次不带 `+short` 的查询看 HEADER 的 rcode 与 AUTHORITY 段。排查结果要落成带日期、执行人的工单，`<TOKEN>` 一类凭据不写进去。

### 纪律：只枚举有授权的名字，不 claim

OWASP Web Security Testing Guide（WSTG）的子域接管测试项明确要求 **"Do not claim it"**（原文措辞见参考资料里的官方项目页）。这条纪律在本章有两个具体落点：

- **范围**：只读的 CT / 被动 DNS / WHOIS-RDAP 可以自由查；主动 `dig`、AXFR、`+nssearch` 只对自己有授权的名字与自己的权威服务器执行；不对第三方权威服务器做 AXFR 或高速枚举。
- **发现可接管资源时**：只确认指纹（错误页特征、CNAME 目标是否 NXDOMAIN），在自己的资产清单里登记，然后**删掉自己的悬空记录**。不要去服务商那里注册同名资源「验证一下」，不要往该名字写内容、发请求或申请证书——那已经越过授权边界，且可能破坏他人正在使用的服务。

## 悬空 CNAME 与子域接管

### 成因：DNS 记录是公开指针，不是所有权证明

CNAME 常指向第三方资源：对象存储桶、Pages 站点、SaaS 自定义域、CDN 自定义域。服务下线或资源被释放后，DNS 记录留在区里，就成了「悬空 CNAME」（dangling CNAME）。若服务商在新建同名资源时不校验域所有权，任何人注册该资源名，就能在这个子域上提供内容。

要点是**不是所有「查不到」的 CNAME 都可接管**：有的服务商会校验所有权，有的名字已被回收但保留错误页，有的只是暂时解析失败。区分「可接管」与「仅下线」，靠的是指纹而不是猜测。

### 影响分级

| 被接管的记录 | 接管后能做什么 | 相对危级 |
|---|---|---|
| NS | 控制整区：改任意记录、签证书、改 MX 收信 | 最高 |
| MX | 接收或观察该域邮件 | 高 |
| CNAME / A | 在该子域挂内容、钓鱼、读父域作用域的 cookie | 高 |
| TXT（SPF include、域验证） | 借用的发件授权、长期残留的验证记录 | 中 |

父域设了 `Domain=example.org` 的 cookie 会发给所有子域，所以一个被接管的子域能读到会话 cookie；钓鱼页面还额外获得「看起来是自家域名」的 URL 与合法证书。若父域 SPF `include:` 了被接管域，发件授权也会被借用——记录里放了什么、谁消费，第 30 章展开，本章只看「指针被别人拿走」这一层。NS 接管最高危，因为它把**整份资产清单**的控制权交出去，而不是只交出一个子域。

### 下线服务先删 DNS

顺序反过来就会留窗口：先释放第三方资源名、后删 DNS，中间那段时间记录指着一个人人可注册的名字。正确顺序是：

1. 删掉或改掉 DNS 记录（先处理 CNAME，再处理相关的 TXT / MX / NS）；
2. 等 TTL 与链路上各层缓存过期——负缓存也会缓存 NXDOMAIN，改完仍可能短时间查不到（第 4、22 章）；
3. 再释放第三方资源名、关停实例。

把「删 DNS 已完成」写成下线变更单里的**必选勾选项**，没有这一项不允许关单。靠人记是这类问题反复出现的主要原因：DNS 记录没有「服务已下线」的自动感知，它只会一直指下去。

### 指纹库、资产清单与记录生命周期

- **对照公开指纹库**：`can-i-take-over-xyz` 一类项目按服务商归集错误页文案、CNAME 目标形态与可接管判据。指纹会随服务商改版变化，要定期复核，不能一次扫描定终身；本章不复制任何指纹条目。
- **资产清单字段**：FQDN、记录类型、RDATA、第三方服务与资源 ID、负责人、创建日期、复核日期、关联变更单。少了「第三方资源 ID」，就无法判断一条 CNAME 是否还指向自己的资源。
- **生命周期绑定**：记录与资源的创建、变更、下线走同一张工单；CNAME 目标 `dig +short` 是否仍存在、目标是否已被释放，纳入定期扫描；告警落到第 31 章的栈里。
- **缩小耦合面**：内部服务尽量用 `home.arpa.` 一类内网域与内部记录，少把内部名字挂到外部第三方资源上。

### 与第 13、28 章的两个接口

第 13 章那个**违反 [RFC 8020] 的 CDN CNAME 区**案例，本章只取一层含义：CNAME 链可以很长，中间层父名返回 NXDOMAIN 而子名却存在，且链上多跳完全由第三方控制。QMIN strict 的参数、整站 CSS/JS 解析失败与逐层刷缓存的步骤都在第 13 章，这里不重述；本章要补的是——**链上每一跳都是需要盘点、需要监控的资产**，任何一跳被释放都可能造成悬空，链越长越容易漏掉中间那一跳。

第 28 章故障域隔离的结论在这里有了安全侧的对应：内部可用性不该绑到外部 CNAME 链。接管其实是同一枚硬币的反面——别人不仅能改你的内容，也能改你的可用性。把权威面、递归面、控制面切开之后，还要把「外部第三方资源」作为一类独立故障域纳入资产清单。完整的负缓存放大故障在第 22 章，本章只引用不展开。

## 历史漏洞与 Unbound 的加固模式

### 2008 Kaminsky 缓存投毒

2008 年的 Kaminsky 缓存投毒事件把两处熵不足叠到了一起：DNS 事务 ID 只有 16 位，源端口在很多实现里可预测。攻击者只要在真应答返回前猜中这对值并伪造一个带胶水记录的应答，就能把攻击者控制的权威 NS 写进递归解析器的缓存，此后该域的查询全部被引走。行业的加固方向是三条：随机化源端口（扩大可用熵）、0x20 大小写随机化（把查询名的大小写当额外校验位，回显不一致即丢弃）、以及加速 DNSSEC 部署。

[RFC 5452]（*Measures for Making DNS More Resilient against Forged Answers*）把这些伪造韧性建议系统化了；Unbound 从设计上就按这一族建议实现，而不是事后逐个打补丁。要守住两条边界：0x20 与随机源端口只是**提高伪造难度**，不是加密；DNSSEC 提供的是数据完整性与来源认证，DoT / DoH / DoQ 提供的是传输加密与隐私，三者不在同一层。域外夹带的胶水记录是经典投毒面，对应 `harden-glue` 一类默认加固（第 9 章），它与是否启用验证器无关。

### 四个公开名称：只说机理

下表的名称与机理都来自公开资料；**具体影响版本、公告编号与年份见官方资料**（NLnet Labs 安全公告与对应版本发布说明），本章不列 CVE 编号、年份与版本号，也不把任何版本写成「已修复」。升级判断以你所用发行版的安全公告为准。

| 名称 | 公开可核验机理 | 对应的加固方向 |
|---|---|---|
| NXNSAttack | 恶意委派应答里塞入大量 NS 名，诱使递归器把一次客户端请求放大成海量出向查询 | 对单个请求可产生的出向查询数设限 |
| DNSBomb | 把一批查询的超时/慢应答在时间上对齐，汇聚成脉冲式流量 | 限速、超时分散，避免一批超时同时到期 |
| NRDelegation | 恶意委派让解析器反复迭代、反复回到同一批名字，耗尽解析预算 | 迭代次数与 referral 限额 |
| ReTrap | NLnet Labs 安全公告里提到的后续研究，利用 DNSSEC 验证路径的算法复杂度形成 degradation of service | 限额 + 挂起让出 CPU，避免长计算占死线程 |

Debian 的 unbound changelog 里出现过 "The DNSBomb attack, via specially timed DNS queries" 这样的措辞，可作为名称可核验的一处线索；除此之外本章不对时间线做断言。

**KeyTrap** 与 NSEC3 那一组 DNSSEC 计算放大问题在第 10 章结合验证器配置讲，这里只作一句交叉引用：它同样属于「用有限的计算预算对抗无限的输入组合」这一族问题。

### Unbound 的加固模式

下面六条是**本书对公开设计说明与版本公告的归纳**，不是官方原话，也不是「Unbound 免疫这些攻击」的承诺：

1. **限额**：把「一次解析能消耗多少」变成有界量——出向查询数、迭代次数、referral 数、挂起请求数、`ratelimit`。NXNSAttack、NRDelegation 之所以能被压住，靠的就是这类上界。
2. **挂起让出 CPU**：解析状态被挂起等待应答，而不是占着线程阻塞；单个慢查询不拖死整个实例，也给超时分散留了余地。
3. **分离线程**：按角色/模块拆开，验证、递归、控制面的资源与故障不互相拖累（呼应第 7 章多实例、第 28 章故障域隔离）。
4. **fail-closed**：上游或加密通道失败时明确 SERVFAIL，不静默回退明文（第 5、14 章）。
5. **默认安全**：不对公网开放递归、DNSSEC 可验、`harden-*` 一族默认打开；运营者要显式做错才会变弱。
6. **小代码面便于审计**：功能集中在递归与验证，不把权威服务、过滤表、HTTP 栈都塞进同一进程；新的攻击族出现时，改动面与复查面都小。

把这六条合起来看，结论不是「逐个给攻击起名字、逐个加黑名单」，而是：上面所有攻击争抢的都是同一份有限资源——CPU 时间、出向查询额度、缓存与线程。**加固的方向是给这份资源设上界、并让超限与失败可观测**；检测与告警的长期工程在第 31 章。

| 攻击 / 风险 | 观测信号 | 加固动作 | 本书章节 |
|---|---|---|---|
| DNS 隧道数据外泄 | 单域唯一 FQDN 数突增、长 QNAME、罕见 QTYPE | 出向 53 只准内部解析器、dnstap 全量日志、限速 | 第 7、9、14、29 章 |

## 与后续章节的分工

本章站在**防守侧**：我的暴露面怎么自查、怎么加固。同样的工具与信号换一个视角看，就是第 34 章的「对手按什么顺序找你、每一步留下什么痕迹」，以及第 35 章的「怎么用蜜罐把这些痕迹变成高质量观测数据」。三章共享同一套事实，但落点分别是**加固 / 侦察链 / 反向观测**，不重复阈值表与脚本。

## 本章要点

- DNS 隧道把数据编码进子域标签，靠攻击者控制的权威服务器收上行、靠 TXT / NULL / CNAME 回下行；payload 分析看单条查询（长 QNAME、高熵、罕见 QTYPE），流量分析看聚合行为，其中**单域唯一 FQDN 数**最通用、最抗规避。所有阈值都是需按 7 天基线调整的复核起点，不是阻断线。
- 缓解的顺序是「出向 53 只准内部解析器 → dnstap 全量查询日志（含保留期）→ 限速 → RPZ 处置已确认域」，**不是封几个域名**：DGA 会轮换，域名黑名单只是事后 IOC。出向收敛配置见第 9、14 章。
- 开放解析器与高速扫描的整改目标是**不提供可被滥用的服务能力**：默认拒绝递归、experimental 的 `ratelimit` / `ip-ratelimit` 按 `stats_noreset` 基线调、权威侧 RRL、失败应答退避、禁 AXFR 给未授权源。源可分布式、可伪造，所以「封 IP 就行」是 denylist 式的止血而非证明。
- 暴露面排查以运行中的权威区为准，CT / 被动 DNS / WHOIS-RDAP 只负责找出「以为没有、其实有」的名字；纪律是**只枚举有授权的名字、发现可接管资源不要 claim**（OWASP WSTG 明确要求），只确认指纹并删除自己的悬空记录。
- 悬空 CNAME 的成因是「DNS 记录是公开指针，不是所有权证明」；NS 接管最高危，cookie 作用域、钓鱼与邮件次之。下线服务要先删 DNS 并等缓存过期，再释放第三方资源；第 13 章的长 CNAME 链案例与第 28 章的故障域隔离说明了链上每一跳都要盘点。
- 从 2008 Kaminsky 缓存投毒到 [RFC 5452] 伪造韧性，再到 NXNSAttack / DNSBomb / NRDelegation / ReTrap，攻击争抢的都是有限的计算与出向预算；Unbound 的加固模式是限额、挂起让出 CPU、分离线程、fail-closed、默认安全、小代码面便于审计，而不是堆功能或堆黑名单。
