# 代理与过渡场景里的 DNS

本书讨论的是 DNS 协议机制与失效边界，不构成绕过网络管理的操作指南。

本章涉及的代理、TUN、DNS64/NAT64、464XLAT 等场景，只作为「DNS 应答形态发生变化」的研究对象出现：看一个名字在哪一步被换成地址、被谁换、换出来的地址能不能真的被网络转发。文中不提供任何出口配置、订阅、账号或连通性规避步骤，也不列可用的公共服务清单；所有地址与域名都是教学用文档值——IPv4 用 [RFC 5737] 的 `192.0.2.0/24`、`198.51.100.0/24`、`203.0.113.0/24`，IPv6 用 `2001:db8::/32` 与 NAT64 知名前缀 `64:ff9b::/96`，域名用 `example.net` / `example.org` / `home.arpa.`，主机名一律不指向真实环境。

在这些场景里，DNS 应答不再是「目标的真实地址」。有时它是本地的占位票据，有时它是网关合成出来的可路由地址，有时它干脆被跳过——应用拿着一个 IPv4 字面量直接发包。判断一套方案能不能工作，只需看三件事：应答在哪一层被改写、改写者是否还掌握原始域名、改写后的地址是否真的能被转发。第 3 章的四种角色（存根解析器 stub resolver、缓存解析器、转发器、递归解析器）在这里仍是分析骨架，只是每多一层中间设备，就多一个可以改写应答的位置。

## DoH 与 HTTPDNS 不是一回事

这两个名字里都有 HTTP，也都能在 443 端口上把解析请求送出去，所以常被当成同一种东西。实际上一个是 IETF 标准协议，一个是厂商私有接口；差别不在传输，而在「载荷是什么」和「谁有权决定用哪个解析器」。

### 一张对照表

| 维度 | DoH [RFC 8484] | HTTPDNS（厂商私有 API） |
|---|---|---|
| 性质 | IETF 标准（Proposed Standard） | 无 RFC，厂商自定义 |
| 载荷 | DNS wire format 二进制，`Content-Type: application/dns-message`；GET 用 base64url 的 `dns` 变量，POST 放 body | 通常 JSON（`?name=…&type=A` → `{"Answer":[…]}`）或私有文本 |
| 客户端 | 系统存根 / 浏览器 / 支持 DoH 的解析器 | **App 内嵌 SDK**，绕过系统解析器 |
| 服务端 | DoH 服务器（本书第 12 章 dnsdist + nginx 链路） | 厂商自有 HTTP 端点，后端仍是递归解析器 |
| 配置 | **URI Template**（[RFC 6570]）；RFC 8484 明确 DoH client **MUST NOT** 因「发现」就换 URI | 硬编码在 SDK 里 |
| 缓存 | HTTP 缓存语义；建议 DNS ID = 0 | 客户端 SDK 自己做 |
| 目的 | 链路隐私、防 on-path 干扰 | 绕过运营商 LocalDNS 劫持/污染、精确调度 |
| 代价 | 端点运营者看到全部查询 | **绕过本机/内网 DNS 策略**（正是第 13 章的「客户端绕过」） |

第 12 章已经放过这张对照表。本章往下展开的是它背后的原理与信任模型，不重复 DoH 服务端的配置。

### 载荷与端点：wire format 和 URI Template

DoH 不改变 DNS 报文本身。同一个 `api.example.net A` 查询，在 UDP/53、TCP/53、DoT 和 DoH 里是同一段二进制，只是外面套的传输不同。[RFC 8484] 规定了 `application/dns-message`：GET 把二进制 DNS 报文做 base64url 无填充编码后放进 `dns` 查询变量，POST 直接把二进制放进 body；服务器 GET 与 POST 都 MUST 支持；HTTP/2 是最低 RECOMMENDED 的 HTTP 版本（其余版本要求见官方资料）。每一对 DNS 问答映射到一个 HTTP exchange，于是 HTTP 层的缓存键、`Cache-Control`、内容协商全都进入了解析链路；RFC 建议把 DNS ID 置 0，避免它和 HTTP 缓存键互相干扰。

URI Template 决定端点路径。[RFC 8484] 明确要求 DoH 客户端 MUST NOT 因为某种「发现」结果就改用未配置的 URI，服务器也不得被动接受未配置 URI 上的应答。这一条容易被当成实现细节，其实是整章最关键的信任约定：它把「谁有权决定解析器」固定在本地配置里，而不是交给链路上的发现机制。第 13 章讲的 DDR 压制、浏览器 canary 域，本质上都是在守这条边界。

```text
[DoH：二进制 DNS 报文套在 HTTP 里，端点与域名均为文档值]
GET /dns-query?dns=<base64url(DNS wire format; qname=api.example.net; qtype=A)> HTTP/2
Host: resolver.example.org
Accept: application/dns-message

[HTTPDNS：查询参数 + JSON，DNS 报文根本不存在]
GET /resolve?name=api.example.net&type=A HTTP/2
Host: resolver.example.org
Accept: application/json
```

```json
{
  "Status": 0,
  "Question": [{ "name": "api.example.net", "type": 1 }],
  "Answer": [
    { "name": "api.example.net", "type": 1, "TTL": 300, "data": "192.0.2.10" }
  ]
}
```

上面这块 JSON 只是示意形状，字段名与状态码以厂商文档为准（见官方资料）。重要的是：它不再是 DNS 报文，没有 QR/OPCODE/RCODE 标志位，没有 EDNS0 选项，也没有可以挂 RRSIG 的位置。

### 信任模型的差异

DoH 是「同一份 DNS 数据 + 换一条加密传输」。信任从链路转移到了端点运营者：链路上的人看不到也改不了查询，但端点运营者看到全部查询。只要 DoH 端点就是自己的解析器，本机/内网的策略依然完整——过滤表、`local-zone`、查询名最小化、DNSSEC 验证、dnstap 观测都还在，因为对解析器而言这仍然是一次规规矩矩的 DNS 查询。DoH 没有改变「谁解析」，只改变了「怎么送」。这也是第 12 章坚持把 DoH 端点放在自己的解析器后面的原因：端点在自己手里，策略才还在自己手里。

HTTPDNS 把解析动作从系统存根整体搬进 App 的 SDK。对系统解析器来说，一次 DNS 查询都没发生过，只发生了一次 HTTPS 请求。于是 DNSSEC 验证、缓存与负缓存、过滤表、日志观测全部被跳过；解析器地址由 SDK 硬编码，管理员在网关上改 DHCP option、改 RDNSS、压 DDR 都影响不到它。这是第 13 章「客户端绕过」最彻底的一种形态：不是绕过了某条规则，而是绕过了整套 DNS 子系统。

这里必须重申全书一致的区分：**DNSSEC 是数据完整性与来源认证，DoT/DoH/DoQ 是传输加密与隐私，二者不互相替代**。DoH 保证「这段报文在链路上没被看到、没被改动」，不保证「数据的来源经过签名认证」；HTTPDNS 则连 DNSSEC 能挂靠的报文结构都不存在了。

### 同一 resolver 的两种外观

一个有公开文档的 DNS64 服务同时给出两种接口：DoH 形态的 `https://resolver.example.org/dns-query{?dns}`，以及 JSON 形态的 `https://resolver.example.org/resolve?name=ipv4only.arpa&type=AAAA`。后者属于 HTTPDNS 形态，但两者背后是同一个递归解析器、同一套缓存、同一套 AAAA 合成逻辑。它们是**同一 resolver 的两种外观**（接口编码方式不同），不是两种协议，更不是两个信任域。`ipv4only.arpa` 是用于前缀发现的特殊用途查询名，其定义见官方资料；本节所有 URI 中的域名都是教学用文档域名，不指向任何真实服务。

判断时别被路径里的 `dns-query` 和 `resolve` 迷惑，只看载荷：是不是 `application/dns-message` 的二进制 DNS 报文。是，就是 DoH；不是，就是私有 API。一个公开 DNS64 服务（Google DNS64）常被拿来举例，原因正是它把这两种外观并排放在同一个域名下——但这只能说明接口可以复用，不能说明协议相同，更不构成任何服务推荐。

### 判据：看载荷，不看路径

现场辨认只需要一步：抓一次请求，看 `Content-Type` 和 body 是不是 DNS wire format。是 `application/dns-message` 就是 DoH，无论路径写成 `/dns-query`、`/resolve` 还是别的什么；是 `application/json` 且字段里直接铺着 `Answer` 数组，就是私有 API，无论它自称「加密 DNS」还是「安全解析」。URL 里的 `dns` 字样不提供任何信息，厂商完全可以把 JSON 端点也命名成 `/dns-query`。

这个判据直接影响运维动作。若是 DoH，可以把它接到自己的解析器后面，让过滤表、DNSSEC 验证、dnstap 继续生效（第 12 章）；若是私有 API，这些手段一个都用不上，只能在应用层或网络层另想办法——而按本章开头的声明，本书不展开任何针对应用层的规避或拦截操作，只指出策略边界在哪里。

还有一层容易忽略：DoH 的「每对 DNS 问答映射一个 HTTP exchange」让 HTTP 缓存进入了解析链路，`Cache-Control`、HTTP 层过期时间与 DNS TTL 可能出现两套不一致的时钟。这不是协议缺陷，但它意味着排查「应答为什么没刷新」时要同时看 HTTP 头与 DNS 头，不能只查解析器缓存（第 7 章）。

## Fake-IP：把域名解析推迟到连接建立时

Fake-IP 不是标准，没有 RFC，是代理客户端在工程上发明的技巧。它改动的是 DNS 应答的内容：本该返回真实 A 记录，却返回一个本地保留段里的假地址。

### 完整数据流

```text
1. 应用向本地 DNS 模块查询 api.example.net 的 A 记录
   → 立刻回一个 198.18.0.0/15 里的假地址，例如 198.18.0.10
   → 同时在内存里记下映射：198.18.0.10 ↔ api.example.net
2. 应用对 198.18.0.10:443 发起 connect
   → TUN / 透明代理按目的地址截获这个包，反查映射表得到 api.example.net
3. 代理拿域名（不是那个假地址）去匹配域名规则集
   → 命中后由出口按规则发起真实连接，真实 DNS 解析在出口侧才发生
4. 应答沿原路回到应用；应用自始至终只见过 198.18.0.10
```

`198.18.0.0/15` 是 [RFC 2544] 的基准测试保留段，这里只作协议示例，不指向任何具体产品配置；IPv6 侧的对应物可以用 `2001:db8:1::/48` 一类文档前缀示意。选保留段的原因很实际：它不会与任何真实可达的公网地址冲突，落到路由表里也不会被误送到别的主机。

### 为什么存在

透明代理和 TUN 只能看到 IP 包。如果客户端先做真实解析再发包，代理拿到的是目标 IP，原始域名已经丢了；可分流规则偏偏是按域名写的（第 14 章的 `route.rules`）。要么让应用把域名显式交给代理——HTTP 绝对 URI、 socks 一类带名字的握手——要么就干脆别在客户端解析。Fake-IP 选了后者：用一个保留段地址当占位符，把「域名 → IP」这一步推迟到连接建立的那一刻，由同时持有映射表的代理来还原。

于是 DNS 应答在这里不是「目标地址」，而是「一张票据」。这也决定了它的信任模型：映射表和规则匹配必须在同一个进程或同一台设备上，否则反查不到域名，占位地址立刻变成黑洞。Fake-IP 因此天然和 TUN 绑定，它不是「递归解析器上可以打开的某个开关」——第 3 章的四种角色里，这里的本地 DNS 模块扮演的是存根加缓存的混合体，而真实递归发生在出口侧。

### 映射表的生命周期

占位地址只在映射表存在时才有意义，因此这张表的寿命直接决定整套机制的可靠性。它至少要覆盖三段：DNS 应答发出、应用发起 connect、代理完成规则匹配并接管连接。任何一段提前过期，反查就会失败。

几个和 DNS 缓存不同的性质值得单独记：

- **不按 TTL 淘汰。** DNS TTL 描述记录可以缓存多久，映射表描述的是「哪个名字对应这次连接」，两者没有换算关系。把 DNS TTL 直接当映射寿命，短 TTL 域名会立刻黑洞。
- **重启即丢。** 映射表通常在内存里，代理进程重启后旧的占位地址全部失去含义；客户端若还握着连接池里的旧地址，会持续失败到连接重建。
- **一对多与多对一都麻烦。** 同一域名多次查询可能分到不同占位地址，同一占位地址也可能在回收后被另一个名字复用；后者更危险，反查出的域名是错的，规则匹配会走到完全不该走的出口。
- **IPv6 侧同理。** 用 `2001:db8:1::/48` 一类文档前缀做 IPv6 占位时，映射表要同时维护 A 与 AAAA 两套占位；并行连接一类的地址选择机制会让两条路径几乎同时到达代理（具体行为见官方资料）。

### 失效边界

凡是依赖「拿到的是真实 IP」的行为都会坏。逐条看：

**连通性探测。** 操作系统和浏览器为判断「有没有网」，会向固定名字发查询并期待一个可预期、可达的应答，有的还会检查返回内容。Fake-IP 给的是占位地址，探测方拿它去连 80/443，得到的响应与预期不符，于是误判为断网，甚至触发 captive portal 弹窗。这类名字必须排除。

**服务发现。** mDNS/DNS-SD（第 27 章）、SRV 与 SVCB 记录里的目标名、以及「先解析、再对结果做二次查询」的逻辑，都假定 A/AAAA 里是真实地址。占位地址会让后续步骤连到不存在的主机，或让发现结果在局域网里根本传不出去。

**内网域。** `home.arpa.`、`.local`、内网单标签名本该由本地解析器直接给出 RFC 1918 地址。给了 `198.18.0.10` 之后，打印机、NAS、网关管理页全部连不上——那个地址不属于内网，也不是任何一台内网主机。

**literal IPv4。** URL 里直接写 `192.0.2.10` 时根本没有 DNS 查询，映射表无从建立，Fake-IP 完全不参与。这条流量要么按 IP 规则走，要么直连，域名规则集对它无效。

**UDP 与 QUIC。** 无连接的 UDP 包没有「建连」这个反查锚点；短生命周期会话、QUIC 把连接迁移到新地址的路径，都容易让映射在需要时已经过期或不匹配。连接跟踪超时一过，反查就失败，而且失败表现为静默丢包，很难从应用侧看出来。

**PTR 反查。** 需要反向解析的协议拿 `198.18.0.10` 去查对应的 `in-addr.arpa` 反向域，本地解析器没有权威数据，返回 NXDOMAIN 或被上游拒绝；依赖 PTR 结果做校验的服务直接失败。

还有两类较隐蔽的：应用自己的地址缓存与 HTTP 连接池会把占位地址复用很久，映射表过期后仍被使用；证书校验要求 SNI 与证书名一致，而占位地址本身不携带名字，一旦代理在还原域名前就完成握手，TLS 会失败。

### 失效边界速查表

| 失效场景 | 为什么坏 | 可观测症状 | 处理方式 |
|---|---|---|---|
| 连通性探测 / captive portal | 期待可预期应答与可达地址，得到占位地址 | 误报「无网络」、反复弹门户页 | 加入 `fake-ip-filter` |
| 服务发现（mDNS/DNS-SD、SRV、SVCB） | 假定 A/AAAA 是真实可达地址 | 发现结果为空或指向不存在主机 | 排除内网后缀，走正常解析 |
| 内网域与单标签名 | `198.18.0.10` 不属于内网任何主机 | 打印机、NAS、网关管理页连不上 | 排除 `home.arpa.` / `.local` / `*.lan` |
| literal IPv4 | 没有 DNS 查询，映射表无从建立 | 域名规则完全不生效 | 按 IP 规则处理，或补域名还原 |
| UDP / QUIC / 连接迁移 | 无建连锚点，跟踪超时后映射失效 | 静默丢包，应用侧难以定位 | 保证映射寿命长于连接寿命并补兜底 |
| PTR 反查 | 反向域无权威数据 | NXDOMAIN，依赖 PTR 校验的服务失败 | 允许真实解析或配置本地反向区 |
| 地址缓存 / 连接池复用 | 占位地址被长期复用，映射已过期 | 间歇性连接失败，重启应用后恢复 | 让映射寿命与连接跟踪状态同步 |

表里最后一行说明一个常被低估的约束：Fake-IP 的映射表不是 DNS 缓存，它不能靠 TTL 自然淘汰，必须和连接跟踪状态同步。映射比连接先消失，就会出现「明明解析过、却连不上」的假故障——这类假故障最容易被误判成出口不通。

### fake-ip-filter 与本书内的交叉引用

因此实现都会带一个排除清单，常写作 `fake-ip-filter`：把连通性检查域、`*.lan`、`.local`、`home.arpa.`、内网后缀，以及明确要按真实地址访问的名字排除，让它们走正常解析。要理解它的定位——这是「缩小占位范围」，不是「修好占位地址」。排除项之外的名字依然享受 Fake-IP 带来的域名保留，也依然承担上面全部失效边界。

本书已有对应物在此只作交叉引用，不展开任何配置：`dns-fake6` 入站、`fakeip` server（`198.18.0.0/15` 加 `2001:db8:1::/48` 一类文档段）、第 3 章的四种角色、第 14 章的域名规则与 `route.rules`。第 12 章的 DoH 端点与本节无关：Fake-IP 处理的是「应答内容被替换」，不是「应答怎么送」，两者处在不同层，可以同时存在也可以完全不相干。

## DNS64 / NAT64 / 464XLAT：纯 IPv6 网络访问 IPv4 目标

这一族标准解决的是另一个问题：接入网只有 IPv6，目标却只有 IPv4。它同样改写 DNS 应答，但改写出来的地址是**真的能路由**的。

### 标准族与各自职责

| 组件 | 标准 | 做什么 |
|---|---|---|
| DNS64 | [RFC 6147] | 客户端问 AAAA、权威侧只有 A 时，把 A 里的 IPv4 地址嵌入一个 IPv6 前缀，**合成** AAAA 返回 |
| NAT64 | [RFC 6146] | 网关收到发往合成地址的包，抽出内嵌的 v4 地址，做**状态式** v6→v4 报文头转换与地址/端口映射 |
| SIIT | [RFC 2765] 一类 | 无状态报文头翻译基础，为前两者提供翻译规则 |
| 464XLAT / CLAT | [RFC 8683] | 给只认 IPv4 字面量、或只调用 v4 socket API 的应用，在客户端侧再补一层本地翻译 |
| DNS proxy | [RFC 5625] | 规定 CPE / CLAT 上的 DNS 代理行为，包括哪些查询该转给谁 |

```text
查询：  api.example.net  AAAA
权威：  只有 A = 192.0.2.10，没有 AAAA
DNS64： 用 NAT64 知名前缀 64:ff9b::/96 与 192.0.2.10 合成
       → AAAA = 64:ff9b::c000:20a（等价嵌入写法 64:ff9b::192.0.2.10）
客户端：向 64:ff9b::c000:20a 发 IPv6 包
NAT64： 抽出 192.0.2.10，建立状态映射，转成 v4 包继续转发
```

`64:ff9b::/96` 是 NAT64 知名前缀；网络也可以使用自己分配的前缀，此时客户端需要前缀发现机制。前缀定义、可用范围与发现方式见官方资料，本书不展开。注意合成是有条件的：只有「查了 AAAA、且权威侧确实没有 AAAA」时才发生，名字本身有原生 AAAA 就不合成。

### 合成成立的三个前提

把上面的数据流拆开，DNS64 要真正生效，必须同时满足三件事，缺一件就退化成「纯 v6 网络访问不了 v4-only 目标」：

1. **客户端问的是 AAAA。** 只问 A、或应用直接用 IPv4 字面量，合成不会发生。
2. **权威侧确实只有 A。** 名字本身有原生 AAAA 时，DNS64 应原样返回，不能覆盖；否则会破坏已有的 IPv6 路径。
3. **查询确实经过那台做合成的解析器。** 解析器被绕过，或下发的解析器自己不合成，前两条再成立也没用。

三条分别对应后面六个坑里的第 2、4、6 条。把它们列在前面，是为了让排查顺序固定下来：先看查询有没有到、再看名字有没有要求 AAAA、最后才怀疑合成与翻译本身。多数现场故障其实停在第一条，却被当成 NAT64 网关的配置问题查了很久。

### DNSSEC 与合成应答的冲突

这是 [RFC 8683] 明列的第一个坑。DNSSEC 的 RRSIG 覆盖的是原始应答数据；DNS64 在网络侧把「无 AAAA」改成了「有这样一个合成 AAAA」，签名却还是原来那一份。安全感知的验证器自己验签，会把合成应答判为 bogus，进而 SERVFAIL 或直接丢弃。第 10 章的三种验证状态在这里有了新含义：验证器越严格，合成应答越活不下来；而关掉验证换来的「能通」，代价是把第 16 章讲的那套来源认证整个让出去。

[RFC 6147] §5.5 一类条文给出的正解是：**安全感知主机应在本地做 DNS64**——先完成 DNSSEC 验证、拿到可信的 A 记录，再由本机合成 AAAA。这样验证器验的是原始签名数据，合成发生在验证之后，两者不再作用于同一段字节。呼应全书那条区分：DNSSEC 管数据完整性与来源认证，DNS64 管可达性；它们作用在不同层，不能互相替代，也不能叠加在同一段被改写的应答上。客户端看到 AD 位并不代表安全，如果网络侧有人改写了应答，AD 位本身也失去意义。

### 加密 DNS 让网络侧 DNS64 失效

客户端用 DoT 或 DoH 直连外部解析器时，查询根本不经过网络里那台做合成的 DNS64 设备，于是拿不到合成 AAAA。客户端按普通 IPv6 语义理解为「这个目标没有 IPv6 地址」，在纯 v6 接入网里直接失败——NAT64 一次都没被调用。[RFC 8683] 明确把 DoT/DoH 场景列为 out of scope，不是遗漏，是承认这两类设计目标相撞：加密传输保护链路隐私，同时也把「网络侧基于 DNS 的策略」一起绕过了。

这和本章第 1 节的 HTTPDNS 是同一个信任模型问题，可以并起来记：**谁离查询最近，谁才有机会改写应答**。客户端把查询送到外部加密端点，网络侧的 DNS64、过滤表、本地策略就同时出局。第 12、13 章讨论的「加密 DNS 与本地策略冲突」，在纯 v6 网络里不是策略失效那么温和，而是直接表现为连通性归零。

### 知名前缀与地址混配

有公开文档的 DNS64 服务使用 `64:ff9b::/96`，并要求客户端只配置它自己的那两个 IPv6 解析器地址；把 IPv4 解析器地址混进去，客户端会时而在支持合成的路径上解析、时而在不支持合成的路径上解析，合成 AAAA 时有时无，症状是「同一个名字一会儿能通、一会儿超时」，极像链路抖动，实际是解析结果不一致。这里只作协议示例，不写成任何服务清单：要点是「一台客户端的所有解析器必须落在同一套合成策略里」，以及「合成前缀必须与 NAT64 网关的前缀一致」——前缀不一致时，包会被路由到别处，NAT64 收不到。

### IPv4 字面量不走 DNS

DNS64 只对「走了 DNS 的名字」有效。应用里写死 `192.0.2.10`、用 IP 字面量构造的 URL、或只调用 v4 socket API 的程序，没有 AAAA 查询，也就没有合成机会；在纯 v6 接入网里这些包无处可去。这正是 CLAT 存在的理由：它在客户端本地把 v4 报文头翻译成 v6，让应用以为自己仍在一个有 IPv4 的网络里。464XLAT 因此是两段的组合——客户端侧 CLAT 做无状态翻译，网络侧 NAT64 做状态式翻译，[RFC 8683] 描述这一架构，[RFC 2765] 一类 SIIT 提供报文头翻译基础。注意这恰好是 Fake-IP 那一节「literal IPv4」边界的镜像：两者都因为「没有 DNS 查询」而失去改写机会，只是一个补翻译、一个补规则。

### CLAT 的查询翻倍

CLAT 不该把每个查询原样转发两遍。按 [RFC 5625] 的 DNS proxy 指引，它应只把 IPv6 原生查询与 AAAA 查询交给网络的 DNS64 解析器；如果 A 查询也照发、或为同一个名字额外向上游发起 A 与 AAAA 两次查询，查询量直接翻倍。后果不只是带宽：缓存命中率下降，上游超时时的负缓存放大（第 7 章）也跟着翻倍，故障恢复后客户端仍会拿到过期的空应答。判断一个 CLAT 实现是否合格，只看它在「名字只有 A」和「名字有原生 AAAA」两种情况下各向上游发了几个查询就够了。

### RDNSS 下发的解析器自己不做 DNS64

第 19 章主张用 RA/RDNSS 给纯 v6 客户端下发自己的 ULA 解析器地址，并压掉上级广告的 DNS。可达性做对了，功能却可能没做对：如果这个解析器只是普通递归解析器、自身不做 DNS64，客户端问 v4-only 名字的 AAAA 只会拿到空应答，合成不发生，NAT64 依然空转。也就是说「客户端用哪个解析器」和「那个解析器会不会合成」是两件必须同时成立的事。第 19 章解决前者，本节提醒后者；RA/RDNSS 的条文原理在第 18 章，本章不重复。把这一条和「DoT/DoH 绕过」并排看会更有意思：一个是解析器选对了但没能力，一个是解析器有能力但被绕过，症状都是「纯 v6 网络访问不了 v4-only 目标」。

### 六个坑速查表

| # | 坑 | 机理 | 症状 | 结构性对策 |
|---|---|---|---|---|
| 1 | DNSSEC 冲突 | 网络侧改写应答，RRSIG 覆盖的是原始数据 | 验证器判 bogus → SERVFAIL | 安全感知主机本地做 DNS64（[RFC 6147] §5.5 一类） |
| 2 | DoT / DoH 绕过 | 查询不经过网络侧 DNS64 设备 | 拿不到合成 AAAA，NAT64 空转 | 统一解析器来源；[RFC 8683] 明列 out of scope |
| 3 | 前缀与地址混配 | 部分解析走合成、部分走普通路径 | 同一名字时通时断，像链路抖动 | 客户端只配同一套合成策略里的解析器；前缀与网关一致 |
| 4 | IPv4 字面量 | 没有 DNS 查询就没有合成机会 | v4-only 应用在纯 v6 网里直接失败 | CLAT 在客户端侧做本地翻译 |
| 5 | CLAT 查询翻倍 | A 与 AAAA 一并转发、重复向上游查询 | 缓存命中率下降、负缓存放大翻倍 | 按 [RFC 5625] 只送 v6 原生查询与 AAAA 给 DNS64 |
| 6 | RDNSS 解析器不合成 | 可达性对了，功能没对 | 客户端拿到空 AAAA 应答 | 下发的解析器自身需具备 DNS64 能力（第 19 章） |

第 1 条和第 2 条方向相反，值得并排记：一个因为「验证太严」而失败，一个因为「离查询太远」而失败。两者都说明同一件事——**合成必须发生在验证之后、且必须发生在查询真正经过的那台解析器上**。这也回到本章反复出现的那条主线：谁离查询最近，谁才有机会改写应答。

## 域名还原：当 DNS 已经不给出名字时

Fake-IP 覆盖不到的路径——literal IPv4、UDP/QUIC、连接跟踪超时后被排除的名字、被 `fake-ip-filter` 放行的名字——有个共同点：代理收到包时只有 IP，没有名字。于是出现三类把名字「找回来」的机理。本节只归纳为什么需要它们以及各自的边界，具体规则与实例在第 14 章。

### sniff：从协议首部里读名字

TLS 的 SNI 与明文 HTTP 的 `Host` 首部在连接建立时就会带出域名，代理可以在完全不改动 DNS 的前提下，从首部还原出名字再拿去匹配规则。边界很清楚：只对首部明文可见的流量有效，加密 ClientHello 一类机制会封住这个入口（见官方资料），非 HTTP/TLS 协议根本读不到；而且 sniff 是启发式的，读不到时必须有兜底行为——放行还是拒绝，这个兜底本身就是策略，属于第 5、14 章反复出现的 fail-open / fail-closed 取舍。

### resolve：从缓存反查

如果本地缓存里存着「域名 → IP」的映射，代理可以拿目的 IP 反查缓存得到域名。它比 sniff 便宜，不用等首部；但只在缓存未过期、且该 IP 确实来自一次本地可观测的查询时成立。CDN 的共享地址、anycast（第 26 章）、一对多映射都会让反查变成多义。更要紧的是语义：反查到的是「曾经解析过这个名字」，不是「这次连接一定属于这个名字」。所以它能当规则匹配的提示，不能当审计证据。

### 规则集与 ip_version 固定出口

按域名规则集分流（第 14 章 `route.rules`）解决「同一个名字走哪条路」；`ip_version` 一类参数解决「这次解析要 A 还是 AAAA」，避免出现「规则说走 v6、解析器却给了 v4」的错配。在纯 v6 + NAT64 的场景里，这个开关还决定客户端会不会去问 AAAA——不问就没有合成，合成不做 NAT64 就空转。三者合起来看：域名还原不是 DNS 的替身，而是「DNS 已经把名字丢了」之后的补偿机制；补偿用得越多，说明上游的 DNS 形态越不适合这套代理架构。

## Fake-IP 与 DNS64 的本质区别

### 本地占位与可路由合成地址

Fake-IP 给出的 `198.18.0.10` 在公网和内网都不存在对应主机：它只在本地映射表里有意义，必须经 TUN / 透明代理反查成域名才能用，一旦离开那台设备就是黑洞。DNS64 合成的 `64:ff9b::c000:20a` 是真的能路由的：网络里有 NAT64 设备为这个前缀准备了状态映射，任何不参与这套代理的普通 IPv6 主机拿到它，一样能发包并到达目标。一个是**本地占位票据**，一个是**可路由合成地址**。

由此推出三条不同的性质：

- **谁做决定**：Fake-IP 由本地代理决定（映射表 + 域名规则集），DNS64 由网络侧解析器与网关决定（合成策略 + 翻译状态）。前者是端点行为，后者是网络行为。
- **对 DNSSEC 的影响**：Fake-IP 替换的是本地应答，压根不进验证器；DNS64 在网络侧改写应答，会和验证器正面冲突。
- **失败模式**：Fake-IP 的失败是「反查不到域名」，表现为黑洞或误判断网，排查看映射表与连接跟踪；DNS64 的失败是「拿不到合成 AAAA」，表现为超时或「无 IPv6 地址」，排查看解析器与前缀是否一致。

两者目的完全不同，也不是互为备选：一个服务于「按域名分流」，一个服务于「纯 v6 网络访问 v4 目标」。同一个名字理论上可以先后经过两种变形（本地占位 → 出口侧真实解析 → 出口网络恰好是 NAT64 环境），但每一步的改写者、地址性质与失效点都要分开算，不能因为「都改了 DNS 应答」就归成一类。

### 排查顺序：先定位改写者

现场遇到「代理/过渡环境里 DNS 不对」时，按下面顺序问，能省掉大半无效排查：

1. 这次流量到底有没有 DNS 查询？没有（IPv4 字面量、缓存命中、连接池复用），所有基于应答改写的机制都不参与。
2. 查询送到了哪台解析器？是本机存根、网关转发器、RDNSS 下发的解析器，还是 App SDK 里硬编码的外部端点？这一步决定谁有机会改写。
3. 它返回的 A / AAAA 是真实地址、本地占位、还是合成地址？看地址段就能分：`198.18.0.0/15` 一类是占位，`64:ff9b::/96` 一类是合成，其余按真实应答处理。
4. 那个地址在转发路径上有人接吗？占位要代理反查，合成要 NAT64 状态映射，两者缺一即黑洞。
5. 规则匹配用的是域名还是 IP？域名还原失败时，兜底是放行还是拒绝（第 5、14 章的 fail-open / fail-closed 取舍）。

第 2 步最容易漏。管理员盯着自己那台递归解析器的日志，客户端却早把查询送到了别处——日志里什么都没有，恰恰就是答案。

### 场景总表

| 场景 | DNS 形态 | 谁做决定 | 失效点 | 本书章节 |
|---|---|---|---|---|
| 普通递归解析 | 真实 A / AAAA 应答 | 递归解析器 | 上游不可达、负缓存放大 | 第 3、4、6 章 |
| DoH（自建端点） | 二进制 DNS 报文套 HTTP/2 | 配置里的 URI Template + 端点解析器 | 端点运营者可见全部查询；HTTP 缓存语义 | 第 12、17 章 |
| HTTPDNS | JSON / 私有文本，App 内嵌 SDK | SDK 里硬编码的端点 | 绕过本机/内网 DNS 策略、DNSSEC 与观测 | 第 13 章 |
| Fake-IP | `198.18.0.0/15` 本地占位 | 本地代理的映射表 + 域名规则集 | 探测 / 服务发现 / 内网域 / literal / UDP / QUIC / PTR | 第 14 章 |
| DNS64 + NAT64 | 合成 AAAA（`64:ff9b::/96` + v4） | 网络侧 DNS64 解析器 + NAT64 网关 | DNSSEC、DoT/DoH 绕过、前缀混配、查询翻倍 | 第 18、19 章 |
| 464XLAT / CLAT | v4 应用本地翻译 + 网络侧合成 | CLAT 侧 DNS proxy + 网络 DNS64 | literal IPv4、查询翻倍、RDNSS 解析器不合成 | 第 19 章 |
| 域名还原 | DNS 已给出 IP，名字从首部或缓存补回 | 代理的启发式匹配 | 首部加密、缓存多义、兜底策略 | 第 14 章 |

表里最后两列是排查顺序的提示：先定位「谁做决定」，再对照「失效点」。多数现场问题不是协议没实现，而是改写者被换掉了——客户端改用了别的解析器，或网络侧的策略根本没被调用到。

## SSH / SOCKS 通道里，DNS 到底归谁解析

代理场景里最容易漏的一层是：**`ssh -D` 起的 SOCKS 监听并不自动接管系统 DNS**。应用把目标名字交给谁解析，决定了查询是留在本机还是走通道 —— 这就是「DNS 泄漏」的分界。

一类客户端把这层选择写成一个开关，常见形态是 **`resolvdns yes/no` 式的 DNS 归属设置**：`yes` 把主机名直接交给对端或代理去解析，`no` 则由本机先解析成 IP 再把连接交给通道。本书按语义描述这类开关，**不把它归为 OpenSSH `ssh_config` 的原生选项** —— OpenSSH 里没有同名配置项，具体名称与归属以所用客户端文档为准。公开可查的等价能力分散在几处：

| 实现 | 形式 | 语义 |
|---|---|---|
| PuTTY | "Do DNS name lookup at proxy end" = Yes / No / Auto | Yes 传主机名；No 本地解析后传 IP；Auto 下 HTTP/SOCKS5 传主机名、SOCKS4 不传 |
| Firefox | `network.proxy.socks_remote_dns` | 让 SOCKS v5 代为解析 |
| curl | `--socks5-hostname` / `socks5h://` | 远程解析；`--socks5` / `socks5://` 是本地解析 |
| sshuttle | `--dns` / `--to-ns` | 捕获本机 53 查询并转发到远端解析器 |

判读方法：让客户端访问一个你控制的全新名字，同时在两端分别看 DNS 日志 —— 只有「本机无查询、对端有查询」才能证明名字确实交给了通道，仅凭出口 IP 变化说明不了 DNS 归属。这与第 29 章「客户端绕过」、第 36 章的工具箱是同一条线索：**先分清是哪一层在解析，再谈通不通**。

## 本章要点

1. DoH 是「同一份 DNS wire format + 加密传输」，信任从链路转移到端点运营者，本机策略仍可完整保留；HTTPDNS 是「App 内嵌 SDK + JSON API」，把解析动作整体搬出系统解析器，绕过过滤、DNSSEC 与观测。同一 resolver 可以同时提供两种接口，那是两种外观而非两种协议。
2. Fake-IP 用 `198.18.0.0/15` 的本地占位地址把「域名 → IP」推迟到连接建立时，让 TUN / 透明代理还能按域名分流；它不可路由、必须反查，连通性探测、服务发现、内网域、IPv4 字面量、UDP/QUIC、PTR 都是失效边界，靠 `fake-ip-filter` 缩小范围而非修好地址。
3. DNS64 [RFC 6147] 合成 AAAA、NAT64 [RFC 6146] 做状态式转换、CLAT [RFC 8683] 补 IPv4 字面量、DNS proxy [RFC 5625] 约束转发行为；六个坑是 DNSSEC 冲突（安全感知主机应本地做 DNS64）、DoT/DoH 绕过网络侧合成、知名前缀与 v4 地址不能混配、literal IPv4 不走 DNS、CLAT 查询翻倍、RDNSS 下发的解析器自身不做合成。
4. sniff（SNI / HTTP Host）、resolve（缓存反查）、域名规则集与 `ip_version` 固定出口，都是「DNS 已经不给名字」之后的补偿机理，不是 DNS 的替身；补偿越多，说明上游 DNS 形态越不适合这套代理架构。
5. 判断任何代理或过渡方案只需三问：应答在哪一层被改写、改写者是否还掌握原始域名、改写后的地址是否真的可路由。Fake-IP 是本地占位（不可路由、必须反查），DNS64 是可路由合成地址，二者目的不同，不能互换。
6. 加密传输（DoT/DoH/DoQ）与 DNSSEC 不互相替代：前者管链路隐私，后者管数据完整性与来源认证；DNS64 在网络侧改写应答，破坏的正是后者。
