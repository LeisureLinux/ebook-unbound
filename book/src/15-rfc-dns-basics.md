# 第四篇　RFC 与协议理论 {.unnumbered}

# DNS 基础 RFC 族

[RFC 1034] 与 [RFC 1035] 发布于 1987 年 11 月，前者叫 *Domain Names - Concepts and Facilities*，后者叫 *Domain Names - Implementation and Specification*。两者加起来不到两百页，却规定了此后三十多年几乎所有 DNS 行为的骨架：命名空间是树、解析是自上而下的委派、报文是固定首部加四个段、资源记录（resource record, RR）是类型化的键值。

这一章不复述报文格式表，也不给任何配置块。它要回答的是另一类问题：为什么后来的十几份 RFC 都要回来"澄清" 1987 年的原始文本；这些澄清各自堵住了哪个实现漏洞；以及当我们在第三篇里打开某个开关时，究竟是踩在哪一条条文逻辑上。全章对每份 RFC 采用统一的四段式：**它要解决什么 → 关键条文 → 对实现的约束 → 常见误读**。

第四篇统一按 RFC 编号引用，不写完整 URL；可核验的公开链接集中在本章末尾《参考资料》。

## 命名空间与报文：[RFC 1034] / [RFC 1035]

### 它要解决什么

1980 年代初的主机名到地址映射靠一份集中维护的 `HOSTS.TXT`。规模一大，分发延迟、名字冲突、单点编辑权都成了问题。[RFC 1034] 的答案是把名字空间做成**倒置的树**，并把管理权按子树切分：根不存主机，只存指向顶级域的委派；每一级只对自己这一层负责。[RFC 1035] 把这套概念落成线格式与算法，定义了报文首部、四类段（Question / Answer / Authority / Additional）、以及资源记录的通用编码。

两者是一体的：[RFC 1034] 明确写着自己"省略了许多细节"，细节要到配套的 [RFC 1035] 里找；反过来 [RFC 1035] 假定读者已经读过 [RFC 1034] 的概念部分。把它们拆成"概念 RFC"与"实现 RFC"是理解后续所有澄清 RFC 的前提——**后来大量的争议不是概念错了，而是线格式层面的歧义没写死**。

### 关键条文

- 域名是从叶向根读的标签序列，书写时用点分隔；根用零长度标签表示，绝对域名以根标签结尾。树上的每个节点可以有一组 RR，节点的存在与否和它有没有某个类型是两件事。
- 委派（delegation）通过 NS RRset 与胶水记录（glue record）实现：父区在 Authority 段给出子区的 NS，并在 Additional 段附上这些 NS 名字对应的地址，让递归解析器不必先解析 NS 名字就能继续往下走。
- 报文首部里的 RD（Recursion Desired）、RA（Recursion Available）、RCODE、以及四个计数，规定了存根解析器与递归解析器之间的分工。CNAME 与 DNAME 之类的重定向由应答内容表达，不是独立 RCODE。
- [RFC 1034] 定义了 TTL 与缓存的必要性：任何应答都可以被缓存，缓存时长由 RRset 的 TTL 决定；[RFC 1035] 规定了压缩指针（compression pointer），允许报文里重复出现的域名用两字节偏移引用。

### 对实现的约束

递归解析器必须实现**迭代**（iteration）：从根 hints 出发，一次一个区切（zone cut）往下问，把每次得到的委派当作新的权威服务器集合。权威服务器在应答里塞进不属于自己权威范围的附加数据，接收方不能直接信任——这条约束在 [RFC 2181] 里被再次强调，也是现代清理器（scrubber）只把"可信"数据写入缓存的条文源头。

压缩指针意味着解析器不能简单地按字节比较域名：同一个名字在报文里可能有多种编码形式。大小写不敏感与压缩叠加，直接催生了 [RFC 4343] 的澄清。

### 常见误读

**误读一：RD=1 表示"请递归"，所以权威服务器必须递归。** 权威服务器对 RD 置位的查询仍可只回答自己权威范围内的数据，并把 RA 清零；RD 是请求方的意图，不是命令。把"收到带 RD 的查询"当成"必须代为解析"是开放解析器（open resolver）常见的成因之一。

**误读二：Additional 段里的地址是可信数据。** 不是。只有落在当前委派所必需的胶水范围内的地址才有理由被使用；域外夹带的 glue 是经典缓存投毒面。这一点与 DNSSEC 是否开启无关，任何模式都该清理。

**误读三：NXDOMAIN 只说"这个名字不存在"。** 原始文本表述含糊，直到 [RFC 8020] 才把"其下所有名字也不存在"钉死。这个歧义是第三篇里严格查询名最小化（strict QNAME minimisation）踩坑的条文根源。

## 操作与规范的澄清：[RFC 1912] / [RFC 2181]

### 它要解决什么

[RFC 1912]（1996，*Common DNS Operational and Configuration Errors*）是 Informational，它不定义协议，而是把当时实际部署里反复出现的配置错误列成清单：SOA 参数不合理、CNAME 与其他类型共存、NS 指向 CNAME、PTR 缺失、胶水不匹配、把私有地址写进公共区等。它的动机很朴素：协议没错，但人写错了，而且错法高度重复。

[RFC 2181]（1997，*Clarifications to the DNS Specification*）性质不同，它是把 [RFC 1034]/[RFC 1035] 里"似乎规定了但各家实现理解不一致"的地方重新写明确的规范文本。

### 关键条文

[RFC 2181] 里对后续实现影响最大的几条：

- **RRset 是缓存与签名的单位**。同一 owner name、同一 class、同一 type 的所有记录构成一个 RRset，必须整体处理：TTL 必须一致，不能只缓存其中一条，也不能把从不同应答里拼起来的记录混成一个 RRset。后来 DNSSEC 的 RRSIG 签的是 RRset 而不是单条记录，根子就在这里。
- **TTL 的语义被收紧为"最多可缓存的秒数"**，并明确 16 位无符号解释、以及高位被置时的处理，避免把大 TTL 当负数。
- **RCODE 与区段内容的组合**被逐类说明：什么是 referral、什么是权威否定、什么时候 Authority 段的 NS 属于引用而非答案。
- **class 不是只有 IN**，类型码与 class 码是独立的命名空间；实现不该假定 QCLASS 恒为 IN。
- **名字的长度上限、标签的字节语义**被明确：DNS 名字比较是逐标签的、大小写不敏感的二进制比较，不是本地化的字符串比较。

[RFC 1912] 则给出了大量"应当避免"的操作惯例，其中与今天仍强相关的包括：NS 与胶水记录必须一致、SOA 的序列号与刷新参数要能真正驱动传送、不要把 CNAME 当作可与其他数据共存的别名。

### 对实现的约束

解析器在缓存层必须以 RRset 为粒度做插入、淘汰与 TTL 递减；以"单条记录"为粒度的缓存会在 TTL 不一致时产生半新半旧的应答。清理器还需检查应答里 owner name 是否落在查询所期待的范围内，避免把无关联的 RRset 顺手写进缓存。

权威侧与递归侧共用一套线格式解析，但信任边界不同：权威服务器对本地区数据天然可信，递归解析器对收到的任何东西都要重新判定归属。

### 常见误读

**误读一：[RFC 1912] 是标准，必须逐条照做。** 它是 Informational，内容是运维经验清单，不是协议一致性判据。但其中"NS 不能指向 CNAME""CNAME 不能与其他数据共存"后来在别处被规范化，实际约束力比它的类别看起来强。

**误读二："澄清"意味着 [RFC 1034] 写错了。** 更准确的说法是：原文留了多种自洽的读法，[RFC 2181] 选定一种并要求实现收敛。把澄清 RFC 当"补丁列表"读，会漏掉它最有价值的部分——RRset 作为原子单位这一条，后来成了整个 DNSSEC 数据模型的地基。

## 负缓存：[RFC 2308]

### 它要解决什么

[RFC 1034] 提到了可以缓存否定应答，但没说清楚缓存多久、按什么判据判定"这是否定应答"、以及 NXDOMAIN 与"名字存在但类型不存在"要不要区别对待。结果是否定查询反复打向权威服务器，既浪费带宽也放大故障。[RFC 2308]（1998，*Negative Caching of DNS Queries (DNS NCACHE)*）把负缓存（negative caching）从"可选优化"提升为解析器应有的常规行为，并明确说"negative caching should no longer be seen as an optional part of a resolver"。

### 关键条文

- 区分两种否定：**NXDOMAIN**（RCODE = Name Error，名字不存在）与 **NODATA**（RCODE = NOERROR、Answer 段无相关记录、Authority 段有 SOA 或无 NS）。NODATA 是伪 RCODE，必须从应答内容算法式地判定，没有独立编码。
- 负缓存的 TTL 取自 Authority 段 SOA 记录的 MINIMUM 字段与 SOA 自身 TTL 中**较小者**；[RFC 2308] 还重定义了 SOA MINIMUM 的语义为"负缓存 TTL"，不再被当作区刷新间隔使用。
- 负应答的 RCODE 不能被解析器"美化"成 NOERROR 空应答；缓存的否定要能在后续同域查询时直接复用，包括对同名不同 QTYPE 的查询。
- [RFC 2308] 也允许对 SERVFAIL 一类失败做短时缓存（上限很小，常见实现取数分钟），但明确这属于实现选择。

### 对实现的约束

解析器必须为否定结果建立独立的缓存条目，并且该条目要有明确的过期时间；不能靠"没有正向记录"来隐式表达否定。缓存键要同时覆盖 QNAME、QTYPE 的否定语义与 class，否则 NODATA 会被误用于其他类型。

运维上最要紧的推论：**上游一次瞬时 NXDOMAIN 会被按 SOA minimum 缓存**——现实中这个字段常见取 3600 秒。权威侧修好之后，客户端仍会在整段 TTL 内继续失败。而链路上的每一层缓存（本地 Unbound、前置缓存、系统存根）各自持有一份否定条目，只刷其中一层不会让故障消失。第三篇与第五篇讨论的"逐层刷缓存"就是从这条条文里直接推出来的。

### 常见误读

**误读一：负缓存只缓存 NXDOMAIN。** NODATA 同样要缓存，判定逻辑反而更复杂。只实现前者的解析器会在"域名存在但没有 AAAA"这类高频查询上反复外发。

**误读二：把 SOA MINIMUM 当刷新计时器。** [RFC 2308] 之后它在负缓存语境里的含义是 TTL 上限；区传送节奏由 SOA 的 REFRESH / RETRY / EXPIRE 决定。

**误读三：负缓存是"错误"，关掉更安全。** 关掉等于把否定查询全部变成实时递归，权威侧抖动会被原样放大到客户端；问题不在机制，而在 TTL 取值与故障时的可观测性。

## EDNS0：[RFC 2671] → [RFC 6891]

### 它要解决什么

1987 年的报文首部把不少字段用满了：RCODE 只有 4 位、标志位没有余量、UDP 应答默认被限制在 512 字节。DNSSEC 一出现，签名与密钥让应答轻易超过 512 字节，必须走 TCP，代价是连接开销。[RFC 2671]（1999，*Extension Mechanisms for DNS (EDNS0)*）用"伪资源记录"的方式扩展报文而不改首部；[RFC 6891]（2013，*Extension Mechanisms for DNS (EDNS(0))*, STD 75）**废弃** [RFC 2671] 与 [RFC 2673]，成为现行规范。

### 关键条文

- OPT 伪 RR 放在 Additional 段，owner name 为根，type 为 OPT；它的 CLASS 字段被借作**请求方 UDP 载荷上限**，TTL 字段被借作扩展标志（其中最高位是 DO 位，供 DNSSEC 使用），RDATA 承载若干 `option-code / option-length / option-value` 三元组。
- 扩展 RCODE 由 OPT 里的 8 位 EXTENDED-RCODE 与原首部 4 位组合，形成 12 位 RCODE 空间；BADVERS 用于版本不匹配。
- 不支持 EDNS 的一方会忽略或拒绝 OPT；**发送方必须能在超时后回退**：先降载荷、再退回无 EDNS 的 512 字节 UDP、必要时走 TCP。[RFC 6891] 把这种回退与"不要对同一服务器反复重试已知不支持的扩展"写成实现要求。
- OPT 不是真实 RR，不进缓存、不参与签名、不出现在区文件里。它只在这一个报文的这一跳上有效。

### 对实现的约束

解析器出向通告的 UDP 载荷与入向可接受的最大值是**两个方向、两个参数**。只调入向参数不会缩小自己发出的查询，路径 MTU 出问题时分片照样发生。这也是本书把出向 EDNS 载荷压到 1232 字节、而不是沿用早期 1472 字节的条文依据：IPv6 规定的最小链路 MTU 是 1280 字节（见 [RFC 8200]），减去 IPv6 首部与 UDP 首部后，1232 是能在不分片前提下装下的 DNS 载荷；PPPoE 1492、各类隧道 MTU 也都比 1472 更紧。

此外，EDNS 是逐跳的：转发器与上游之间、上游与权威之间可以各自协商不同的载荷。任何一跳丢失分片，表现都是"等超时 → 重试 TCP"，而不是清晰的报错。

### 常见误读

**误读一：EDNS0 等于 DNSSEC。** EDNS0 只是承载机制；DO 位表示"请把 DNSSEC 相关记录给我"，但数据完整性与来源认证由 DNSSEC 自己完成。反过来，DoT / DoH / DoQ 提供的是**传输加密与隐私**，与 EDNS0 也毫无替代关系。

**误读二：把载荷调大能提升性能。** 在存在分片丢弃的链路上，调大只会把一次 UDP 往返变成一次超时加一次 TCP 连接。

**误读三：OPT 里的选项会被中间解析器透传。** 不会。每个解析器按自己与下一跳的协商重新构造 OPT；ECS（[RFC 7871]）这类选项的隐私代价正来自"它会被有意识地重新生成并沿链路传递"，见第 17 章。

## 未知 RR 类型：[RFC 3597]

### 它要解决什么

[RFC 1035] 只定义了当时存在的类型码。新类型（后来有 SRV、NAPTR、DS、RRSIG、NSEC、SVCB、HTTPS 等）出现时，如果每个中间节点都要升级软件才能"看懂"新记录，协议就无法演进。[RFC 3597]（2003，*Handling of Unknown DNS Resource Record (RR) Types*）给出的是**透明转发**规则：不认识类型时，按通用二进制格式搬运，不要猜测、不要丢弃、不要把 RDATA 当名字解析。

### 关键条文

- 定义 `\# <length> <hex>` 的通用 RDATA 表示法，供区文件与展示工具使用。
- 明确**名字是否可压缩取决于类型**，未知类型的 RDATA 里不得做压缩指针解析，也不得对 RDATA 里的字节做大小写折叠。未知类型的记录按不区分大小写处理其 owner name，但 RDATA 保持原样。
- 服务器对未知 QTYPE 应正常应答（有则给记录，无则 NODATA），不得因为"不认识"就返回 FORMERR 或 REFUSED。
- 递归解析器缓存未知类型时按 RRset 整体缓存，与已知类型一致。

### 对实现的约束

这条 RFC 是 SVCB / HTTPS 记录能被逐步部署的前提，也因此是第 17 章 DDR 发现机制能跑在现有解析器上的前提。它要求缓存与转发路径对类型码保持"数据不可知"：只有当实现确实知道某类型的语义（例如 DS 用于构建信任链）时才做特殊处理。

它也解释了 DNSSEC 的一个设计选择：RRSIG、NSEC、DS 等在 [RFC 4034] 中被明确定义之前，中间设备若按 [RFC 3597] 透明搬运，就不会成为部署障碍。

### 常见误读

**误读一：不认识的类型可以丢掉以"保持安全"。** 丢弃会制造人为的 NODATA，客户端会据此得出错误结论（例如认为某域不支持某种服务），而且这种错误会被负缓存放大。

**误读二：所有 RDATA 里的域名都能压缩。** 只有类型定义允许时才可以；[RFC 3597] 明确禁止对未知类型做压缩解析，避免把任意二进制误当成指针。

## 大小写：[RFC 4343]

### 它要解决什么

[RFC 1034] 说域名比较"case-insensitive"，但没说清边界：是 ASCII 字母吗？非 ASCII 字节呢？大小写不敏感是否适用于 RDATA 里的名字？压缩指针里的名字呢？0x20 编码这类把大小写当随机熵使用的技巧是否合法？[RFC 4343]（2006，*Domain Name System (DNS) Case Insensitivity Clarification*，更新 [RFC 1034]/[RFC 1035]/[RFC 2181]）逐条收口。

### 关键条文

- DNS 名字的大小写不敏感**仅指 ASCII 的 A–Z 与 a–z**，且只作用于 owner name 与 RDATA 中"域名类型"的字段；其他字节不折叠，也不做 Unicode 大小写或本地化规则。
- 比较与缓存键应当按规范化形式进行，但**应答里应尽量保留查询方原本的大小写写法**（所谓 0x20 兼容）：解析器把查询名里的大小写当作额外熵，权威服务器回显它，接收方据此判别应答是不是针对自己这次查询的伪造包。
- 大小写不敏感不改变线格式：压缩指针、标签长度、字节序列都照旧。
- 明确"case-insensitive"不等于"case-preserving 是必需的"，但把大小写原样回显是实现可以合法利用的信道。

### 对实现的约束

缓存键必须规范化，否则 `Example.ORG` 与 `example.org` 会变成两份缓存条目，负缓存与 DNSSEC 验证结果也会分裂。同时，出向查询名可以携带随机化的大小写，只要接收与比较时按不敏感规则处理；这要求实现把"比较用的规范形式"与"线上实际发的字节"分开保存。

对 DNSSEC 也有一层影响：规范名（canonical name）用于签名计算时统一按小写处理，因此大小写差异不应导致签名验证失败；但把 RDATA 里非名字字段也一起折叠，就会破坏签名。

### 常见误读

**误读一：大小写不敏感 = 全部转小写后连 RDATA 一起改。** 会破坏二进制 RDATA，尤其对未知类型（[RFC 3597]）。

**误读二：0x20 是加密或认证。** 它只是提高伪造应答的猜测成本，属于熵增强；[RFC 4343] 讲清它合法，不等于讲清它安全。真正给数据来源认证的是 DNSSEC，给传输加密与隐私的是 DoT / DoH / DoQ。

## 特殊用途域名：[RFC 6761]

### 它要解决什么

`.local`、`.test`、`localhost`、`onion`、`invalid`、以及后来的 `resolver.arpa`、`home.arpa` 这类名字，散落在各份 RFC 里被"保留"，但保留到底意味着什么并不统一：是权威服务器上永远不该出现？是递归解析器必须本地回答？还是仅仅"建议别用"？[RFC 6761]（2013，*Special-Use Domain Names*）定义了"特殊用途域名"这一概念、注册程序，并建立了 IANA 注册表，把若干已有名字作为初始条目写入。

### 关键条文

[RFC 6761] 为每个特殊用途域名按七类问题给出明确答案，其中最要紧的三类是：

- **用户与应用**是否应把它当普通域名对待；
- **存根解析器 / 递归解析器**是否应本地生成应答、是否允许向上游查询；
- **权威服务器**是否应对该名字下的查询给出 NXDOMAIN 或 NODATA。

例如 `invalid` 被设计为"保证解析失败"，用于测试；`test` 保留给测试与文档；`localhost` 要求本地解析到环回地址、不许出网。注册表是活的表，后续 RFC 可以往里加条目（第 17 章的 `resolver.arpa`、第 18 章涉及的 `home.arpa` 都是通过各自 RFC 注册或引用的）。

### 对实现的约束

递归解析器需要一份本地策略来处理这类名字：**在本地给出规定好的应答，不向外发送查询**。这既避免把内部查询泄露到公网，也避免让上游的意外应答污染本地语义。第三篇里对 `_dns.resolver.arpa.` 做 `always_nodata`、以及用 canary 域让浏览器退回系统解析器的做法，条文依据都落在这套"本地服务区（locally served zone）"思路上，而不是"按 IP 封端口"。

需要注意 [RFC 6761] 建立的是**框架**：某个具体名字该返回什么，要看注册表中该条目所引用的具体 RFC。把"特殊用途"笼统理解成"一律 NXDOMAIN"是错的。

### 常见误读

**误读一：保留名只是"没人注册所以解析不了"。** 不是。它要求实现主动做本地处理；依赖"公网恰好没有这个区"是不可靠的。

**误读二：特殊用途域名可以随意拿来当内网域名。** 恰恰相反，注册过的名字有规定语义；自建内网应使用自己拥有的域名或使用明确规定可用于此目的的名字，并把文档示例域名（`example.net` 等）与实际部署区分开。

## NXDOMAIN cut：[RFC 8020]

### 它要解决什么

原始规范对 NXDOMAIN 的范围表述含糊：如果 `foo.example` 返回 NXDOMAIN，那么 `bar.foo.example` 是否必然不存在？按树形命名空间的逻辑应该是，但 [RFC 1034] 没写死，[RFC 2308] 的负缓存规则也没要求据此剪枝。[RFC 8020]（2016，*NXDOMAIN: There Really Is Nothing Underneath*，更新 [RFC 1034] 与 [RFC 2308]）把这句话变成规范：**NXDOMAIN 意味着被否定的名字以及它下面所有名字都不存在**。

### 关键条文

- 递归解析器收到 NXDOMAIN 后，**可以且应当**据此判定该名字的整个子树都不存在，从而停止对该子树的后续查询。
- 这条更新同时修正了 [RFC 2308] 中负缓存适用范围的表述：负缓存条目可以覆盖整个被否定的子树，而不只是被查询的那一个名字。
- 权威服务器若让某个中间名返回 NXDOMAIN、却在更深的子名上挂数据，属于违反本协议的行为；[RFC 8020] 的附录专门解释了为什么"用返回应答的 owner name 来判断"是不可靠的 workaround。

### 对实现的约束

对查询名最小化（QNAME minimisation）影响最直接。最小化解析器逐标签往上问，中间某一层若返回 NXDOMAIN，按 [RFC 8020] 就可以直接结束，无需再问完整域名。**严格模式（strict）**正是把这条推理用到极致：拿到中间层 NXDOMAIN 就断定整条链不存在，不做回退。

现实里存在违反 [RFC 8020] 的权威配置——典型是某些大型 CDN 的 CNAME 区，父名返回 NXDOMAIN、子名却真实存在。此时严格模式会把整站的资源域名判成不存在，页面样式与脚本全部解析失败。而且这个错误结论会被链路上的每一层负缓存按 [RFC 2308] 的 TTL 记住，所以改回宽松模式后**还需要逐层刷新缓存**。第三篇第 13 章记录了这个兼容坑的参数处理；本章只讲条文：出问题的是权威侧违反 [RFC 8020]，不是解析器"多疑"。

另有一条容易混淆的边界：`harden-below-nxdomain` 一类剪枝选项只对 **DNSSEC-secure 的 NXDOMAIN** 生效，无签名区的 NXDOMAIN 不触发它。这是实现把安全强度分级的结果，不是 [RFC 8020] 本身的要求。

### 常见误读

**误读一：NXDOMAIN cut 是解析器可选的优化，不开也没损失。** 它对最小化查询量与负缓存范围有实际影响；但开启严格模式的收益，建立在"所有权威都守规矩"这个前提上。

**误读二：把 [RFC 8020] 当成 DNSSEC 的一部分。** 它是纯 DNS 解析语义的澄清，与签名无关；[RFC 8499] 也把它归入术语与语义收敛的一条线。

**误读三：改了模式就立刻恢复。** 负缓存是分布式的，每一层实例都得刷。

## 术语统一：[RFC 8499]

### 它要解决什么

DNS 由几十份 RFC 共同定义，同一个词在不同年代的文档里含义漂移："resolver" 有时指递归侧、有时指存根；"zone" 与 "domain" 被混用；"negative answer"、"NODATA"、"NXDOMAIN"、"referral"、"delegation" 的边界也常被写混。[RFC 8499]（2019，*DNS Terminology*，废弃 [RFC 7719]、更新 [RFC 2308]）把当前用法集中成一份术语表，供后续 RFC 引用。

### 关键条文

[RFC 8499] 逐条给出当前定义，与本书用词直接相关的有：

- **存根解析器（stub resolver）**、**递归解析器（recursive resolver）**、**转发器（forwarder）**、**权威服务器（authoritative server）**、**缓存解析器（caching resolver）** 是不同角色，一台进程可以同时扮演多个，但概念上不能互换。
- **区（zone）** 是管理边界，**域（domain）** 是命名空间中的子树；**委派（delegation）** 是父区把子区的权威指出去，不等同于区切本身。
- **肯定应答 / 否定应答 / 引用（referral）** 的判据被重新表述，并顺带更新了 [RFC 2308] 对 NODATA 的措辞。
- 明确 "QNAME minimisation"、"aggressive use of DNSSEC-validated cache" 等较新术语的所指。

### 对实现的约束

术语表不产生线格式变化，但它决定了配置文档与日志的可读性：当手册说 "validator"、"iterator"、"scrubber" 时，指的是验证器、迭代器、清理器三个可分离组件；当说 "AD bit" 时指的是验证结果标志而非请求标志。本书采用同一套中文译名（见术语统一表），并把 **DNSSEC = 数据完整性/来源认证** 与 **DoT/DoH/DoQ = 传输加密/隐私** 作为不可互换的两条线，正是遵循 [RFC 8499] 的收敛方向。

### 常见误读

**误读一：术语 RFC 没有技术内容，可以忽略。** 恰恰相反，很多"配置看起来对但结论错"的排查，根源是把 `forwarder` 当成 `recursive resolver`，或者把 `NODATA` 当成 `NXDOMAIN`——这两种否定在负缓存、在查询名最小化、在 DNSSEC 否认存在里的处理都不同。

**误读二：把 "caching resolver" 当产品名。** 它是角色。一个进程可以既是递归解析器又是缓存解析器，也可以只做转发而不自行迭代。

## 过期缓存应答：[RFC 8767]

### 它要解决什么

权威服务器不可达（DDoS、链路故障、配置事故）时，传统解析器在 TTL 到期后只能返回 SERVFAIL。但缓存里那份数据往往仍然正确——变化的只是"没来得及重新确认"。[RFC 8767]（2020，*Serving Stale Data to Improve DNS Resiliency*）把业界早已存在的做法写成规范：在刷新失败时，允许把过期缓存应答（serve-stale）返回给客户端，用短暂的数据陈旧换取可用性。

### 关键条文

- 定义三个计时器：**查询解析计时器**（一次解析努力的总时长上限）、**最大过期计时器**（数据最多能被当作过期数据使用多久）、以及已有的常规解析计时器。
- 建议流程是**先尝试刷新，失败或超时才回过期缓存**，而不是一开始就回旧数据；[RFC 8767] 也讨论了"先回旧数据再后台刷新"的变体。
- 返回过期数据时应让客户端能感知：TTL 被置得很小，且应答不应被误标为权威。
- 明确过期数据不是"权威数据"，不得用它去覆盖 DNSSEC 验证失败，也不得把它当作新的信任依据。

### 对实现的约束

实现必须把"缓存条目的 TTL 到期"与"条目被删除"分开：前者之后条目仍要留在缓存里一段时间，才能被 serve-stale 复用。同时要先启动刷新、在计时器到期后才回退，否则会把一次瞬时抖动变成全站旧数据。

这里最容易被误读的是计时器单位：`serve-expired-client-timeout` 的取值单位是**毫秒**，默认 1800 即 1.8 秒，语义是"先尝试刷新，超过 1.8 秒还没结果才回过期缓存"，不是 1800 秒。把它当秒来调，等于把回退窗口放大三个数量级。

还要注意与 [RFC 2308] 的关系：serve-stale 复用的是**过期的肯定数据**，负缓存里的否定结果不应被同样复用——把一次瞬时 NXDOMAIN 当"过期但可继续用"的旧答案，会把负缓存放大故障的问题再叠一层。

### 常见误读

**误读一：serve-stale 等于"忽略 TTL"。** 它只在刷新努力失败时启用，且有最大过期时长上限。

**误读二：过期数据一定是错的。** 大多数 DNS 记录的 TTL 远短于实际变更频率；但"通常正确"不等于"可以认证"，DNSSEC 验证状态必须重新判定。

**误读三：可用性机制能替代安全机制。** [RFC 8767] 解决的是权威不可达时的可用性，与 DNSSEC 的数据完整性、与加密传输的隐私，三者各补一块。

## 文档地址段：[RFC 5737]

### 它要解决什么

技术文档、示例配置、教材里的 IP 地址如果随手写成可路由的公网地址，读者复制粘贴后可能真的把流量送到无辜的第三方，也会让"这个地址属于谁"变成误导。[RFC 5737]（2010，*IPv4 Address Blocks Reserved for Documentation*，更新 [RFC 1166]）指定三段专门用于文档的地址，并在 IANA 保留。

### 关键条文

- `192.0.2.0/24`（TEST-NET-1）、`198.51.100.0/24`（TEST-NET-2）、`203.0.113.0/24`（TEST-NET-3）专门留给文档与示例。
- 这些地址**不应出现在公共互联网路由表**中，也不应被当作可到达的目的地；文档作者可以放心使用，不需要向任何人申请。
- 对应的 IPv6 文档前缀是 `2001:db8::/32`（[RFC 3849]），私有网络地址用 RFC 1918 段与 [RFC 4193] 的 ULA 通用写法。

### 对实现的约束

本书所有示例统一使用上述段，并明确标注"以下为教学用示例地址"。域名侧使用 `gw.example.net`、`dns.example.org`、`resolver.example.net` 这类保留示例名；ULA 用 `fd00:…` 的通用写法；API token 一律写作 `<TOKEN>` 或 `example-token-0000`。

这条约束不只是脱敏，也是可复现性要求：读者在自己的实验环境里看到 `192.0.2.x` 时，应当立刻知道"这是要被替换的占位符"，而不会误以为某台真实主机在应答。

### 常见误读

**误读一：文档地址段就是私有地址。** 不是。RFC 1918 的地址（如 `192.168.x.x`）可以在真实内网使用；[RFC 5737] 的三段只应出现在文档里，不该被配置到接口上。

**误读二：只要换掉 IP 就不算泄露。** 主机名、域名、token、拓扑全貌同样属于需要泛化的信息；本书把它们统一处理为 `gw-01`、`edge-01`、`cloud-01` 这类中性教学标识，并明确写为教学环境。

## 条文之间的因果链

把上面十一组 RFC 串起来，能看到一条清晰的演进逻辑，而不只是编号列表：

1. [RFC 1034]/[RFC 1035] 定义了树、委派、报文与缓存，但把许多边界留给实现自己判断。
2. [RFC 1912] 收拾运维错误，[RFC 2181] 把 RRset、TTL、RCODE 组合这些歧义收口；RRset 作为原子单位后来成了 DNSSEC 签名的数据模型基础（第 16 章）。
3. [RFC 2308] 补上负缓存，[RFC 8020] 补上 NXDOMAIN 的作用范围；两者叠加，既让否定查询不再反复外发，也埋下了"瞬时否定被长时间记住""严格最小化遇到不守规矩的权威"两类坑。
4. [RFC 2671] → [RFC 6891] 用 OPT 伪 RR 打开扩展空间，才有 DNSSEC 的大应答、ECS 的选项、SVCB 的承载；[RFC 3597] 保证新类型能穿过不认识它的中间节点。
5. [RFC 4343] 把大小写不敏感的边界划清，使 0x20 熵增强与缓存规范化能共存；[RFC 6761] 把"这个名字不要出网"变成显式本地策略；[RFC 8499] 最后把三十年里漂移的词汇统一。
6. [RFC 8767] 在可用性维度上给缓存加了一条"过期但可回退"的路径，与 [RFC 2308] 的否定缓存形成互补而非重复。
7. [RFC 5737] 与 IPv6 文档前缀是写作层的基础设施，保证前六步讨论的所有机制都能用不会伤及第三方的示例地址讲清楚。

这条链也解释了第四篇与其余各篇的分工：第二、三、五篇处理"怎么做"，本卷只处理"为什么这么规定"。例如 EDNS 1232 的取值在第三篇是配置，在这里是 [RFC 6891] 的逐跳载荷协商加上 [RFC 8200] 的 1280 字节最小 MTU；严格最小化的兼容坑在第三篇是参数，在这里是 [RFC 8020] 与 [RFC 2308] 的组合推论。

## 本章要点

- [RFC 1034]/[RFC 1035] 分工是"概念"与"实现"；后续大量 RFC 不是推翻它们，而是把线格式与语义的歧义收口。[RFC 2181] 确立的 **RRset 原子性**后来成为 DNSSEC 签名的数据模型地基。
- [RFC 2308] 让负缓存成为常规行为：NXDOMAIN 与 NODATA 判据不同，TTL 取 SOA MINIMUM 与 SOA TTL 的较小者；瞬时否定会被长时间记住，且链路上每层缓存都要单独刷新。
- [RFC 2671] 被 [RFC 6891] 废弃；OPT 伪 RR 借 CLASS 通告 UDP 载荷、借 TTL 位承载 DO/扩展 RCODE。**出向载荷与入向最大值是两个方向**，IPv6 最小 MTU 1280 是 1232 字节取值的根因。
- [RFC 8020] 把 NXDOMAIN 的范围钉死为"该名字及其下所有名字均不存在"，这是严格查询名最小化的条文依据；权威侧违反它会造成整站资源解析失败，且错误结论被 [RFC 2308] 的负缓存逐层记住。
- [RFC 3597] 的未知类型透明转发、[RFC 4343] 的 ASCII 大小写边界、[RFC 6761] 的特殊用途域名本地服务区、[RFC 8499] 的术语收敛，分别支撑了 SVCB/HTTPS 逐步部署、0x20 熵增强、DDR 压制与全书用词一致。
- [RFC 8767] 的过期缓存应答是**可用性**机制：先刷新、超时才回旧数据，计时器单位为毫秒；与 DNSSEC 的数据完整性/来源认证、DoT/DoH/DoQ 的传输加密/隐私互不替代。
- 本书示例统一采用 [RFC 5737] 的 `192.0.2.0/24`、`198.51.100.0/24`、`203.0.113.0/24` 与 `2001:db8::/32`，并明确标注为教学用示例地址。
