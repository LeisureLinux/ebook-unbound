# DHCP 与 DNS 的交接面

一台客户端打开网页时先问谁，不是 `/etc/resolv.conf` 自己决定的。地址、掩码、网关、以及"把 DNS 查询交给谁"，绝大多数情况下是同一个 DHCP 应答一次性写进去的。于是 DNS 的**输入侧**并不在递归解析器手里，而在 DHCP 服务器手里：option 6 填错一个地址，Unbound 配得再严也没有流量进来；option 15/119 多塞一个后缀，根服务器就要替你收一批无效查询；option 81 与 option 42 更是从名字和时钟两个方向决定了动态更新能不能成立。**交接面**指的就是这一段：配置从 DHCP 落到存根解析器，再落到 DNS 行为的全过程。

这一章做 DHCPv4 / DHCPv6 的 option 工程。RA / RDNSS / DNSSL 的条文与实现差异见第 18 章，家庭网关"广告自己 ULA 解析器、压制上级 DNS"的部署做法见第 19 章，WPAD 草案的五种发现机制与 devolution 安全史见第 23 章，微软 DNS 与 DDNS 的更新模型见第 25 章。



## 一条配置要穿过四层

"当前生效的 DNS 是谁"不是一个字段，而是四层叠加后的结果。排查时最容易犯的错，就是只看其中一层就下结论：DHCP 服务器明明写对了，客户端却仍在查别处，往往是被更靠上的一层覆盖了。

| 层 | 写入者 | 覆盖关系 | 观测点 |
|---|---|---|---|
| 固件 / 镜像默认值 | 设备厂商 | 最底层，仅在无人下发时生效；常常塞进一个自造后缀 | 恢复出厂后立刻抓一次 `resolvectl domain` |
| DHCPv4 / DHCPv6 租约 | 网关或独立 DHCP 服务器 | 覆盖默认值，但按 T1/T2 刷新，不即时生效 | 租约文件、`resolvectl dns` |
| RA 的 RDNSS / DNSSL | 链路上的任一路由器 | 与 DHCPv6 并行，谁赢取决于主机实现 | `rdisc6` 一类工具按名称在官方资料检索 |
| 每链路 / 每应用覆盖 | VPN、浏览器 DoH、容器运行时 | 优先级最高，能把前三层全部绕开 | 第 13 章客户端绕过、第 32 章加密传输选路 |

第四层要特别标出来：即便 DHCP 侧做到完美，一个自带 DoH 端点的浏览器仍可以把查询直接送出内网（第 13 章的 DDR 压制与 canary 域就是在处理这件事）；第 32 章讲的 DNS64 / Fake-IP 也都建立在"客户端确实把查询交给本地解析器"这个前提上。**交接面只负责把流量交到本地解析器，交到之后不被绕走是第三篇与第 32 章的事**，两段的责任要分清楚，否则故障归因会来回甩锅。

一个实用的判据：先问"这台主机此刻把查询发给了谁"，再问"为什么会发给他"。前者用 `resolvectl dns` 或抓包一次性回答，后者才需要沿着这张表逐层排除。把两件事混在一起，是本章多数排障时间被浪费的原因。

## 一张表：option 编号 → DNS 行为 → 症状 → 验证

左半边是"这个 option 是什么、出自哪份标准"，右半边是运维真正关心的三件事：它改动了哪一个 DNS 行为、配错之后在客户端上看到什么、以及用哪条命令能当场确认。

| Option | 名称 | 作用 | 标准 | 影响哪个 DNS 行为 | 配错的症状 | 验证命令 |
|---|---|---|---|---|---|---|
| 6 | Domain Name Server | 下发一个或多个递归解析器地址 | [RFC 2132]；[RFC 5625] §5.1 | 决定存根解析器把查询发给谁 | 查询全被送到不该去的解析器，本地过滤表与验证策略失效；或 WAN 未通时全部超时 | `resolvectl dns` |
| 15 | Domain Name | 单个默认域后缀 | [RFC 2132]；[RFC 5625] §5.2 | 裸主机名被追加一次后缀 | 固件默认的 `lan` / `local` 类后缀产生大量无效 TLD 查询打根服务器 | `resolvectl domain` |
| 119 | Domain Search List | 多个搜索域，DNS wire 压缩编码 | [RFC 3397] / [RFC 6731] | 裸名依次追加多个后缀，与 `ndots` 叠加放大查询 | 一次访问发出四五次查询，NXDOMAIN 比例升高，日志里全是同一批可疑后缀 | `resolvectl domain` |
| 81 | Client FQDN | 客户端自报 FQDN，附 S/N/O 标志 | [RFC 4702] | 决定是否触发 [RFC 2136] 动态更新、由谁更新 | 名字解析不到自己；或 DDNS 记录被非授权名字占据 | `dig +short gw-01.home.arpa. @192.0.2.53` |
| 252 | WPAD URL | 指向代理自动配置文件 | 1999 年过期草案（非 RFC） | 决定 PAC 文件从哪取 | 代理发现落到组织边界外（详见第 23 章） | `curl -I http://wpad.example.net/wpad.dat` |
| 42 | NTP Servers | 下发时间服务器 | [RFC 2132] | 时钟偏差决定 GSS-TSIG 更新、DNSSEC 验签、日志关联是否成立 | 时钟偏差超过 5 分钟，Kerberos / GSS-TSIG 安全动态更新失败；验证器把有效签名误判为过期 | `timedatectl timesync-status` |
| v6-23 | OPTION_DNS_SERVERS | v6 侧递归解析器地址 | [RFC 3646] | 与 option 6 等价，但走 DHCPv6 通道 | 与 RA 的 RDNSS 各发一套，主机取谁不确定 | `resolvectl dns` |
| v6-24 | OPTION_DOMAIN_LIST | v6 侧域搜索列表 | [RFC 3646] | 与 option 119 等价 | 同 15/119 污染，且 v4/v6 两侧后缀还不一致 | `resolvectl domain` |
| v6-56 | NTP Server 子选项 | v6 侧时间同步 | [RFC 5908] | 与 option 42 等价 | v6-only 客户端无时间源 → 动态更新与 DNSSEC 一并失效 | `chronyc tracking` |
| v6-25 | IA_PD | 前缀委派 | [RFC 8415] 一类 | 决定 LAN 侧前缀，间接决定 RDNSS 发布的解析器地址可达性 | 前缀轮换后旧地址失联（第 18、19 章） | `ip -6 addr show` |

表里的编号空间要分清：DHCPv4 的 6/15/119/81/42/252、DHCPv6 的 23/24/56/25、以及 RA 里的 RDNSS / DNSSL 是三套独立编号，各自的选项类型号按 [RFC 8106] 与 IANA 注册表核对（见官方资料）。不同载体里出现相同的数字纯属巧合，彼此没有任何关系；看到"25"先问是哪个载体，别把 IA_PD 和 RA 的 DNS 选项混为一谈。

### option 6 / 15 / 119：地址、默认后缀、搜索域

option 6 是唯一真正决定"查询去哪"的字段，可以下发多个地址，顺序即存根解析器的尝试顺序。[RFC 5625] §5.1 指出一个很常见的默认值：家用网关把**自己**填进 option 6，因为它同时是一个 DNS 代理（DNS proxy）；这条做法本身合理，问题在于管理员往往改不掉这个默认值，于是"想让客户端直连本地 Unbound"就无从下手。选服务器时要留一个可改的入口，而不是把网关自身硬编码进固件。

option 15 与 119 都不给地址，只给"后缀"。区别是 15 只能给一个默认域，119 给一个有序列表。119 的载荷不是逗号分隔的明文，而是 DNS wire format 的域名标签序列，允许使用压缩指针（[RFC 3397]）；[RFC 6731] 与该编码在客户端侧的处理相关，具体互操作性结论与位级约束见官方资料，本书不臆造字节序列或版本号。正因为编码特殊，不同客户端对压缩指针的支持并不一致，这也是"能不下发就不下发"的现实理由。

[RFC 5625] §5.2 的措辞值得照抄进运维规范：并不存在标准化的 `local` 后缀，默认域**应当为空**；没有显式配置时，服务器就**不要发** option 15 / 119。第 20 章讲过 `ndots` 的代价——绝对域名也会被反复追加 search 域再查一次——把 119 的列表长度乘上去，就是本章要处理的查询放大。确需本地后缀时，用专门保留的 `home.arpa.`，不要自造 `.lan` / `.local`；后者与 mDNS 的 `.local`（第 27 章）还会撞车。

### option 81 / 42：名字与时钟

option 81 让客户端在租约里自报 FQDN，并用几个标志位约定"这次 DNS 更新由谁做"。[RFC 4702] 的三个关键标志：

- **S**：客户端请求服务器代为更新正向（A / AAAA）记录，PTR 由客户端自己负责。
- **N**：客户端明确要求服务器**任何** DNS 更新都不要做；N 与 S 互斥。
- **O**：服务器告知客户端，它覆盖了客户端原本的 S 意图（服务器策略优先）。

其余标志位（含域名编码方式）与精确位序见官方资料。S/N/O 共同决定这条租约会不回落到 [RFC 2136] 的 DNS UPDATE 上，也就是第 25 章 DDNS 的入口。这里只强调一件事：**option 81 是"客户端自报名字"进 DNS 的那道门**，下一节的安全问题全部发生在这道门上。

把 option 42 放进 DNS 章不是凑数。AD 集成 DNS 的安全动态更新走 Kerberos / GSS-TSIG，票据对时钟偏差有硬约束，偏差超过 5 分钟即失败；DNSSEC 的 RRSIG 有明确的生效与过期时间，验证器本机时钟错了会把有效签名判成过期、把尚未生效的签名判成 bogus，最终表现为一片 SERVFAIL（第 10 章）；跨设备排查时，dnstap、DHCP 日志、DNS 日志要能按时间对齐（第 31 章）。DHCPv6 侧的 option 56（[RFC 5908]）同理，v6-only 客户端没有 NTP 源时，动态更新与 DNSSEC 会一起坏，且症状看起来像"DNS 挂了"而不是"表没对上"。

### option 252 与 v6 侧的编号空间

option 252 只是把 PAC 文件的 URL 塞进 DHCP 应答，草案从未成为 RFC，也不在 [RFC 2132] 的正式 option 表里，属于 IANA 私有/保留段；五种发现机制、`wpad` 这个名字的归属边界、以及 DNS devolution 越出组织的安全史都在第 23 章，放进 option 体系里占一个位置：它和 15 一样，是"名字/位置"而非"解析器地址"。

DHCPv6 的 23 / 24（[RFC 3646]）在语义上就是 v6 版的 6 / 119，56（[RFC 5908]）是 v6 版的 42；25（IA_PD）负责前缀委派，条文见 [RFC 8415] 一类，第 18 章已讲，这里只一句带过。要留意的是：**23/24 与 RA 的 RDNSS/DNSSL 是并行通道**，不是互为备份，下一节专门处理这个冲突。

## RDNSS 与 DHCPv6 的优先级战争

IPv6 侧最反直觉的一点是：DNS 配置有两条完全独立的下发通道。[RFC 8106] 定义的 RA 选项（RDNSS 给地址、DNSSL 给搜索域）由路由器在邻居发现阶段周期性广播；[RFC 3646] 的 DHCPv6 option 23/24 由 DHCPv6 服务器随租约下发。两条通道都合法、都能单独工作，但标准并没有规定客户端同时收到两者时该怎么合。

### 主机怎么合并两路 DNS

合并策略是实现细节，各系统不一样：有的以 RA 为准、DHCPv6 只作补充；有的把两路地址拼接成一张列表；有的按接口维护"路由域"（routing domain），哪个名字走哪条链路取决于后缀匹配；还有的以后到的消息覆盖先到的。systemd-resolved、Windows、macOS 的具体行为与版本相关，见官方资料，不要凭一次抓包就当成通用结论，也不要把某一次观测写成实现承诺。

更麻烦的是生命周期不同步：RDNSS 带自己的 Lifetime，到期就失效；DHCPv6 的 23/24 跟着租约的 T1/T2 走。于是两边刷新节奏天然错开，即使某一刻恰好一致，下一刻也可能漂移。这也解释了第 19 章为什么强调 hop limit 255、SLLAO、`RDNSS lifetime=0` 这些细节——RA 那条通道是要靠参数**主动管理**的，不是发出去就稳定。

### 为什么不能两边各发一套

第 19 章的结论是：RA 只广告网关自己的 ULA 解析器地址，并用 `RDNSS lifetime=0` 压掉光猫/上级广播进来的 DNS，从而做到"全屋无污染"——所有查询都经过本地 Unbound 的过滤、验证与缓存。在这个前提下发两套不同地址，等于把这个前提拆掉：

- **结果不确定**。同一间屋子里，A 主机可能取 RA 的 ULA 解析器，B 主机可能取 DHCPv6 23 里的上级解析器，C 主机可能把两者拼接后按某种顺序重试。哪一个赢取决于实现与消息到达顺序，无法通过服务端配置固定。
- **策略被绕过**。凡是落到上级解析器的那部分流量，本地过滤表、DNSSEC 验证、QMIN、加密上游、dnstap 观测全部落空，而且客户端没有任何报错——它只是"能上网"。
- **故障排查失去单一事实来源**。第 5 章反复强调转发器只留一个上游；这里同理，DNS 入口必须只有一个可指认的来源，否则"到底查了谁"要逐台主机抓包才能回答。
- **与搜索域叠加放大**。若 RA 的 DNSSL 与 DHCPv6 24 各给一份后缀，合并后列表更长，配合 `ndots`（第 20 章）放大倍数进一步上升。

还有一层容易被忽略：v4 与 v6 是两套独立的下发通道，双栈主机同时持有 option 6 与 RDNSS/DHCPv6 23。理想状态下它们应当指向同一台本地解析器；若 v4 侧给了 `192.0.2.53`、v6 侧给了另一个地址，那么"同一个域名走哪条协议族"就会变成谁拿到 DNS 答案的决定因素，而选哪条地址又是 RFC 6724 地址选择的事（第 18 章）。症状是间歇性的过滤失效：同一台主机，有时命中本地过滤表，有时没有，和域名本身无关。**双栈环境下，option 6 与 v6 侧来源必须一起看**。

所以工程上的做法不是"两边都配上更保险"，而是**选一条通道作为唯一来源**：按第 19 章用 RA 广告 ULA 解析器，DHCPv6 就干脆不下发 23/24（`dhcpd6.conf` 里注释掉），或者两边填**完全相同**的同一个地址并接受它只是冗余而非独立配置。本章后面的 `dhcpd6.conf` 片段采用前一种。

## 租约时序陷阱

[RFC 5625] §5.3 描述的是一台家庭网关开机时最容易踩、又最难复现的问题。WAN 侧还没建立时，网关上的 DHCP 服务器已经开始给 LAN 客户端发租约；此刻它还不知道上游 DNS 是什么，只能把**自己**填进 option 6，靠本机 DNS 代理顶着。等 PPPoE / WAN 侧 DHCP 客户端把链路拉起来、网关从上游学到真正的 DNS 地址后，服务器这边的数据变了，但已经拿到租约的客户端不会主动重问——DHCP 是"服务器推送、客户端按 T1 续期"的模型，配置变更不会反向通知。于是客户端继续把查询发给那个尚未就绪的代理，直到下一次续期才更新。

观察到的现象很有迷惑性：开机后头几十秒到几分钟，`dig` 超时或 SERVFAIL，过一阵子自己就好了；`resolvectl dns` 从头到尾显示的都是同一个网关地址，看不出哪里变了。这正好和"DNS 服务没起来"混淆，容易把人引去重配 Unbound，而真正的问题在租约时序上。

[RFC 5625] §5.3 给出的缓解是**短租约**（例如 60 秒量级），让 T1 尽快到来，把不一致窗口压到可接受范围；代价是 DHCP 与续期流量变多，在小规模 LAN 里通常可以接受。另一个更干净的思路是从设计上消除变更：option 6 始终指向网关自身的 DNS 代理，地址永不改变，上游怎么换都由代理内部消化——这本来就是 [RFC 5625] 讨论 DNS 代理的初衷。两条路可以叠加：短租约兜底，稳定的代理地址治本。

```conf
# /etc/dhcp/dhcpd.conf 片段：把不一致窗口压短
default-lease-time 60;
max-lease-time 60;
```

- ① 为什么这么设：T1 约为租约的一半，60 秒租约让 WAN 就绪后的最长失配窗口落在几十秒量级；仅在启动阶段的过渡网段使用。
- ② 怎么验证：`dhcpd -t -cf /etc/dhcp/dhcpd.conf && echo OK`，再到客户端看 `resolvectl dns` 与实际 `dig +short example.org @192.0.2.1` 的恢复时间点。
- ③ 失败模式 / 回滚点：租约过短会让续期流量与服务器日志明显变多，WAN 抖动时还可能反复触发重配置；回滚为 `default-lease-time 600` / `max-lease-time 3600` 并 reload，客户端会按新值在下一次续期收敛。注意改配置不会立即改写已有租约——这本身就是本节要讲的陷阱。

## option 15 / 119 的污染

厂商固件爱给 LAN 客户端塞一个"看起来贴心"的默认后缀。它可能是自造的 `.lan`、`.local`，也可能是运营商标配的域名。客户端存根解析器拿到后，会把不带点的裸名——以及在第 20 章 `ndots` 语义下**连绝对域名**——逐个追加后缀再查一次。这些后缀绝大多数不是有效 TLD，于是查询一路出网打到根服务器，换回一片 NXDOMAIN。[RFC 5625] §5.2 原文就点名了这类"大量无效 TLD 查询打根服务器"的后果：不是安全事件，是全体递归基础设施替一份没必要的固件默认值买单。

放大系数很容易估：一个 119 列表有 3 个后缀，`ndots` 让一个原本该一次命中的名字先试 3 次带后缀的组合，再加绝对名本身，单次访问就是 4 次查询；若 v4 的 119 与 v6 的 24 又各给一份，列表还能更长。对本地来说是无谓的延迟和日志噪声，对上游来说是被放大的无效负载，对排查来说是一堆同后缀 NXDOMAIN 把真正的故障信号淹掉。

排查顺序建议固定下来：

```bash
# 1) 客户端：看是否被强加了搜索域（systemd-resolved 环境）
resolvectl domain
# 2) 看当前生效的上游是不是自己期望的那一个
resolvectl dns
# 3) 用一个绝对域名（注意末尾的点）确认解析器本身可用
dig +short example.org. @192.0.2.53
# 4) 解析器侧：查 dnstap / 日志里以可疑后缀结尾的 NXDOMAIN 是否成片
```

- ① 为什么用这几条：把"DHCP 下发了什么"与"解析器本身能不能用"拆成两个独立判断，避免一上来就改 Unbound 配置。
- ② 怎么读输出：第 1 步只要出现非预期的后缀，基本可以断定是 DHCP（或 RA 的 DNSSL）塞进来的；第 3 步带尾点是为了**绕开**搜索域追加。第 4 步的成片 NXDOMAIN 是判定污染范围最直接的信号，可喂给第 31 章的告警规则。
- ③ 失败模式 / 回滚点：直接删掉 15/119 后，依赖裸名互访的旧脚本会解析不到——这是删后缀最常见的回归。回滚点是保留 `home.arpa.` 这**一个**专用后缀，并把依赖裸名的名字改成显式带点的形式；不要靠再加更多后缀去"补救"。

顺带一提：`.local` 归 mDNS（第 27 章）使用，把它当普通单播后缀追加，查询行为会和组播解析抢同一批名字，症状比单纯的 NXDOMAIN 更乱。

把常见症状与交接面上的具体环节对上，可以少走很多弯路：

| 症状 | 优先怀疑的环节 | 确认动作 |
|---|---|---|
| 开机后短暂全超时，过一会自愈 | 租约时序([RFC 5625] §5.3) | 看租约剩余时间与 WAN 建立时间是否重叠 |
| 本地过滤表对某些主机不生效 | 多条 DNS 来源或上层覆盖 | 逐台比对 `resolvectl dns` |
| 成片后缀相同的 NXDOMAIN | 15 / 119 / DNSSL 污染 | `resolvectl domain` + dnstap QNAME 分布 |
| 少数域名间歇性解析失败 | 双栈两侧来源不一致或 `ndots` 放大 | 分别用 `-4` / `-6` 各测一次 |
| 动态更新失败但 DNS 本身正常 | option 42 / 56 时钟、S/N/O 配置 | `timedatectl timesync-status` |
| 带尾点的绝对名正常、裸名异常 | 后缀追加，而非解析器故障 | `dig example.org.` 与不带尾点对比 |

最后一行是最快的一个分水岭：带尾点能通、不带尾点不通，问题一定在后缀追加或搜索域，不必再去查 Unbound 的上游、缓存或 DNSSEC 状态。反过来，带尾点也不通，就与本章的 option 无关了，该回到第二篇的角色配置去查。

## option 81 与动态更新注入的攻防

这一节只写机理与防守，不提供任何伪造报文、构造 option 或注入记录的可复制流程；任何验证都只能在自己有书面授权的隔离实验网段进行（纪律见第 34 章）。

### 机理止于这一层

微软 DHCP 与 AD 集成 DNS 的 "DHCP DNS Dynamic Updates" 组合里，DHCP 服务器可以**以自身凭据**代客户端向 DNS 发起 [RFC 2136] 更新，好让客户端不用各自持有写权限。触发这条路径的输入，正是 option 81 里客户端自报的 FQDN。若服务器对"这个名字是否属于该客户端"不做归属校验，就出现一个结构性问题：一个自报的名字可能被写成一条正式的 A / AAAA 记录，落在内网权威区里。

攻击者把名字选成 `wpad` 或能被通配匹配到的形式时，这条记录就与第 23 章的 WPAD 名称解析叠加，形成名称劫持面；这与第 25 章 DDNS、第 29 章暴露面自查是同一条链上的三个观察点。Akamai 2023 的《Weaponizing DHCP DNS Spoofing》与 TrustedSec 2021 的《Injecting Rogue DNS Records Using DHCP》都公开分析过这条机理，本书只引用其公开的结论，不复刻流程、不列工具、不给步骤、不写报文字段序列。

关键在于信任边界：DNS 更新请求看起来来自"可信的 DHCP 服务器"，而服务器只是转述了一个未经证实的客户端自报值。**凭据的可信不等于名字的可信**。这一点也解释了为什么 option 81 不该被当成"只是给客户端起个名字"的普通字段。

### 防守清单

- **Name Protection / DHCID**：把 DNS 记录与 DHCP 租约绑定，用 DHCID 记录（名称与编号按官方资料检索）标记归属，使别的客户端不能覆盖已有名字。
- **DHCP 专用低权限凭据**：代更新用的账号只授予必要的更新权限，不要用域管理员级凭据；凭据泄露时爆炸半径限定在一小片区。
- **Global Query Blocklist**：Windows DNS 侧的全局查询阻断列表默认包含 `wpad` 等敏感名字，保持启用并按需补充，别为了"让 WPAD 好用"把它关掉（第 23 章）。
- **预置占位记录**：对 `wpad`、`isatap` 一类高价值名字预先建立受控的正式记录，让动态更新无法抢占已存在的名字。
- **DNS 更新 ACL**：区与记录两级限制谁能更新什么，把代更新范围收敛到明确的区与名字集合。
- **交换机端口安全 / DHCP snooping**：只让授权端口能进 DHCP 服务器应答，压缩伪造租约进入的入口（见下一节）。
- **审计与观测**：监视非租约来源的名字更新、敏感名字的新增记录、以及同一名字在短时间里被不同客户端改写；信号进第 31 章告警。

这些措施并不互相替代，它们分别封住四个不同环节：端口安全 / snooping 管"谁能发租约"，Name Protection / DHCID 与更新 ACL 管"哪个名字能写"，低权限凭据管"写坏了能坏到哪里"，Global Query Blocklist 与占位记录管"最敏感的那几个名字根本不能被抢"。只做其中一条，其余环节仍会漏。

时间同步（option 42 / 56）在这里也有防守价值：安全动态更新与 GSS-TSIG 依赖可用时钟，把 NTP 源纳入受控范围，本身就是收紧更新链的一环；反过来，若日志无法按时间对齐，"先有租约还是先有更新"这个关键归因就做不出来。

### 现象层：不靠攻击复现也能自查

防守方不必也没有必要去复现注入流程，只看结果就够了：

- 权威区里出现与任何已知租约都不对应的 A / AAAA 记录；
- 敏感名字（`wpad` 等）出现了未预期的记录，或占位记录被改写；
- 同一名字短时间内被不同客户端反复更新；
- DNS 更新日志里出现来源与 DHCP 服务器绑定表不一致的条目；
- 一批名字同时指向同一个陌生地址，且 TTL 与正常租约节奏不符。

把这些做成定期比对（租约绑定表 ↔ 权威区记录 ↔ DNS 更新日志）即可，也就是第 29 章资产自查的思路在交接面上的具体化。发现异常先按变更流程回滚占位记录与更新 ACL，不要在不清楚归属前批量删记录。

## rogue DHCP 与 DHCPv6 假 DNS

假 DHCP 服务器应答 DISCOVER / SOLICIT，把 option 6（或 v6 的 23）指向攻击者控制的解析器，是经典的内网劫持：客户端全程无报错，只是查询都被别人看见了，且本地过滤、DNSSEC 验证、加密上游一并被绕过。v6 侧还有一条更隐蔽的路径——伪造 RA 塞进 RDNSS，效果相同且不依赖 DHCP 服务器存在。第 34 章从对手视角看这条链，本节只落防守，不展开任何伪造或投毒的操作序列。

防守依赖二层而非 DHCP 本身：

- **DHCP snooping / DHCPv6 Guard**：交换机把端口分成 trusted 与 untrusted，只在 trusted 口接受 OFFER / ACK / REPLY，并维护租约绑定表；非授权应答在入端口就被丢弃。
- **RA Guard**：过滤非授权端口发出的 RA，避免 RDNSS / DNSSL 绕过 snooping 单独下发（规范按名称在 RFC Editor 检索）。
- **端口安全 / 802.1X**：限制端口上可出现的 MAC 与设备数量，减少私接小路由的机会。
- **客户端侧核对**：把"当前生效的 DNS 是谁"做成常规巡检项，出现陌生上游、多个 OFFER、option 6 与预期不符即告警；`resolvectl dns` 与 dnstap 里的异常 QNAME 分布都是可用的信号（第 31 章）。

这些控制与第 19 章压制上级 DNS 是互补关系：RA Guard / snooping 保证"只有我发的算数"，RDNSS 参数保证"我发的是本地解析器"，两者缺一，另一方都能被绕过。

## 教学配置片段（全部文档地址段）

下面几段都是教学骨架，不是生产模板。所有地址取自 RFC 5737 文档段与 `2001:db8::/32`，域名用 `example.net` / `home.arpa.`，主机名 `gw-01` 等仅为示意。**option 15 与 119 一律注释掉**——按 [RFC 5625] §5.2，未配置就不要发，这本身就是正确配置。

### ISC dhcpd：option 6 / 15 / 119

```conf
# /etc/dhcp/dhcpd.conf
authoritative;
default-lease-time 600;
max-lease-time 3600;

subnet 192.0.2.0 netmask 255.255.255.0 {
    range 192.0.2.20 192.0.2.200;
    option routers             192.0.2.1;    # gw-01（示意）
    option domain-name-servers 192.0.2.53;   # option 6：本地递归解析器
    # option domain-name       "home.arpa."; # option 15：未配置就不要发
    # option domain-search     "home.arpa."; # option 119：未配置就不要发
    option ntp-servers         192.0.2.123;  # option 42：时间同步
}
```

- ① 为什么这么设：option 6 只给一个本地解析器，避免第 5 章"多上游竞速"把查询送到不该去的地方；15/119 注释掉，避免查询放大与无效 TLD 查询；42 保证 Kerberos / GSS-TSIG 与 DNSSEC 验签有可用时钟。option 119 的 `domain-search` 压缩编码声明与 Kea 的写法不同，按名称在官方手册检索，不要手写字节序列。
- ② 怎么验证：`dhcpd -t -cf /etc/dhcp/dhcpd.conf && echo OK`；客户端 `resolvectl dns` 应只列出 `192.0.2.53`，`resolvectl domain` 应为空或只含预期后缀。
- ③ 失败模式 / 回滚点：误打开 15/119 会出现成片无效 TLD 查询；回滚＝重新注释两行、reload 服务，并留意已有租约要等 T1 才收敛（正是本章"租约时序陷阱"）。若要临时恢复裸名互访，只加 `home.arpa.` 一个后缀，不要堆列表。

### Kea：同一组 option 的等价写法

```json
{
  "Dhcp4": {
    "interfaces-config": { "interfaces": [ "eth0" ] },
    "valid-lifetime": 600,
    "subnet4": [
      {
        "subnet": "192.0.2.0/24",
        "pools": [ { "pool": "192.0.2.20 - 192.0.2.200" } ],
        "option-data": [
          { "name": "routers",              "data": "192.0.2.1" },
          { "name": "domain-name-servers", "data": "192.0.2.53" },
          { "name": "ntp-servers",          "data": "192.0.2.123" }
        ]
      }
    ]
  }
}
```

- ① 为什么这么设：与 ISC dhcpd 保持同一意图——只下发 option 6，`domain-name`（15）与 `domain-search`（119）**故意不出现在 `option-data` 里**；Kea 未配置的 option 不会凭空编一个默认值，这正是 §5.2 想要的行为。
- ② 怎么验证：`kea-dhcp4 -t /etc/kea/kea-dhcp4.conf` 做配置自检；字段名、code 与 `csv-format` 的取值以 Kea 官方手册的内置 option 定义为准（见官方资料），不要照抄臆造的类型。
- ③ 失败模式 / 回滚点：手写 `code` / `space` 不匹配会导致启动自检失败或下发空 option；回滚＝还原备份的 JSON，自检通过后再 reload。若确需 119，先在隔离网段用 `csv-format` 验证客户端对压缩编码的支持，再决定是否下发。

### dhcpd6.conf：23 / 24

```conf
# /etc/dhcp/dhcpd6.conf
default-lease-time 600;
preferred-lifetime 300;

subnet6 2001:db8:1::/64 {
    range6 2001:db8:1::100 2001:db8:1::200;
    option dhcp6.name-servers 2001:db8:1::53;   # option 23
    # option dhcp6.domain-search "home.arpa.";   # option 24：未配置就不要发
}
```

- ① 为什么这么设：按上一节的结论，**v6 侧只保留一条 DNS 来源**。这里给出 23 是为了演示写法；若 LAN 已按第 19 章用 RA 广告 ULA 解析器，就把 23/24 一并注释掉，只由 RA 负责，避免两侧各发一套。option 56（[RFC 5908]）的内置写法见官方手册，本片段不臆造指令名。
- ② 怎么验证：`dhcpd -6 -t -cf /etc/dhcp/dhcpd6.conf && echo OK`；客户端 `resolvectl dns` 只应出现**一个**来源，且 v4/v6 两侧指向同一台解析器。
- ③ 失败模式 / 回滚点：23 与 RA 的 RDNSS 各发不同地址时，主机合并策略不确定、部分流量绕过本地策略（本章"优先级战争"）；回滚＝注释 23/24、统一由 RA 下发，或两边填完全相同的地址。IA_PD（option 25）不在本片段内，前缀轮换的处理见第 18、19 章。

### 客户端侧校验

```bash
# 谁在下发 DNS、下发了什么
resolvectl dns
resolvectl domain
# 时间源与偏差（option 42 / 56 是否真的生效）
timedatectl timesync-status
chronyc tracking
# 解析器本身是否可用（尾点绕开搜索域追加）
dig +short example.org. @192.0.2.53
# v6 侧前缀与地址是否符合预期
ip -6 addr show
```

- ① 为什么用这几条：把四组字段（6、15/119、42/56、IA_PD 的间接影响）各留一个可当场确认的观测点，一次巡检就能定位交接面在哪一段断了。
- ② 怎么读输出：Windows 侧用 `ipconfig /all` 看 "DNS Servers" 与 "DNS Suffix Search List"，macOS 侧查系统配置里的搜索域；命令形态按名称在官方资料检索，本书不逐平台展开。`resolvectl dns` 出现陌生上游时先怀疑 rogue DHCP 或两侧通道冲突，而不是先改 Unbound。
- ③ 失败模式 / 回滚点：这套命令只观测、不改写配置，回滚无风险；但要注意它反映的是**当前生效值**，租约未续期前可能与服务器新配置不一致，务必结合 T1 时间点判读。

## 本章要点

- **option 6 决定查询去哪、15/119 决定名字被追加几次、81 决定动态更新由谁做、42/56 决定这套机制有没有可信时钟**；四组字段都不是"DNS 服务器配置"，却先行决定了 DNS 行为。
- **[RFC 5625] §5.2 的默认应是空**：没有标准的 `local` 后缀，未配置就不要发 option 15 / 119；固件默认值会造成成片无效 TLD 查询打根服务器，并与 `ndots`（第 20 章）叠加放大。
- **v6 侧只留一条 DNS 来源**：[RFC 8106] 的 RA 选项与 [RFC 3646] 的 DHCPv6 23/24 并行且主机合并策略不一，各发一套必然让部分客户端绕过本地策略；按第 19 章用 RA 广告 ULA 解析器即可。
- **租约是推送模型**：WAN 建立后上游 DNS 变了，客户端要等 T1 续期才感知（[RFC 5625] §5.3）；短租约压窗口，稳定的 DNS 代理地址治本。
- **option 81 的自报 FQDN 是信任边界**：凭据可信不等于名字可信；防守靠 Name Protection / DHCID、低权限凭据、Global Query Blocklist、占位记录、更新 ACL 与二层 DHCP snooping / RA Guard，本书只写机理与防守。
- **改了 DHCP 配置不等于改了客户端**：排查"DNS 忽然好了/坏了"先看 `resolvectl dns` 与 `resolvectl domain`，再动 Unbound。
