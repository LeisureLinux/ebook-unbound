# DNS 基础与主流实现横评

一台递归解析器上出现的"解析失败"，可能来自命名空间里的任何一层：本地存根解析器没发出去、缓存里有一条过期的 NXDOMAIN、委派链上某一级给了不该给的 glue、CNAME 链断了、EDNS 通告的缓冲大小导致分片被丢。不把 DNS 的数据模型和解析全过程先讲透，后面所有的加固配置都会变成"照抄参数但不知道在防谁"。

本章前半部分是通用入门，与具体产品无关；后半部分是横评，按角色和取舍对照，重点放在用户最容易混淆的 BIND 与 dnsmasq 上。全章不贴长配置块，配置属于第二篇起的内容。

## 命名空间、委派与区域

### 一棵倒过来的树

DNS 的命名空间是一棵树，根（root）写作 `.`，往下依次是顶级域（TLD，如 `org`）、二级域（如 `example.org`）、以及更下层的名字。完整域名（FQDN）从最具体的标签一路写到根，例如 `www.example.org.`，末尾那个点表示根；日常书写常省略最后一个点，但**在配置文件里省略与不省略语义不同**，这是运维踩坑的高频来源之一。

每个标签最长 63 字节，完整域名总长不超过 253 字节（wire 格式下的常见表述）。这里先交代 **wire format**：它指 DNS 报文在**线路上传输时的二进制格式**，由 [RFC 1035] 定义——固定 12 字节报文头（ID / 标志 / 各段计数）+ question / answer / authority / additional 四段，名字用「长度字节 + 标签」的编码，类型与类别用数字而非文本。「同一份 DNS wire format 装在 UDP/53、TCP/53、DoT、DoH 里」指的就是这一串字节；DoH 只是换了个外壳，HTTPDNS（第 37 章）则连这串字节都没有。名字不区分大小写，但 wire 报文会保留查询名的大小写——这一性质后来被 0x20 编码用作额外的熵来源，第 1 章提到过。

树上的每个节点可以拥有一组**资源记录（resource record, RR）**。相同名字、相同类型、相同类别的记录组成一个 **RRset（resource record set，资源记录集）**，RRset 是缓存与 DNSSEC 签名的基本单位，不是单条记录。理解这一点很重要：TTL 作用于 RRset，签名也覆盖整个 RRset；"一条 A 记录过期了"严格说应是"这个 A RRset 的 TTL 到了"。

**RRset 举例**（这是最常见的一处误解）：针对 `www.example.org.` 查到一条 A 记录和一条 AAAA 记录，它们**不是同一个 RRset**——类型不同（A / AAAA）、名字类别相同，但 RRset 按 `(owner, type, class)` 划分，所以是两个 RRset：A RRset 与 AAAA RRset，各自有各自的 TTL 与 RRSIG。同理 MX 记录是**另一个** RRset；一个 MX RRset 里可以有多条 MX 记录（不同优先级），它们共享一个 TTL、被**一条** RRSIG 整体签名。`www.example.org.` 若有两条 A 记录（例如 `192.0.2.10` 与 `192.0.2.11`），这两条才属于**同一个** A RRset。缓存里刷 `www.example.org A` 只会淘汰 A RRset，不会动 AAAA / MX。

### 区域与委派

**区域（zone）**是命名空间里由同一管理者负责、并被作为一个单元维护的连续部分。区域与域（domain）不是同义词：一个域可以包含多个区域，因为其中某些子树被委派给了别人。

**委派（delegation）**发生在父区域里：父区域用 NS 记录声明"这个子树由这几台权威服务器（authoritative server）负责"。例如 `org` 区域里为 `example.org` 写入 NS 记录，就把 `example.org` 及其以下的名字交了出去。负责该子树的服务器称为该区域的权威服务器，它给出的应答在报文里带 **AA（Authoritative Answer）** 标志。

委派带来两个必须记住的推论：

- 父区域**不负责**子区域里的具体记录，它只知道"去问谁"；因此父区域的数据变了，子区域的记录不会自动跟着变；
- 权威服务器只对**自己被委派的区域**有权威。一个应答里夹带了不属于自己区域的记录，就是典型的越界数据，解析器必须能识别并丢掉。第 1 章说的清理器（scrubber）与 `harden-glue` 处理的正是这一类：域外夹带的 glue 是经典缓存投毒面，且**它与 DNSSEC 无关**，任何模式都该开。

### 胶水记录：委派的自举问题

如果 `example.org` 的 NS 记录写的是 `ns1.example.org`，那么要查 `ns1.example.org` 的地址，又得先问 `example.org` 的权威服务器——形成循环。解决办法是：**父区域在委派应答的附加段（additional section）里，一并给出这些 NS 名字的 A / AAAA 记录**，这些记录就叫**胶水记录（glue record）**。

胶水记录有两条性质，直接决定了它的风险：

1. 它**不是权威应答**。父区域给的是"顺带提供的地址提示"，不是对该名字的权威数据；
2. 它位于附加段，历史上很多实现会不加分辨地把它写进缓存。

第 2 条就是缓存投毒的经典入口：伪造的应答里夹带一条指向攻击者地址的 glue，一旦被缓存，后续对该域的所有查询都会被导向攻击者。Unbound 的处理方式是只放行特定条件下的 glue（委派中出现、类型为 A / AAAA、名字确实出现在 authority 段的 NS 记录里），并且把它标记为"来自附加段"，不会作为对客户端的直接应答返回；对这个名字的直接查询会另走一遍解析，用来自 answer 段的权威数据覆盖它。

这段机制的实践含义是：**别把"有 glue 就能解析"当成理所当然**，也别把"开了 DNSSEC 就不用管 glue"当成结论。两者处理的是不同层面的问题。

## 递归与迭代：谁在替谁跑腿

### 两种查询模式

**递归查询（recursive query）** 的意思是：客户端把整个解析任务交给服务器，服务器要么给出最终答案，要么给出明确的失败，中间过程客户端不参与。报文里用 **RD（Recursion Desired）** 位表示"我希望你替我递归"；服务器用 **RA（Recursion Available）** 位回答"我提供递归服务"。

**迭代查询（iterative query）** 的意思是：被问的服务器不替你继续跑，只给出它知道的最好的答案——可能是最终记录，也可能是"我不知道，但你可以去问这几台"（ referral，指引应答）。递归解析器向根、TLD、各级权威服务器发出的，就是这种不带 RD 的迭代查询：每得到一次 referral，就换一台服务器再问，直到拿到答案或明确的不存在证明。

于是"递归解析器"这个名字其实描述的是**它对客户端的承诺**，而不是它对外的工作方式：对客户端它做递归，对上级它做迭代。第 3 章会把它拆成四种角色。

### 一次 `www.example.org` 的追踪


假设本机存根解析器把查询交给一台本地递归解析器，缓存为空：

1. **存根 → 递归解析器**：`www.example.org. A?`，带 RD。存根不打算自己问根，它要一个最终答案。
2. **递归解析器 → 根服务器**：`www.example.org. A?`，不带 RD。根不解析具体主机，返回对 `org` 的 referral：`org` 的 NS 列表与对应 glue。
3. **递归解析器 → `org` 的权威服务器**：同样问 `www.example.org. A?`，不带 RD。`org` 返回对 `example.org` 的 referral。
4. **递归解析器 → `example.org` 的权威服务器**：`www.example.org. A?`，不带 RD。这里可能出现三种结果：
   - 直接给出 `www.example.org` 的 A / AAAA RRset，带 AA；
   - 给出一条 CNAME，指向另一个名字，于是从第 4 步重新开始（CNAME 链见后文）；
   - 给出 NXDOMAIN 或 NODATA，表示名字不存在或该类型不存在（负缓存见后文）。
5. **递归解析器 → 存根**：最终答案，带 RA；若做了 DNSSEC 验证且签名链通过，还会带 **AD（Authenticated Data）** 位。

注意第 2、3 步：递归解析器每次都把**同一个完整查询名**发给上级，这正是查询名最小化（QNAME minimisation）要改掉的行为。它只减少发给上级的标签数，不加密报文；相关 RFC 的演进在第四篇第 17 章，本篇不展开。

### 追踪示例里的可观测点

真要排查时，`dig +trace` 能模拟这条迭代链，但它与真实递归解析器的行为有差别：`+trace` 是从**本机**逐级发问，不会经过本地缓存，也不会体现解析器自己的端口随机化、超时算法、验证与缓存策略。因此它适合看"委派链在哪一级断了"，不适合判断"我的解析器为什么返回 SERVFAIL"。

一条实用的分工是：

| 想看什么 | 看哪一层 | 常见误判 |
|---|---|---|
| 委派链是否完整、哪一级 NS 配错 | 逐级迭代追踪 | 把 referral 当成失败 |
| 本地解析器是否命中缓存、是否验证 | 解析器统计与应答标志位 | 只看 TTL 就以为数据新鲜 |
| 客户端实际拿到什么 | 从客户端发查询、看 RA/AD/状态 | 在服务器上测完就以为客户端一样 |

第三篇会给出可复制的验证命令；此处只需建立"链路上每一层都可能单独出问题"的直觉。第 5 章的故障案例里，同一个 NXDOMAIN 在链路上被层层缓存、层层刷不干净，就是这个直觉的实战版本。

## 资源记录、缓存与 TTL

### 常见记录类型

| 类型 | 作用 | 与本书加固的关系 |
|---|---|---|
| A / AAAA | 名字 → IPv4 / IPv6 地址 | 最常见的应答，也是过滤与改写策略的作用对象 |
| NS | 委派：该区域由哪些权威服务器负责 | referral 的核心，glue 依附于它 |
| SOA | 区域的起始授权记录，含序列号、刷新/重试/过期 timers、minimum TTL | 负缓存时长、区域传送与主备同步的依据 |
| CNAME | 名字的规范名别名 | 形成链，链上任一环失败整条失败 |
| PTR | 反向解析 | 日志与反查，不是本章重点 |
| MX / TXT / SRV / SVCB / HTTPS | 邮件路由、文本、服务发现等 | 现代客户端常查，`ndots` 放大时会一并出现 |

**SVCB 是什么**：SVCB 全称 **Service Binding**（服务绑定），定义在 [RFC 9460]。它是一条通用资源记录，用来在**发起连接之前**就告诉客户端「这个服务可以从哪些替代端点访问、各自带什么参数」——例如优先用 HTTP/3、端口是多少、可用的 IP hint、以及 TLS 相关配置。它还支持 `AliasMode`，能在区域顶点（apex）做别名，这是 CNAME 在 apex 上做不到的。**HTTPS 记录**是 SVCB 专用于 HTTP 的变体（[RFC 9460] 一并定义），浏览器查它来决定用不用 HTTP/2、HTTP/3、ECH。本书第 13 章的 DDR 压制要挡的 `_dns.resolver.arpa. SVCB`，正是借 SVCB 来「发现加密解析器」：客户端查一条 SVCB 就能拿到 DoT / DoH / DoQ 端点，所以本地解析器用 `always_nodata` 让它查不到。第 30 章讨论信任数据时会再回到 SVCB / HTTPS 的字段。
| DNSKEY / RRSIG / NSEC / NSEC3 / DS | DNSSEC 的密钥、签名、否认存在与委派签名 | 完整性/来源认证，与加密传输不是一回事 |
| OPT | 并非真实记录，是 EDNS(0) 的伪记录 | 通告 UDP 缓冲大小、携带选项（如 ECS） |

要特别区分 **DS** 与 **NS**：NS 把子树交给谁，DS 把父区域对子区域密钥的承诺写进父区域，两者共同构成 DNSSEC 的信任链。第 3 章讲 AD/CD 位时会再用到这个区分。

### 缓存与 TTL

每条 RRset 带一个 **TTL（time to live）**，单位是秒，表示"这份数据可以被缓存多久"。递归解析器命中缓存时，返回给客户端的 TTL 是**剩余** TTL，不是原始值——所以连续查同一个名字，看到的 TTL 会递减，这是正常现象，不是数据变了。

TTL 的本质是权威服务器与缓存解析器之间的契约：到期后就不该再用。[RFC 8767] 定义的**过期缓存应答（serve-stale）** 是对这份契约的有条件例外——刷不到新数据时可以暂用旧的，以提高韧性。Unbound 的 `serve-expired` 早于该 RFC 存在，官方手册标注 1.6.0 引入、1.11.0 引入 RFC 行为、1.23.0 起 RFC 行为成为默认。

这里有一个在实测中反复被读错的细节：`serve-expired-client-timeout` 的单位是**毫秒**（默认 1800，即 1.8 秒），语义是"先尝试刷新，超过这个时间才回过期缓存"，不是 1800 秒。把它当成 1800 秒，会得出完全相反的超时判断。

### 缓存的层级性

一次客户端查询背后往往不止一层缓存：浏览器或应用有自己的缓存，操作系统存根解析器可能有缓存，本地递归解析器有缓存，前面还可能串着转发器或节点级缓存。于是会有两个反直觉的后果：

- **缓存命中率不等于"权威侧健康"**：上游已经全断，本地仍可能靠缓存正常应答几十分钟；
- **故障修复不等于"客户端恢复"**：某一层缓存里存着旧的负面结果，修好权威后那一层仍会继续返回失败，必须逐层刷。

第 7 章讲多实例与可观测性时会把"链路上每个实例都要刷缓存"写成检查清单；本篇只建立模型：**缓存是分层的，任何一层都可能是你排查时漏掉的那一层**。

### 负缓存：不存在的东西也会被记住

[RFC 2308] 规定了**负缓存（negative caching）**：NXDOMAIN（名字不存在）与 NODATA（名字存在但没有该类型）也可以被缓存，时长取 SOA 记录里的 minimum 字段与 SOA 自身 TTL 中较小的一个，常见值是 3600 秒。

它的价值是挡住对不存在名字的重复查询；代价是**故障放大**。上游瞬时抖动返回一次 NXDOMAIN，权威侧恢复后客户端仍会失败整整一个负缓存周期。更麻烦的是，如果链路上串了多个实例，只刷最靠近客户端那一层没用——每一层都可能各自缓存了一份 NXDOMAIN。

负缓存与过期缓存应答于是构成一组对照：前者是"把失败记久一点"，后者是"把旧数据再用一会儿"。两者都改变 TTL 的字面语义，方向却相反。第五篇第 22 章的故障案例会把它们放在同一条排查链里。

### EDNS(0) 与 1232

原始 DNS 的 UDP 报文被限制在 512 字节，放不下带 DNSSEC 签名的应答。**EDNS(0)** 全称 **Extension Mechanisms for DNS (Version 0)**（[RFC 6891]），用一条伪记录 OPT 扩展了报文：客户端在 OPT 里通告"我能重组多大的 UDP 应答"，还可以携带各种选项（ECS 就是其中之一）。

通告值不是越大越好。Unbound 的 `edns-buffer-size` 当前官方默认 **1232**，来自 DNS Flag Day 2020 的推荐；把出向值调大到 1472，在 MTU 1280（IPv6 最小 MTU、部分隧道）或 PPPoE 1492 链路上会分片，分片被丢后表现是**等超时再重试 TCP**，而不是自动变小报文。同一份手册里 `max-udp-size` 也默认 1232，但它只管**入向**应答；把入向调小却指望出向不分片，是常见误判。

| 参数 | 方向 | 管什么 |
|---|---|---|
| `edns-buffer-size` | 出向 | 向权威服务器通告的重组缓冲大小 |
| `max-udp-size` | 入向 | 本实例返回客户端的 UDP 应答最大尺寸 |

EDNS 选项里还有一类与隐私直接相关的：ECS（[RFC 7871]）把客户端网段信息带给权威服务器以换取更近的 CDN 节点，代价是泄露客户端位置信息、并把缓存键从"查询名"变成"查询名 + 网段"。Unbound 把它做成显式白名单式的能力。

## CNAME 链与解析过程中的"重来一次"

**CNAME** 表示"这个名的规范名是另一个名"。解析器遇到 CNAME，必须**用新名字重新走一遍解析**，可能再次遇到 CNAME，形成链。链上任何一环失败，整个查询失败；链太长或出现环，会触发实现自己的上限与错误处理。

三个 practical 后果：

1. **CNAME 不能与同名的其他数据共存**（除少数 DNSSEC 相关记录外）。给 `www` 同时写 A 和 CNAME 是配置错误，不是"两条都生效"。
2. **CNAME 的目标可能在另一个区域、另一条委派链上**。所以一次"简单的 A 查询"可能触发两三轮独立的迭代。CDN 场景里尤其常见：站点域名 CNAME 到 CDN 提供的名字，而那个名字又在另一套权威体系下。
3. **查询名最小化的严格模式会咬人**。某些大型 CDN 的 CNAME 区违反 [RFC 8020]（父名返回 NXDOMAIN、子名却存在），`qname-minimisation-strict: yes` 会在中间层拿到 NXDOMAIN 就直接收工，不再回退完整查询名 → 整站 CSS/JS 全部解析失败。改回 `strict: no` 才恢复，**并且链路上每一层缓存都要刷**，否则前一层照样返回缓存的 NXDOMAIN。参数与兼容坑在第三篇第 13 章，这里只解释为什么"一条 CNAME"能引发整站故障。

CNAME 链也解释了为什么"解析全过程"不能只画一次直线：它是一条可能分叉、可能回头、可能在任意一层命中缓存的图。第 3 章把这张图按角色切成四段，就是为了定位"到底哪一段出了问题"。

## 主流实现横评

### 先定角色，再看产品

比较 DNS 软件时最常见的错误，是拿不同角色的产品互比"谁更快、谁更安全"。一台权威服务器和一台存根解析器没有可比性。先把五种角色列清楚：

| 角色 | 做什么 | 对谁提供递归 |
|---|---|---|
| 权威 | 只对自己被委派的区域给出权威应答 | 不提供 |
| 递归（验证） | 自己从根开始迭代，缓存并验证 | 提供，且通常是最终信任边界 |
| 转发 | 把查询整体交给指定上游，自己不做完整迭代 | 视配置，可能只是代理 |
| 缓存 | 主要靠缓存应答，减少上游查询 | 视配置 |
| 存根 | 把查询交给别处，自己不迭代 | 不提供 |

一个产品可以覆盖多个角色（BIND 9 几乎全覆盖），也可以只做其中一个（NSD 只做权威）。**"全能"不是优点也不是缺点，它是取舍**：功能集中省机器，配置面与故障半径同时变大。

### 总对照表

下表中的"强 / 中 / 弱"是相对定位，用于建立选型直觉，不是基准测试结论；具体能力以各项目官方文档的当前版本为准。

| 实现 | 主要角色 | DNSSEC 验证 | 加密传输 | 过滤能力 | 配置复杂度 | 资源占用 | 典型场景 |
|---|---|---|---|---|---|---|---|
| BIND 9 | 权威 + 递归 + 转发 + 缓存 | 完整（并支持权威侧签名） | 支持 DoT 等能力，见官方手册 | view / RPZ 等，能力强 | 高 | 中–高 | 企业级权威与递归一体、复杂策略 |
| dnsmasq | 转发 + 缓存 + DHCP | 可作为验证器但通常弱/可选 | 依赖上游，自身不主攻 | 基于域名与地址的基础过滤 | 低 | 极低 | 家庭网关、嵌入式、小型网络 |
| CoreDNS | 权威（插件）+ 转发 + 服务发现 | 依赖插件 | 依赖插件 | 依赖插件 | 中（插件链） | 低–中 | Kubernetes 集群内服务发现 |
| NSD | 权威 | 权威侧签名，不做递归验证 | 不涉及递归侧 | 不涉及 | 中 | 低 | 只做权威、追求精简 |
| PowerDNS Recursor | 递归 + 缓存（+ 转发） | 支持 | 支持，见官方手册 | 脚本与策略较强 | 中 | 中 | 运营商/大型递归、需要脚本化策略 |
| PowerDNS Authoritative | 权威 | 权威侧 | 不涉及递归侧 | 不涉及 | 中 | 中 | 多后端权威、数据库驱动 |
| Knot Resolver | 递归 + 缓存 + 转发 | 支持 | 支持 | 模块化策略 | 中–高 | 低–中 | 模块化、偏好 Lua 策略的递归 |
| systemd-resolved | 存根 + 缓存 + 转发 | 有限，依系统策略 | 支持部分加密上游 | 弱 | 低（但与其他解析器共存易冲突） | 极低 | 桌面/主机本地存根 |
| Unbound | 递归（验证）+ 缓存 + 转发 + 可作库 | 默认验证，信任锚就位时真验证 | 下游 DoT/DoH/DoQ、上游加密 | 本地策略 + RPZ | 中 | 低 | 自建递归验证、按角色拆实例 |

**读表时请注意两点**：一是"支持"不等于"默认开启"，例如 DNSSEC 验证在有无信任锚时行为完全不同（第 1 章的三种状态）；二是"加密传输"列只说明能力覆盖，**DNSSEC = 数据完整性/来源认证，DoT/DoH/DoQ = 传输加密/隐私**，两者不能互相替代，也不能用其中一项的勾选去推断另一项已生效。

### 按维度展开的取舍

**配置复杂度。** BIND 9 的配置文件有 view、ACL、zone、options、日志通道等大量结构，一项策略常常要同时改几处；dnsmasq 一个文件加几个命令行参数就能跑，但要把"哪个客户端用哪套过滤表"表达清楚就吃力；Unbound 介于两者之间，配置以 `server:` / `forward-zone:` / `local-zone:` / 模块声明为主，边界清楚。CoreDNS 用插件链表达，灵活但插件顺序本身就是语义。

**DNSSEC 验证。** 需要区分"能做验证"和"默认真的在验证"。BIND 9、Unbound、Knot Resolver、PowerDNS Recursor 都具备完整验证能力；dnsmasq 与 systemd-resolved 在这条链上更依赖上游或系统策略，因而在本书的威胁模型里通常不被当作最终验证边界。NSD 与 PowerDNS Authoritative 属于权威侧，不参与递归验证。第三篇第 10 章会把信任锚、放行与拒绝展开成可验证的状态。

**加密传输。** 这里也要分两段看：客户端到解析器的一段（下游 DoT/DoH/DoQ），以及解析器到上游的一段（加密上游）。浏览器可能自己启用 DoH 而绕过本地解析器，这是第五篇讨论 DDR 压制时的核心问题；而一台本地递归解析器向权威服务器发出的迭代查询，通常仍是明文 53。把"我开了 DoH"当成"整条链路都加密了"是典型误判。

**过滤能力。** dnsmasq 的过滤面向"家用够用"：按域名屏蔽、按地址改写，表达力有限且可观测性弱；BIND 的 RPZ 与 view 能承载复杂策略；Unbound 有 `local-zone` / `local-data` / `respip` 与 RPZ（官方手册标注 1.10.0 初版、1.14.0 补齐完整触发器与动作）。过滤越强，越要明确它作用于哪个信任域，否则"误拦"与"绕过"会同时出现。

**可观测性与资源占用。** dnsmasq 与 systemd-resolved 占用极低，但日志与统计粒度也有限，排查"为什么这个域 SERVFAIL"时常常要换工具；BIND 与 Unbound 都有统计与查询日志能力，代价是多占一点内存与运维注意力。需要全量查询日志时，还要明确保留期——dnstap 是自己的查询流副本，无期限保留会在自家门口把"抗元数据聚合"破功。

## 重点对照：BIND 与 dnsmasq

用户最容易在这两者之间做错选择，因为它们常被放在同一台"网关"上讨论，但实际面向的场景完全不同。

### BIND 9：全能的代价

**强在哪。** 权威与递归一体、view 能按来源给出不同视图、ACL 与日志通道细、RPZ 与 DNSSEC 工具链完整、文档与社区积累最厚。需要一台服务器同时承担对外权威、对内递归、按来源分流、并做复杂策略时，BIND 9 依然是成熟可靠的选择。

**代价在哪。** 配置面大意味着**误配概率高**：一个 view 的匹配顺序、一条 `allow-recursion` 的范围、一次 `recursion yes` 与转发器的组合，都可能把递归服务暴露给不该暴露的来源。历史 CVE 数量多，既有部署广、被审视充分的原因，也有权威 + 递归 + 动态更新 + 区域传送共处一个进程、代码路径相互牵连的原因（第 1 章讨论过这条）。对只想要"帮我查域名并验证签名"的场景，这些额外路径都是不需要承担的面。

**典型失败模式。** 不是"跑不起来"，而是"跑起来了但语义不对"：递归被意外开放、view 命中了预期外的客户端、转发与递归混用导致验证链断裂。这类问题不会在启动时报错，只能靠从客户端侧实际发查询去验证。

### dnsmasq：小型网络的一体化方案

**强在哪。** 极低的资源占用、DHCP + DNS + TFTP 一体、配置短、在路由器固件与嵌入式设备里几乎无处不在。对"一台家庭网关要给局域网发地址、顺便把域名查询转给上游"这个需求，它是最省事的答案。

**代价在哪。** 它面向的是**转发与缓存**，不是自主迭代与验证。DNSSEC 验证与加密传输能力有限且常依赖上游，过滤表达力有限，日志与统计粒度弱；当出现"某个域解析失败"，很难从 dnsmasq 自身判断是上游失败、自己缓存了 NXDOMAIN、还是过滤规则命中。可观测性弱在平时不是问题，在排查时是主要瓶颈。

**典型失败模式。** 上游切换或过滤表更新后，客户端仍在拿到旧结果；因为缓存与转发逻辑混在一起，定位要跨工具。另一个常见冲突是与本机其他存根解析器（如 systemd-resolved）同时占用 53 端口，表现为"配置没改但行为变了"。

### 三者对照：Unbound 的位置

| 维度 | BIND 9 | dnsmasq | Unbound |
|---|---|---|---|
| 定位 | 权威 + 递归全能 | 小型网络 DHCP/DNS 一体 | 只做递归验证，模块化 |
| 默认安全 | 依赖配置收敛暴露面 | 依赖上游，验证与可观测性弱 | 默认随机化、清理器、DNSSEC 验证 |
| 配置面 | 大 | 极小 | 中，边界清楚 |
| 可观测性 | 强 | 弱 | 统计 + 日志 + dnstap，可按需 |
| 适合 | 复杂企业/权威场景 | 嵌入式、家用网关 | 自建递归、按角色拆实例 |
| 不适合 | 只想要一台最小验证器 | 要自主迭代、要可审计验证链 | 要做权威服务器、要做集群服务发现 |

**这不是产品宣传，是角色取舍。** 三句话概括：

- 需要对外权威、view、复杂策略 → BIND 9（或 NSD / PowerDNS Authoritative 专职做权威）；
- 需要 DHCP 一体、资源极省、验证交给上游 → dnsmasq；
- 需要自己从根开始迭代、默认验证、边界可审计、按信任域拆实例 → Unbound。

三者也可以共存：dnsmasq 继续管 DHCP，把 DNS 查询转给本机 Unbound；Unbound 自己做迭代与验证。**不要用一个产品覆盖所有角色，再靠一堆开关互相覆盖语义**。

## 本章要点

- DNS 命名空间是倒树，区域是管理单元，委派靠父区域的 NS 记录；胶水记录（glue record）解决委派自举，但它是附加段的非权威数据，域外夹带 glue 是经典缓存投毒面，与 DNSSEC 无关。
- 递归是解析器对客户端的承诺（RD/RA），迭代是解析器对上级的工作方式；一次 `www.example.org` 解析要经过根 → TLD → 各级权威的多轮 referral，`dig +trace` 只能看委派链，不能代表本地解析器的真实行为。
- 缓存作用于 RRset，返回的是剩余 TTL；负缓存（negative caching，[RFC 2308]）会记住 NXDOMAIN/NODATA 并放大故障，过期缓存应答（serve-stale，[RFC 8767]）则是刷不到新数据时的有条件例外。
- EDNS(0) 用 OPT 伪记录扩展 UDP 报文，`edns-buffer-size`（出向）与 `max-udp-size`（入向）默认值均为 1232，方向不可调反；CNAME 链会让一次查询重走解析，且与查询名最小化的严格模式存在兼容坑。
- BIND 9 全能但配置面大、历史 CVE 多；dnsmasq 面向小型网络/嵌入式、DHCP+DNS 一体但验证与可观测性弱；Unbound 只做递归验证、默认安全、模块化。三者是角色取舍，不是优劣排名。
- DNSSEC = 数据完整性/来源认证，DoT/DoH/DoQ = 传输加密/隐私，二者不能互相替代。
