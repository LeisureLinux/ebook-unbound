# DNS 故障域隔离：从一次全球性中断说起

把 2021 年 10 月 4 日那次近 6–7 小时的中断，记成「内部 DNS 和公网用了同一个域名，DNS 没隔离，所以炸了」，是一句很顺手的总结，也是**不准确的归因**。它把一场路由与控制面的连锁事故，压缩成了一个命名空间配置问题；按这个结论去整改，会去做 split-horizon、改几个内部域名，却在真正断掉的那一层什么都没动。

本章先把官方确认的因果链摆正，再用一张证据分级表把「官方确认 / 外部观测 / 公开报道 / 本书推论」分开，最后给出一套六层隔离框架。这套框架是**本书自定义的归纳**，不是任何厂商的规范，也不是那份官方复盘里的原文。案例里出现的公司名与公开业务域名属于公开事件叙述；本章自身的实验环境统一表述为**一台家庭网关 + 一台云主机**，所有地址均为**教学用示例地址**：IPv4 取 `192.0.2.0/24`、`198.51.100.0/24`、`203.0.113.0/24`（[RFC 5737]），IPv6 取 `2001:db8::/32`（[RFC 3849]），域名只用 `example.net` / `example.org` / `home.arpa.`，令牌一律写 `<TOKEN>`。

## 先把归因摆正：不是「同域名」

### 官方确认的因果链

Meta 工程博客 2021-10-05 的复盘《More details about the October 4 outage》给出的链条是五步，顺序不能调换：

```text
[1] 例行骨干网维护：一条「评估全球骨干容量」的命令
        ↓ 意外生效
[2] 所有数据中心之间的连接被切断；命令审计工具里的 bug 没拦住
        ↓ 数据中心不可达
[3] 小型设施里的权威 DNS 服务器连不上数据中心
        → 按设计「判定自己不健康」
        → 主动撤回自己的 BGP 路由宣告
        ↓ 前缀从全球路由表消失
[4] facebook.com / instagram.com / whatsapp.net 的权威 NS 不可达
    （服务器进程仍在运行，是「不可达」不是「宕机」）
        ↓ 修复动作本身依赖网络与名字解析
[5] 官方明说的两个恢复障碍：
      a. 正常网络访问与带外（OOB）网络访问都断了
      b. DNS 全面失效，打断了大量内部工具（排障/修复要用的工具自己依赖 DNS）
    → 只能派工程师物理到场；数据中心的高物理/系统安全设计
      拖慢了进场与改设备，官方认为这个「日常高安全 vs 罕见事件慢恢复」
      的取舍值得拿出来讨论
```

注意第 [3] 步：撤路由是**健康检查按设计做出的正确动作**，不是配置失误。权威服务器判断「我连不上数据中心，我不该继续对外宣告」，这个逻辑本身没问题；出问题的是「内部可达性、外部可达性、控制面可达性」被绑在了同一个判定条件上。第 [5] 步才是这次事故从「一次路由故障」升级成「近 6–7 小时全局中断」的关键：**修东西要用的路，和坏掉的东西是同一条路**。

### 必须写明的一处纠正

官方复盘里**没有**「内外同域名导致 split-horizon 误配」这一条。既没有说内部视图配错，也没有说因为内部名字和对外名字重名而解析串了。把「同域名」写成根因，等于凭空给官方结论加了一个不存在的环节。

正确的提法分两层，别混：

- **根因不是「同域名」，而是内外共用同一套名字解析基础设施与同一故障域**：骨干网断连 → 权威 DNS 自动撤 BGP 路由 → 内部工具、认证、带外管理跟着一起失效。这是本书据官方链条做出的**归纳**。
- **「内部名字若挂在可公开解析的同一命名空间下，且没有独立的内部权威与内部视图，就会把内部系统的可用性绑到公网路由与公网权威的可达性上」**，是从案例里提炼的**设计推论**，不是已确认根因。它是一条值得照着做的设计教训，不能倒过来当成「官方说事故原因是这个」。

这个区分不是抠字眼。若当成根因，整改会停在「换个内部域名」；若当成推论，整改会落到「把权威面、递归面、控制面的故障域切开」。后者才是本章后面六层要做的事。

顺带把结论的性质钉死：这是**架构问题**，与选用哪个 DNS 软件无关。换成任何一款权威服务器、任何一款递归解析器，只要「权威可达性判定」「内部工具的解析依赖」「带外通道」「进门凭据」共用一个故障域，同样的链条仍然成立。本章不做产品批判，也不给任何实现打分；Unbound 在本书里的定位始终是**递归验证器，不是权威服务器**，`local-zone` / `local-data` 只是「非常有限的权威服务」，这个边界在第 25 章立过，这里继续沿用。

### 推论就是推论

表里 D 类四条，写作上必须自带标签，不能出现「由此可见，事故原因是……」这类把推断伪装成结论的句子。尤其 D3：门禁与工牌的失效，**公开可核验的只有记者的现场描述**（C1）与「派工程师到场」（C2、A6），以及 ThousandEyes 那条标着推测的分析（B5）。把这三者拼成「因为内部 DNS 挂了所以工牌刷不开」是一条合理的假设，适合拿来做演练输入，**不适合写成事实**。

同理，B2 的 30 倍与 B6 的 100 倍是两处不同观测点的放大倍数，前者看的是公共递归器的入向查询，后者看的是顶级域权威侧的查询，不要相加、不要当成同一个数字。B4 的「控制面被切断」是 ThousandEyes 的分析判断，不是 Meta 对自身控制面的说明。

## 六层隔离框架（本书归纳）

下面六层是本书为「把故障域切开」自定义的检查框架，标注为**归纳**：它不来自某份标准，也不宣称覆盖全部风险。顺序有意为之——先切名字，再切权威，再切递归，然后才轮到控制面与失败语义；因为前三层的隔离再干净，只要第四层的「进门」还绑在同一条路上，第五、六层的预案就执行不了。

### ① 命名空间隔离

目标是让内部名字的可解析性**不依赖公网命名空间的可达性**。

- 内部用独立且**不可公网解析**的域：`home.arpa.`（[RFC 8375] 为家庭/小型内网保留）或自己持有的域下划出的**内部专用子域**，配合本地区与内部分区。不要复用对外业务主域。
- 内部专用子域要有明确边界：对外权威上不出现该子域的委派，内部递归器上把它钉到内部权威，公共视角查不到记录。
- split-horizon（同一名字按来源给两套答案）是可选工具，**不是隔离本身**。它的代价要写进运维手册：同一个 FQDN 在两个视图里答案不同，排障时必须先问「这次查询来自哪个视图」，缓存、`dig` 结果、工单记录都会出现「时通时不通」的表述；视图数量一多，变更流程与审计日志都要跟着翻倍。
- 明确不做的事：不靠「改个内部域名」解决可达性。名字换了，若权威面和路由面仍共用，故障域没变。

第 27 章会给出另一条腿：mDNS 的 `.local` 是链路本地多播名字，本链路自洽，天然不依赖单播权威与公网路由；但它出不了子网，也**不能替代**内部权威。

### ② 权威面隔离

目标是让「对外权威不可达」不自动等价于「内部名字也解析不了」。

- 内部权威（NSD、AD 集成区等）与对外权威**分开部署、分开路由宣告、分开变更流程**。第 25 章讲的内部名字产生路径，落点就是这台内部权威；Unbound 用 `stub-zone` / `forward-zone` 指过去，自己不承担权威角色。
- 隐藏主服务器（hidden primary）：真正可写的主不对外宣告，对外只见辅；变更先在主上做，再分发。
- 权威至少两台，分处不同网段与不同地理位置。NIST SP 800-81r3 的部署指导里有同类控制目标（专用 DNS 服务器、每区一主多辅、至少两台异地权威、隐藏主、书面的辅升主流程与组件告警）；本章只引**控制目标名称**，不引条款号，具体条文见官方资料。
- 关键边界：健康检查的判定条件要问清楚「健康」指的是什么。案例里权威服务器「连不上数据中心」就撤自己的路由，等于把跨数据中心的 backbone 状态当成了自身服务可用性的代理指标。内部权威的宣告条件里，不应包含「能否连上对外业务系统」这类同故障域依赖。
- 变更流程分开还有一层意思：对外权威的一次误操作，不应同时改动内部权威的区数据或路由策略。配置与区数据分发要版本化、可回滚，见第 26 章。

### ③ 递归面隔离

目标是让内部客户端的解析**不托管给对外权威或外部网络**。

- 内部递归解析器独立部署，不由对外权威服务器兼任，也不放在「只有公网路由可达」的位置。存根解析器至少配两个递归器地址（第 8 章的威胁模型与第 9 章的访问控制给出基线）。
- 本地根区镜像 / `auth-zone` 让根这一跳不出口（第 6 章）：公网递归链路抖动时，内部仍有根层数据。注意 `auth-zone` 是**只读根镜像，不是可写权威区**，别拿它当内部权威用。
- 缓存与 TTL 撑过上游抖动：第 4 章的最小可用配置、第 7 章的多实例与可观测性，加上 `serve-expired`（过期缓存应答，即 serve-stale 机制，[RFC 8767]），构成「上游短暂不可用时仍给答案」的能力。
- 这里有个常被忽略的边界：递归面隔离**不提供**控制面隔离。递归器再冗余，若工程师的登录、工牌、带外终端仍要靠同一个名字空间进来，第 ④ 层空缺照样会把恢复卡住。

### ④ 控制面隔离

这一层是官方 A5、A6 直接指出的缺口，也是本书前 27 章几乎没碰的一层。

- 带外管理（OOB）要有**独立路径与独立名字**：独立链路、独立地址段、独立的静态名字解析（本地 `hosts` 或 OOB 自带的小型解析），不查业务 DNS，不走业务路由。案例里「正常与带外网络访问都断」说明两条路在某处共用了物理/路由资源，OOB 的「外」必须是真的外。
- 门禁 / 认证 / 工牌系统要有**本地校验与离线兜底**：门禁控制器能在与中心认证断开时按本地缓存的白名单放行应急人员，而不是「刷不开就是拒」。这是从 C1、C2、B5 提炼的**演练假设**（D3），不是对事故原因的断言。
- **物理到场预案**：谁有权限进场、备用凭据放在哪里、离线怎么联系、设备控制台怎么接、多久能到现场。A6 明说高物理/系统安全设计拖慢了恢复，所以预案要提前把「安全流程在应急下如何走」写清楚，而不是出事时临时找人签字。
- 一句实话：这一层**超出 DNS 书的范围**。DNS 章节能做的是「不让 DNS 成为进门的前置依赖」，做不了门禁控制器与身份系统的设计。书里只标注接口与验收条件，实现交给机房与身份团队。

### ⑤ 缓存与失败语义

目标是把「权威不可达」从一次局部抖动，限制成一次局部抖动，而不是放大成 100 倍查询风暴。

- TTL 策略：B7 观测到 1–5 分钟的 TTL 让缓存几分钟内耗尽。对外业务记录给极短 TTL，等于把权威侧的可用性直接暴露给全球重试流量；关键内部记录则应留足可用窗口。TTL 是**故障域的时间维度**。
- 负缓存（[RFC 2308]）：上游瞬时 NXDOMAIN 会按 SOA minimum 被缓存，修好权威后客户端仍失败；本书第 4/7 章与第 22 章案例都踩过，链路上**每个实例都要刷**。故障期尤其要避免把 SERVFAIL/NXDOMAIN 长时间钉在缓存里。
- SERVFAIL 限流与指数退避：B8 的建议正对 B2、B6 的放大。递归器在「父区委派正常、但权威全不响应」时应收敛重试而非线性重发；客户端侧的应用重试同样要有抖动退避。这里没有「一个开关买齐」的做法，参数名称与默认值**见官方手册对应章节**，本节只表达策略意图。
- `serve-expired` 与限流是一对，不是二选一：前者让已有缓存继续服务，后者让没有缓存时不去压垮上游。两者都要配合可观测性（第 7 章）确认真的生效。

下面这个短片段只用来示意第 ③、⑤ 层的衔接，是**教学用示意**，不是完整配置：

```conf
# /etc/unbound/unbound.conf.d/99-fault-domain.conf（节选，教学用示例）
server:
    serve-expired: yes
    serve-expired-client-timeout: 1800
```

**为什么这么设**：`serve-expired: yes` 允许上游不可达时回一份过期缓存应答，把「解析全失败」降级为「答案稍旧」；`serve-expired-client-timeout` 的**单位是毫秒**（1800 即 1.8 秒），语义是「先尝试刷新，超时才回过期缓存」，不是 1800 秒。过期应答的保留上限还有单独参数控制，**名称与默认值见官方手册对应章节**，本节不代填。

**怎么验证**：断开上游前先预热一条记录，再断链并观察 TTL 与应答标志——

```bash
dig @192.0.2.53 www.example.org A +noall +answer +comment
```

断链后应答仍在、TTL 明显偏小或为 0，即说明过期缓存应答在起作用；参数名与默认值以官方手册对应章节为准。

**失败模式 / 回滚点**：过期缓存会掩盖上游已恢复的事实，负缓存还可能把瞬时的 NXDOMAIN 钉住；恢复后必须按「控制面 → 权威 → 递归 → 客户端」的顺序逐层刷缓存（`unbound-control` 相关命令见第 7 章），再复测。回滚只需把该 include 文件移除并 reload，配置管理里保留上一版。

### ⑥ 演练与可恢复性

前五层是设计，第六层是**证明设计成立**。没注入过故障的隔离，只能算图纸。

- 注入清单至少覆盖四类：**断网**（业务链路）、**撤路由**（模拟权威前缀消失）、**关权威**（内部/对外分别关）、**关认证**（中心认证不可达）。每类都要有明确的预期可观测结果与回滚点，见下一节表格。
- **恢复顺序固定：先控制面，再 DNS，再业务**。理由直接来自 A5：DNS 是修复动作的前置依赖，业务先起来而排障工具仍不可用，只会把事故拖长；控制面（OOB、门禁、登录、离线凭据）先可用，工程师才进得去、改得动。
- 演练前钉死三件事：**谁有权限**（变更与撤路由的授权人）、**怎么联系**（不依赖业务 DNS 与业务网络的通信录，纸质或离线副本）、**离线凭据**（`<TOKEN>` 类凭据与应急账号的存放位置、有效期、轮换记录）。这三项恰恰是 A6 里拖慢恢复的部分。
- 演练要记录「实际恢复耗时」与「预期耗时」的差，差在哪一层就把哪一层拎出来重做。别把演练做成「跑一遍命令都绿了」——绿的是命令，不是恢复能力。

## 映射到前 27 章

本章是前 27 章的**失败模式总检验**：把每一章已经做过的隔离，放回「一次骨干断连 + 权威撤路由 + 控制面一起失效」的场景里，看它到底挡住了哪一层。

| 章 | 主要提供 | 对应隔离层 | 在这个场景下能挡住什么 / 挡不住什么 |
|---|---|---|---|
| 第 25 章 内网 DDNS 与微软 DNS 对照 | 内部名字的产生路径：外部权威 + `nsupdate`（[RFC 2136]）、NSD 权威 + Unbound 递归、静态生成 `local-data` | ① 命名空间隔离、② 权威面隔离 | 独立内部区 + 内部视图让内部名字不去公网解析；但「更新必须落到主服务器」「AD 集成区发给任意 DC」说明**写路径仍依赖可达性**，主区不可达时动态更新停摆，需靠静态产物兜底 |
| 第 26 章 企业级大规模部署：anycast 与集群 | anycast 服务地址绑 loopback + 路由宣告、健康检查失败即撤路由、隐藏主 + 辅、DNS Cookie 密钥分阶段滚动、配置与过滤表版本化分发 | ② 权威面隔离、③ 递归面隔离（冗余） | anycast 能藏住单节点故障、多台异地权威能扛住单机宕机；但案例里**故障恰恰是「撤路由」本身**。同一 anycast 集合若共用同一套配置分发与同一套健康判定，仍是同一故障域；且缓存不共享，切流量后有冷缓存抖动 |
| 第 27 章 单播 DNS 与多播 DNS | `.local` 的链路本地多播（[RFC 6762]）、`home.arpa.`（[RFC 8375]）与单播名字的边界、Unbound 不参与 mDNS | ① 命名空间隔离（本链路自洽的一支） | 本链路发现不依赖单播权威与公网路由，链路内设备仍可互相找到；但 mDNS 默认不出子网，跨子网要靠单播 DNS-SD / Discovery Proxy，**不能替代内部权威与递归面** |
| 第 21 章 综合实验拓扑 | 一台网关 + 一台云主机，A/B/C 三层实例、五个观测点、八项失败注入矩阵、`serve-expired` / 负缓存 / 逐层刷缓存的回滚纪律 | ③ 递归面隔离、⑤ 缓存与失败语义、⑥ 演练与可恢复性 | 注入矩阵已覆盖「停上游」「断出向」「瞬时 NXDOMAIN」「上游断开时过期缓存」；可直接扩展成下一节的撤路由/关认证项。但它是一台网关的教学拓扑，**没有独立的 OOB 链路与门禁系统**，第 ④ 层无法在拓扑内验证 |

### 仍然空着的那一格

把表竖着看，第 ④ 层「控制面隔离」只有接口、没有实现。**物理门禁的离线兜底、带外管理网的独立链路、工牌控制器的本地白名单、离线凭据的保管与轮换，都不在 DNS 书范围内**。第 21 章的拓扑能演示「DNS 挂了业务怎么降级」，演示不了「人进不去机房怎么修」。

这不是遗漏，是边界。本书能给的承诺只有一条：**别让 DNS 成为「进门」和「修 DNS」的前置依赖**。剩下的部分要在机房、身份与物理安全的方案里闭环；第 28 章把这一格明确留白，比假装六层都配齐了更诚实。

## 故障注入与验收清单

以下为**教学用示例地址与域名**，在「一台家庭网关 + 一台云主机」的实验环境里执行；`192.0.2.53` 代表内部递归器，`198.51.100.53` 代表对外权威视角，`203.0.113.53` 代表外部公共视角（教学桩），`2001:db8::53` 代表内部递归器的 IPv6 地址。实验主机名用 `gw-01`、`edge-01`、`cloud-01` 这类中性写法，不声明是真实环境。执行前先备份：`cp -a /etc/unbound /var/tmp/unbound-before-fault-lab/`。

### 可复制的清单表

| # | 注入动作 | 对应层 | 预期可观测结果 | 验收命令 | 回滚点 |
|---|---|---|---|---|---|
| 1 | 断开网关到云主机的业务链路，保留内网 | ⑥ / ③ | 内部名字仍可解析；外部名字靠过期缓存应答撑住，不出明文 53 兜底 | `dig @192.0.2.53 svc.home.arpa. A +short` 有答案 | 恢复链路；逐层刷缓存 |
| 2 | 撤回对外权威的教学前缀（模拟 B1/B3） | ② / ⑥ | 外部视角 SERVFAIL；**内部权威的 NS 与区数据不受影响** | `dig @203.0.113.53 www.example.net A +short` 无答案，同时 `dig @192.0.2.53 svc.home.arpa. A +short` 仍有答案 | 重新宣告前缀；确认内部权威路由未被动过 |
| 3 | 分别停掉对外权威、再停内部权威 | ② | 两次故障的影响范围不同：前者不影响内部名字，后者影响 | 两次 `dig` 对比，记录差异 | 按「先内部权威，再对外权威」恢复 |
| 4 | 对一条内部名字瞬时返回 NXDOMAIN 后恢复 | ⑤ | 应答在 SOA minimum 期内仍是 NXDOMAIN；刷缓存后恢复 | `dig @192.0.2.53 svc.home.arpa. A +noall +comment` | 逐实例刷负缓存（第 7、22 章） |
| 5 | 断上游后连续查询同一名字 100 次 | ⑤ | 查询计数**不出现 100 倍放大**；有限流/退避或过期缓存应答命中 | `unbound-control stats_noreset | grep -i servfail` | 关闭注入脚本；核对计数基线 |
| 6 | 让中心认证/工牌教学桩不可达 | ④ / ⑥ | 门禁本地兜底放行应急账号；OOB 名字由静态解析给出，不查业务 DNS | `getent hosts oob.example.net` 有静态答案 | 恢复认证桩；核对本地白名单未越权 |
| 7 | 切断业务 DNS，只留 OOB 通道 | ④ / ⑥ | 工程师仍能登录控制台、取到离线凭据、按预案进场 | `dig @2001:db8::53 gw-01.home.arpa. A +short` 在 OOB 侧仍成立 | 恢复业务 DNS；归档离线凭据使用记录 |
| 8 | 全流程恢复演练 | ⑥ | 严格按「控制面 → DNS → 业务」顺序，每步有验收命令与耗时记录 | 见下表命令组逐条复测 | 保留演练记录与配置备份，回滚到基线 |

表中第 6、7 项依赖机房/身份系统的教学桩，**不在 DNS 书实现范围内**；本章只给出验收条件。任何一项出现「预期结果不符」，先按第 21 章的纪律排查观测点与 nftables 规则，再怀疑上游。

### 一组教学用验证命令

```bash
# 1) 命名空间隔离：内部保留域在公共视角不可解析
dig @203.0.113.53 home.arpa. SOA +noall +comment
dig @192.0.2.53  svc.home.arpa. A +short

# 2) 权威面隔离：内部名字与对外名字指向不同的权威
dig @192.0.2.53     home.arpa. NS +short
dig @198.51.100.53  example.net NS +short

# 3) 递归面隔离：根层由本地镜像给出，不依赖公网出向
dig @192.0.2.53 . NS +noall +answer
unbound-control status

# 4) 缓存与失败语义：过期缓存应答、负缓存、SERVFAIL 计数
dig @192.0.2.53 www.example.org A +noall +answer +comment
unbound-control dump_cache | grep -i 'example.org' | head
unbound-control stats_noreset | grep -iE 'servfail|expired'

# 5) IPv6 与 ULA：内部递归器的文档地址段可达性
dig @2001:db8::53 svc.home.arpa. AAAA +short

# 6) 控制面隔离：OOB 名字走静态解析，不经业务 DNS
getent hosts oob.example.net
grep -n 'oob.example.net' /etc/hosts

# 7) 恢复顺序自检：控制面 → DNS → 业务，逐层确认再放行
dig @192.0.2.53 oob.example.net A +short
dig @192.0.2.53 svc.home.arpa. A +short
dig @192.0.2.53 www.example.org A +short
```

**为什么这么设**：七组命令各自只测一层，且都由近及远——先看内部名字、再看权威委派、再看根层、再看缓存语义、最后看控制面与恢复顺序。把注入前后的同一条命令输出留档，差分就是验收证据，不需要额外搭监控。

**怎么验证**：注入 #2 时，第 1 组里公共视角应无答案、内部视角仍有答案；第 2 组两组 NS 应指向不同集合；第 4 组的 `expired` 计数应上升而 `servfail` 计数不呈倍数增长。三处齐备，才说明命名空间、权威面、失败语义三层都真的切开了。

**失败模式 / 回滚点**：注入会污染缓存（尤其负缓存），测完必须按「控制面 → 权威 → 递归 → 客户端」逐层刷；`unbound-control` 不可用时只能重启实例刷缓存，且链路上每个实例都要刷（第 7、22 章）。所有注入前备份 `/etc/unbound`，所有路由/宣告类注入先在实验段做，回滚点是重新宣告教学前缀并恢复链路。演练记录与 `<TOKEN>` 类凭据的使用记录一并归档。

## 本章要点

- **归因必须摆正**：官方复盘里没有「内外同域名导致 split-horizon 误配」这一条；正确链条是骨干维护命令误切断数据中心互联 → 权威 DNS 按设计判定不健康并主动撤回 BGP 路由 → 权威 NS 从全球路由表消失 → 正常与带外访问皆断、DNS 失效打断内部工具 → 只能物理到场且高安全设计拖慢恢复。根因不是「同域名」，而是**内外共用同一套名字解析基础设施与同一故障域**。
- **推论不许写成事实**：「内部名字挂在可公开解析的同一命名空间且无独立内部权威/视图，会把内部可用性绑到公网路由与公网权威」是从案例提炼的**设计推论**；门禁/工牌失效属**公开报道**（NYT、The Verge）与官方「物理到场」互相印证，不是 Meta 逐条确认。证据分官方确认 / 外部观测 / 公开报道 / 本书推论四类。
- **放大与语义**：Cloudflare 观测约 30 倍重试、15:51 SERVFAIL / 15:58 路由撤回；ThousandEyes 观测 15:39 起数百条撤回、7 个覆盖内部 DNS 的 IPv4 前缀消失并指出控制面被切断；Verisign 观测约 7,000 → 900,000 qps（>100 倍）、TTL 1–5 分钟缓存几分钟耗尽，建议限流 + 指数退避。两组倍数是不同观测点，不可混用。
- **六层隔离是本书归纳**：① 命名空间（`home.arpa.` / 内部专用子域，split-horizon 只算工具且排障代价高）② 权威面（分开部署/宣告/变更、隐藏主、至少两台异地）③ 递归面（独立递归器、本地根镜像 / `auth-zone`、`serve-expired`）④ 控制面（OOB、门禁与认证的本地校验与离线兜底、物理到场预案）⑤ 缓存与失败语义（TTL、负缓存、SERVFAIL 限流与退避）⑥ 演练与可恢复性（断网/撤路由/关权威/关认证，恢复顺序**先控制面再 DNS 再业务**）。
- **结论落在架构**：这是故障域划分问题，与选用哪个 DNS 软件无关，不写成产品批判；第 25 章给 ①②、第 26 章给 ②③ 的冗余（但 anycast 撤路由与共用配置分发仍可能是同一故障域）、第 27 章给 ① 的链路本地一支、第 21 章给 ③⑤⑥，**第 ④ 层物理门禁离线兜底不在 DNS 书范围内**，只标注接口与验收条件。
- **验收靠注入不靠声明**：八项注入清单 + 七组教学命令，全部使用 RFC 5737 / `2001:db8::/32` 文档地址与 `example.net` / `example.org` / `home.arpa.`；注入必污染缓存，恢复后逐层刷，配置与凭据使用记录归档。
