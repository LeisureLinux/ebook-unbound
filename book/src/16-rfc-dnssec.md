# DNSSEC RFC 族

第三篇第 10 章讲的是怎么配验证器：信任锚（trust anchor）从哪来、放行与拒绝怎么调、坏签名怎么观测。本章只讲条文逻辑与设计动机——**为什么这套协议被设计成"验证失败必须拒绝"，而不是"尽量给个答案"**；为什么"签名被剥离"在这些条文里等同于降级攻击；以及为什么一个 2005 年定稿的协议族，在此后十几年里还需要七八份 RFC 来澄清、补参数、收编运维经验。

贯穿全章的区分，全书一致：**DNSSEC 提供数据完整性与来源认证**，DoT / DoH / DoQ 提供**传输加密与隐私**，查询名最小化减少元数据外泄，过期缓存应答提供可用性。四者互不替代。把任何一项当成"已经加密了所以数据可信"，会在排查时得出完全错误的结论。

与第 15 章一样，本章按"它要解决什么 → 关键条文 → 对实现的约束 → 常见误读"展开关键 RFC；运维类与历史类小节合并叙述，避免为凑格式而堆砌名词。

## DNSSECbis：[RFC 4033] / [RFC 4034] / [RFC 4035]

### 它要解决什么

最初的 DNSSEC（[RFC 2535] 及其一组配套文档）在 1990 年代末定稿，但部署几乎没推开：密钥管理复杂、与动态更新和委派的组合不清晰、应答尺寸与实现负担都偏重。2005 年 3 月发布的 [RFC 4033]、[RFC 4034]、[RFC 4035] 合称 **DNSSECbis**，一次性废弃 [RFC 2535]、[RFC 3008]、[RFC 3090]、[RFC 3445]、[RFC 3655]、[RFC 3658]、[RFC 3755]、[RFC 3757]、[RFC 3845]，并更新 [RFC 1034]、[RFC 1035]、[RFC 2181]、[RFC 2308] 等多份基础文档。三份分工明确：

- [RFC 4033] *DNS Security Introduction and Requirements*：威胁模型、术语、验证器的四种状态、以及"最后一跳"问题；
- [RFC 4034] *Resource Records for the DNS Security Extensions*：DNSKEY、RRSIG、NSEC、DS 四种记录类型及其线格式；
- [RFC 4035] *Protocol Modifications for the DNS Security Extensions*：DO / CD / AD 标志位、验证流程、名字服务器的发送与应答规则。

设计目标不是"让 DNS 保密"，而是让**应答数据可被验证**：任何人都能伪造报文，但伪造者拿不到私钥，因此签不上名。

### 关键条文

[RFC 4034] 的四种记录构成一条链：

- **DNSKEY**：区里发布的公钥，flags 区分 KSK（密钥签名密钥，SEP 位）与 ZSK（区签名密钥）。
- **RRSIG**：对某个 **RRset** 的签名，签的是第 15 章 [RFC 2181] 确立的原子单位，不是单条记录；RRSIG 自带签名有效期（inception / expiration），过期即不可验证。
- **DS**（Delegation Signer）：父区里对子区 DNSKEY 的摘要，把信任从父区传到子区。这是信任链的关键——验证器不必预先知道每个区的密钥，只需知道根。
- **NSEC**：按规范名排序的"下一个名字"链，用来**证明某个名字或某个类型不存在**。

[RFC 4033] 定义验证器可判定的四种状态，这四个词在本书中保持一致：

| 状态 | 判定条件 |
|---|---|
| Secure | 有信任锚、有信任链、应答中所有签名均能验证 |
| Insecure | 有信任锚与信任链，但在某个委派点有签名证明 DS 不存在，该分支被证明性地未签名 |
| Bogus | 有信任锚且委派指示应签名，但验证失败（缺签名、签名过期、算法不支持、NSEC 说该有却没有等） |
| Indeterminate | 没有可覆盖该部分的信任锚；这是未配置验证时的默认状态 |

[RFC 4035] 规定三个标志位：**DO**（DNSSEC OK，在 OPT 伪 RR 里，请求 DNSSEC 相关记录）、**CD**（Checking Disabled，存根请求"别替我验证"）、**AD**（Authentic Data，服务器告知"我已验证这些数据为真"）。它还明确：安全感知的名字服务器 **MUST NOT** 在 Answer 与 Authority 段里有任何未判定为真的数据时置 AD 位；对 Bogus 数据，用 RCODE=2（SERVFAIL）通知非验证型存根解析器。

### 对实现的约束

验证器必须自己能完成从信任锚到目标区的整条链构建：向父区取 DS、向子区取 DNSKEY、用 KSK 验证 DNSKEY RRset、用 ZSK 验证数据 RRset、检查 RRSIG 有效期与算法支持、用 NSEC/NSEC3 验证否定应答。这意味着**它必须能自己向根发起 priming 查询取根的 DNSKEY**。

由此直接推出第三篇那条运维约束：把 `forward-zone "."` 配成"一切都交给上游"的转发器，与"自己配置信任锚"在架构上是二选一。转发器把根查询也交出去了，无法完成自己的信任锚 priming，日志会持续报 `failed to prime trust anchor`，并间歇性全量 SERVFAIL。这不是软件缺陷，是 [RFC 4035] 的验证流程在转发模式下无法闭环。

另一条约束是 [RFC 4035] §4 附近的 BAD cache 思路（[RFC 6840] 把它写得更明确）：对持续验证失败的 RRset 应有短时负面缓存，避免每次查询都重跑一遍昂贵的验证。但这属于性能与抗放大，不改变"必须拒绝"的结论。

### 常见误读

**误读一：DNSSEC 加密了查询内容。** 完全没有。DNSKEY、RRSIG、DS、NSEC 都是明文记录，任何路径上的观察者都能读到完整 QNAME。加密传输要靠 DoT / DoH / DoQ（第 17 章）。

**误读二：只要区里有 RRSIG 就是 Secure。** 没有信任锚时状态是 Indeterminate，验证器压根不验证；坏签名域也照样返回答案。这就是第三篇记录的"无 trust anchor = 透传不验证"。

**误读三：AD 位可以由客户端自己置。** [RFC 6840] §5.7 专门澄清：服务器应忽略查询里的 AD 位，它只由服务器在应答里根据验证结果设置。客户端置 AD 不能"要求"服务器验证。

## 验证器为什么必须 fail-closed

这一节是本章的核心，也是 DNSSEC 与几乎所有"尽力而为"的网络协议最不一样的地方。

### 它要解决什么

DNS 的传统行为是**fail-open 的可用性优先**：一个权威服务器没应答，就换下一个；TTL 到了就重查；实在不行返回 SERVFAIL，客户端自己重试或换解析器。DNSSEC 若沿用这个思路，会出现一个致命的退化：攻击者只要在链路上**把签名相关记录全部剥掉**（去掉 RRSIG、去掉 DNSKEY、把 DO 位清掉、或干脆伪造一个"该区未签名"的 Insecure 证明），验证器就会从"验证失败"滑到"没什么可验证"，然后把未经验证的数据放行。

换句话说，安全机制的强度取决于**它能否被绕过**，而不是它能否正确工作。一个"验不过就放行"的验证器，等于给攻击者发了一张"如何让我闭嘴"的说明书。

### 关键条文

条文本身并不写"fail-closed"这个词，它分散在几处：

- [RFC 4033] 把 **Bogus** 定义为"有信任锚且委派指示应签名、但验证失败"，并明确该规范只定义"如何用 SERVFAIL 通知非验证型存根解析器数据为 Bogus"——即 Bogus 的对外表现就是拒绝服务，不是降级返回。
- [RFC 4035] 要求 AD 位只在所有相关数据被判定为真时才置位；不置 AD 不等于"可以给数据"，而是"不能宣称可信"。
- [RFC 4035] 明确对验证失败的应答使用 RCODE=2，并建议对重复验证失败做短时缓存（[RFC 6840] §3.1 把这些整理成 BAD cache 的实现要求）。
- [RFC 4033] 的 Insecure 判定要求**有签名证明 DS 不存在**：一个区"看起来没签名"与"被证明未签名"是两件事，只有后者才允许放行。这一条正是抵御"伪造未签名"的关键闸门。

### 对实现的约束

因此验证器在三种状态之间的行为必须是：

| 配置状态 | 行为 | 结论 |
|---|---|---|
| 无信任锚 | 透传，不验证 | 坏签名域也返回答案，等于没有 DNSSEC |
| permissive | 记录日志但放行 | 可观测，但不提供保护 |
| 真验证（`val-permissive-mode: no`） | 坏签名 → SERVFAIL，好签名带 AD 标志 | 唯一能提供保护的模式 |

第三篇里的 `harden-dnssec-stripped: no` 之所以被列为高危，条文依据就在这里：在有信任锚的前提下，它允许"本应签名却看不到签名"的应答被接受，等于主动把 [RFC 4033] 的 Bogus 判定改成放行。

同理，`harden-below-nxdomain` 只对 **DNSSEC-secure 的 NXDOMAIN** 生效：无签名区的 NXDOMAIN 不构成可验证的否定证明，验证器没有依据去做子树剪枝。这不是开关失灵，是"没有可验证的信任链时不能凭空制造结论"的必然结果。它跟 [RFC 8020] 的 NXDOMAIN cut 是两条独立的线，别混。

### 常见误读

**误读一：SERVFAIL 是验证器坏了。** 对 Bogus 而言 SERVFAIL 是**规定的正确结果**。排查方向应该是查信任锚、查时间同步（RRSIG 有效期对时钟极敏感）、查算法支持、查上游有没有剥签名，而不是关掉验证。

**误读二：permissive 模式是"温和上线"，可以长期留着。** 它只是把 Bogus 从"拒绝"改成"记一笔日志然后放行"。长期运行时，攻击者不需要绕过日志，只需要让数据通过。

**误读三：fail-closed 太激进，会影响可用性。** 这是真实的取舍，但应由**过期缓存应答**（[RFC 8767]，第 15 章）与信任锚滚动机制来补，而不是靠放宽验证判定。用可用性机制补可用性、用安全机制保安全，边界不能交叉。

## 被剥离签名为什么等于降级

### 它要解决什么

"降级"（downgrade）指攻击者不破解密码学，而是让双方退回一个更弱、更容易攻击的通信模式。对 DNSSEC 来说，最省力的降级不是伪造 RRSIG（做不到），而是让验证器**看不到该有签名的证据**：

- 在应答里删掉 RRSIG 与 DNSKEY；
- 清掉 OPT 里的 DO 位，让上游不返回 DNSSEC 记录；
- 用伪造的 NODATA 冒充"该区没有 DS"（把 Secure 分支伪装成 Insecure）；
- 在链路上做明文 53 的中间人，直接改写应答。

这些手法与第 17 章的"静默明文降级"是同一类思维：不需要赢下密码学，只需要让保护机制**不被触发**。

### 关键条文

[RFC 4033] 的 Insecure 定义是防御的支点：Insecure 不是"没看到 DS"，而是"在某个委派点拿到了**带签名的** DS 不存在证明"。父区签名过的 NSEC/NSEC3 记录证明该委派未签名，验证器才能合法地放行未签名数据。缺少这份证明，却观察到本应签名的区没签名，只能是 Bogus。

[RFC 6840] §4.3（Check for CNAME）、§4.4（Insecure Delegation Proofs）、§5.11（Mandatory Algorithm Rules）等多处都在堵同一类漏洞：如果实现允许"部分应答""少一条签名""引用里少个 DS"就滑向放行，降级就成立。§5.11 尤其重要——验证器不能因为"我不认识这个算法"就把整个区当成未签名，算法支持与否是验证器的能力问题，不是区的安全状态。

[RFC 4035] 关于 AD 位的规则也从另一侧堵漏：AD 是服务器**自己验证过**才能置的。如果上游悄悄把签名剥了，本地验证器不会置 AD，下游据此可以判别"这一跳没被验证过"。

### 对实现的约束

因此实现必须把"未见签名"与"证明未签名"严格分开，并在应答组装时防止签名被上游或中间设备剥掉。这就是 `harden-dnssec-stripped` 这类加固项存在的理由：它要求验证器在"信任链说该有签名、应答里却没有"时坚持拒绝。

还有一层与传输层的关系值得写清：**加密传输能防剥签名，但不能替代 DNSSEC**。DoT / DoH / DoQ 保护的是客户端到某一台解析器之间这一跳；解析器自己去递归时，如果那一跳仍是明文 53，中间人依然可以在权威应答到达解析器之前动手。反过来，DNSSEC 也保护不了"查询内容被谁看见"。两条线各管一段，任何一条单独成立都不构成完整保护。

第三篇里"上游超时后允许回退到明文 53 会让整条查询流裸奔"的结论，在本章的语言里就是：降级把保护面从"有完整性校验 + 有传输加密"退回到"什么都没有"，而应用层很难从返回码里察觉这件事。

### 常见误读

**误读一：有 RRSIG 才算安全，没有就是不安全。** 正确说法是：有信任链且应答可验证才算 Secure；有签名的 Insecure 证明才是 Insecure；其余情况要么 Bogus 要么 Indeterminate。

**误读二：把 DO 位当安全开关。** DO 只是"请把 DNSSEC 记录给我"的请求标志（[RFC 4035] 借 [RFC 6891] 的 OPT TTL 字段承载）。清掉它确实会造成剥签名，但加上它并不能验证任何东西。

**误读三：用了 DoH 就不用管 DNSSEC 了。** DoH 保证"我到这台解析器之间没被改"，不保证"这台解析器给我的数据本来就是真的"。

## 信任锚滚动：[RFC 5011]

### 它要解决什么

信任锚是验证器的起点，通常很少几个（根的 KSK）。但如果这个锚需要更换——密钥泄露、算法升级、例行轮换——分布在全世界、无人值守的验证器怎么知道？逐台手工改配置不可行。[RFC 5011]（2007，*Automated Updates of DNS Security (DNSSEC) Trust Anchors*）定义了一套**自动、经认证、经授权**的滚动机制。

### 关键条文

- 基于当前锚所建立的信任，把**新的候选锚**加入同一信任点；新密钥先以"待观察"状态出现。
- 引入 `addHoldDownTime`（观察期）与 `removeHoldDownTime`（撤销期）两类计时：新锚必须在连续若干个刷新周期内持续以经签名的方式出现，才能被提升为有效锚；撤销一个锚同样要走完等待期。
- 机制提供对 N 个密钥中 N−1 个被攻破的容忍：只要还有一个可信的当前锚，就能授权加入或撤销其他锚。
- [RFC 5011] 明确说自己改变的是**解析器的管理行为，不是解析行为**：验证流程不变，变的是"锚集合怎么随时间演化"。

### 对实现的约束

实现必须持久化锚的状态机（当前有效 / 待添加 / 待撤销），并在重启后继续计时——把状态只放在内存里，等于每次重启都把观察期清零。这也是为什么自动信任锚需要一个**可写且持久**的锚文件，而不是只读的配置片段。

时间同步在这里同样是硬依赖：观察期与 RRSIG 有效期都按墙钟计算。第三篇提到的时钟漂移导致间歇性全量 SERVFAIL，在 [RFC 5011] 语境下会更隐蔽——锚状态可能被误判。

### 常见误读

**误读一：[RFC 5011] 用于所有密钥轮换。** 它管的是**信任锚**（通常是 KSK / 根锚）。区内部的 ZSK 轮换、以及 KSK/ZSK 的常规滚动时序属于 [RFC 6781] / [RFC 7583] 的范围。

**误读二：看到新 DNSKEY 就该立刻启用。** 恰恰相反，观察期是为了抵御"攻击者短时间注入一个假锚"。立刻启用等于把自动滚动变成单点注入面。

## 澄清与实现说明：[RFC 6840]

### 它要解决什么

DNSSECbis 三份文档发布后，各家实现在细节上又分叉了：NSEC3 支持与否、SHA-2 支持、AD/CD 位该怎么设、DS 摘要算法不认识时怎么办、CNAME 链怎么验、嵌套信任锚怎么处理。[RFC 6840]（2013，*Clarifications and Implementation Notes for DNS Security (DNSSEC)*）把部署经验里踩过的坑逐条写成实现说明。

### 关键条文

按小节看，最影响验证器正确性的几条：

- **§2.1 / §2.2**：明确实现应支持 NSEC3 与 SHA-2 系列，避免把"不支持"误判成"未签名"。
- **§3.1**：实现 BAD cache（验证失败短时负面缓存），既抗放大也避免日志洪泛。
- **§4.1–§4.4**：否认存在证明的澄清、ANY 查询的验证、CNAME 检查、Insecure 委派证明——这几节基本是在堵 16.3 讲的降级路径。
- **§5.2 / §5.11 / §5.12**：未知的 DS 摘要算法、强制算法规则、忽略未知密钥的多余签名。核心立场一致：**验证器的能力缺口不能成为放行的理由**。
- **§5.6–§5.9**：DO 位应答设置、查询里的 AD 位应被忽略、应答里 AD 位的设置条件、以及"验证器应在每一次上游查询都置 CD 位"。最后一条的理由写得很实在：若上游某台已验证的解析器因 Bogus 返回 SERVFAIL，而 [RFC 2308] 允许对 SERVFAIL 短时缓存，本地验证器需要能用 CD 位重新取回原始数据自己判定，而不是继承别人的失败结论。
- **§5.10**：嵌套信任锚的处理。

### 对实现的约束

[RFC 6840] 把 [RFC 4035] 里若干"可以自行理解"的地方变成 SHOULD / MUST 级别的实现建议，实际效果是**让不同实现的验证结果趋于一致**。对运维的含义是：两个解析器对同一个坏签名域给出不同结论时，先查实现版本与算法支持，再怀疑配置——差异往往来自澄清条款是否被实现。

### 常见误读

**误读一：澄清 RFC 是可选的"最佳实践"。** 其中不少条目直接决定"这个应答该不该被判为 Bogus"，属于正确性范畴。

**误读二：CD 位是给客户端关验证用的。** 客户端置 CD 表示"请把原始数据给我，我自己判"；而 [RFC 6840] §5.9 讲的是**验证器对上游**也应置 CD，方向不同，别混。

## 算法信号与算法要求：[RFC 6975] / [RFC 8624]

### 它要解决什么

区管理员想从旧算法换到新算法（例如 RSA/SHA-1 → ECDSA P-256），但不敢贸然切换：万一大量验证器还不支持新算法，整区就会对它们变成 Bogus。[RFC 6975]（2013，*Signaling Cryptographic Algorithm Understanding in DNS Security Extensions (DNSSEC)*）让验证中的端系统通过 EDNS 选项向服务器**声明自己支持哪些签名与摘要算法**，使管理员能观测新算法的覆盖率，判断何时可以完成滚动。

[RFC 8624]（2019，*Algorithm Implementation Requirements and Usage Guidance for DNSSEC*，废弃 [RFC 6944]）则从另一侧给出实现要求表：哪些算法签名侧 MUST NOT、哪些验证侧 MUST、哪些只是 RECOMMENDED。

### 关键条文

[RFC 8624] §3.1 的结论值得完整记住（这是可核验的表格，不是推测）：

| 编号 | 助记符 | DNSSEC 签名 | DNSSEC 验证 |
|---|---|---|---|
| 1 | RSAMD5 | MUST NOT | MUST NOT |
| 3 / 6 | DSA / DSA-NSEC3-SHA1 | MUST NOT | MUST NOT |
| 5 / 7 | RSASHA1 / RSASHA1-NSEC3-SHA1 | NOT RECOMMENDED | MUST |
| 8 | RSASHA256 | MUST | MUST |
| 10 | RSASHA512 | NOT RECOMMENDED | MUST |
| 13 | ECDSAP256SHA256 | MUST | MUST |
| 14 | ECDSAP384SHA384 | MAY | RECOMMENDED |
| 15 / 16 | ED25519 / ED448 | RECOMMENDED / MAY | RECOMMENDED |

表里那个"签名侧不建议、验证侧仍 MUST"的组合是刻意的：老算法虽不该再用于新签名，但仍有存量区在用，验证器必须能验证它们，否则会造成大面积 Bogus。这正是 16.5 §5.11"能力缺口不能成为放行理由"的反面——**该支持的必须支持，不支持的不能假装未签名**。

[RFC 6975] 的信号本身是 EDNS0 选项，属于 [RFC 6891] 的扩展机制；它不改变验证结果，只提供部署侧的观测数据。

### 对实现的约束

实现要维护算法支持表并随版本更新；同时注意 [RFC 8624] 是**时点性文档**，算法推荐会随密码学进展被后续 RFC 更新。本书不复述更晚的版本结论，具体实现支持哪些算法以所用版本的官方手册为准。

应答尺寸也是算法选择的现实约束：ECDSA 相比 RSA 密钥与签名更短，更容易装进 1232 字节的 EDNS 载荷而不分片（第 15 章 [RFC 6891]）。算法不只是密码学问题，也是 MTU 问题。

### 常见误读

**误读一：[RFC 6975] 的信号让服务器按客户端能力"挑算法"。** 不是，它用于统计覆盖率以决定滚动时机，区的签名算法不是按单个查询协商的。

**误读二：验证器只实现"当前推荐"的算法就够。** 恰恰要兼容存量算法，否则会把仍在使用老算法的有效区误判成 Bogus。

## 签名区的否认存在：[RFC 7129] / [RFC 9276]

### 它要解决什么

"证明一个东西不存在"比"证明它存在"难。DNSSEC 的 NSEC 链通过"按规范名排序，给出前后两个名字，说明目标落在两者之间"来证明不存在；代价是**允许区枚举**（zone walking）：顺着 NSEC 链一路走就能把区里所有名字列出来。NSEC3（[RFC 5155]）用哈希名字代替明文名字，并引入 salt 与迭代次数提高枚举成本。

[RFC 7129]（2014，*Authenticated Denial of Existence in the DNS*，Informational）是背景与机理说明：为什么否定应答需要最多两条 NSEC（NSEC3 时三条）、通配符与 Empty Non-Terminal 怎么参与、NODATA 与 NXDOMAIN 的证明有何不同。[RFC 9276]（2022，*Guidance for NSEC3 Parameter Settings*）则纠正了一个长期的运维误区——**堆高迭代次数并不会带来相应的安全收益**。

### 关键条文

[RFC 9276] 的核心论证：

- 名字在 NSEC3 记录里本来就被哈希隐式"加盐"；额外 salt 只有在**在线攻击阶段持续变化**才能抬高成本，而换 salt 要求重建整条哈希链、且必须等链上每个名字都更新完才能生效，操作极其复杂，频繁换盐不现实。
- 额外迭代次数带来的成本对防御方是线性、对攻击者是一次性预计算，收益远小于直觉；文档明确指出"applying additional hash iterations beyond the first"缺乏收益。
- 结论写得很直接：**若必须使用 NSEC3，迭代次数 MUST 取 0**。同时指出高迭代会让验证器与权威服务器都付出 CPU 代价，反而放大 DoS 面。

[RFC 7129] 说明了为什么验证器不能把"没拿到 NSEC 记录"当成"不存在证明缺失无所谓"——没有可验证的否认存在证据，NXDOMAIN 就不能被判为 Secure，这直接影响 `harden-below-nxdomain` 一类剪枝是否生效（见 16.2）。

### 对实现的约束

权威侧签名工具应默认不用 NSEC3 的高迭代与频繁换盐；验证侧要对高迭代保持警惕（验证成本放大），并按 [RFC 8624] 的算法表处理 NSEC3 相关算法。运维侧要理解"用 NSEC3 防枚举"本身就是取舍：若区里名字并非秘密，用 NSEC 更简单；若确实需要防枚举，可用 NSEC3 的 opt-out 等机制，但参数不能靠"调大迭代"来补。

### 常见误读

**误读一：NSEC3 是 NSEC 的加密版本。** 它是哈希化的否认存在机制，哈希是为了抬高枚举成本，不是加密，也不提供保密性。

**误读二：迭代次数越大越安全。** [RFC 9276] 专门推翻这一点，并给出 0 迭代的 MUST 级要求。

**误读三：否认存在与 [RFC 8020] 的 NXDOMAIN cut 是一回事。** 前者是 DNSSEC 的密码学证明，后者是纯解析语义的子树剪枝；一个管"能不能信"，一个管"还要不要继续问"。

## 运维实践：[RFC 6781] / [RFC 7583]

### 它要解决什么

协议定稿之后，真正难的是"每天怎么跑"：密钥多久换一次、KSK 与 ZSK 分工、签名有效期多长、滚动时要等几个 TTL、父区 DS 什么时候更新、出错了怎么回滚。[RFC 6781]（2012，*DNSSEC Operational Practices, Version 2*，废弃 [RFC 4641]）是面向区管理员的实践集；[RFC 7583]（2015，*DNSSEC Key Rollover Timing Considerations*）专攻**滚动时序**，把各事件之间的依赖关系画成时间线。

### 关键条文

- KSK 与 ZSK 分离：ZSK 可较频繁滚动且不必惊动父区，KSK 滚动必须同步更新父区 DS，代价高、周期长。
- 滚动时序由 TTL 与签名有效期共同约束：新密钥发布后要等旧数据的 TTL 全部过期，才能让旧密钥退场；`double-signing`、`pre-publish` 等策略各有不同的等待窗口。
- [RFC 7583] 明确列出各参数（签名有效期、区刷新、父区 DS 的 TTL、验证器缓存）之间的数学关系，并指出**顺序搞错就会在一段窗口内让部分验证器判为 Bogus**。
- 两份文档都强调监控：签名临期、DS 与 DNSKEY 不一致、信任锚状态，都应在变成故障前被发现。

### 对实现的约束

对递归解析器运维者，最实用的一条是理解"远端滚动会波及本地"：某个上游区做 KSK 滚动时，若本地验证器缓存了旧 DNSKEY / 旧 DS，且滚动窗口内有验证失败，表现就是间歇性 SERVFAIL——而不是本地配置坏了。这也是 [RFC 5011] 自动锚状态机必须持久化的原因之一。

时钟同步在这里第三次出现：RRSIG 的 inception/expiration、滚动等待窗口、[RFC 5011] 的 hold-down，全都按墙钟计。把 NTP 当成"最好有"的设施，是 DNSSEC 运维里最常见的低估。

### 常见误读

**误读一：密钥滚动是权威侧的事，与递归侧无关。** 递归侧若锚状态或缓存没跟上，会直接把滚动窗口变成 Bogus 窗口。

**误读二：KSK 与 ZSK 可以随便互换滚动。** 二者对父区 DS 的依赖不同，时序约束不同。

## DLV 的历史与退役：[RFC 4431] / [RFC 5074]

### 它要解决什么

根区在 2010 年签名之前，DNSSEC 面临鸡生蛋问题：验证器有根锚也没用，因为根下面的委派大多没有 DS，信任链从第一步就断了。[RFC 4431]（2006，*The DNSSEC Lookaside Validation (DLV) DNS Resource Record*，Informational）定义了 DLV 记录类型，[RFC 5074]（2007，*DNSSEC Lookaside Validation (DLV)*，Informational）定义了整套旁路验证机制：**在 DNS 委派链之外发布信任锚**，让验证器对"祖先未签名或不发布 DS"的区也能验证。

### 关键条文

- DLV 记录本质是放在一个旁路域里的 DS，验证器在找不到常规信任链时，去 DLV 域查对应名字的锚。
- [RFC 5074] 明确说这是**过渡机制**：为根与 TLD 尚未全面签名的阶段提供起点；同时提到它可用于"在一个组织内集中管理多个验证器的锚"或"外包信任锚管理"。
- 两份都是 Informational，不是 Standards Track——这个类别本身就说明它们不是长期架构。

### 对实现的约束与退役

根区于 2010 年签名、根的信任锚可通过 IANA 公开发布后，常规信任链在绝大多数路径上可用；DLV 的历史任务完成。此后各实现陆续移除 DLV 支持，公共 DLV 注册服务停止运营；**新部署不应再依赖 DLV**，历史配置里的 DLV 锚应清理，否则会留下一个"以为在验证、其实查的是一个已不存在的旁路域"的假象。

本章不复述具体停用日期与版本号——这类事实以各实现的发布说明与官方手册为准；可核验的根信任锚信息以 IANA 的 `root-anchors.xml` 为准（见《参考资料》）。

### 常见误读

**误读一：DLV 是 DNSSEC 的一部分。** 它是特定历史阶段的补丁，不是 [RFC 4033]/[RFC 4034]/[RFC 4035] 定义的协议组件。

**误读二：留着 DLV 配置"总没坏处"。** 一个指向已退役旁路域的锚配置，会让配置审计失真，也会在排查时把注意力引向错误方向。

## 根 KSK 轮换（2018）

### 它要解决什么

根 KSK 是全球所有 DNSSEC 验证器共同的起点。它一旦更换，任何没有及时获得新锚的验证器都会把整个签名 DNS 判成 Bogus——这是 DNSSEC 部署史上影响面最大的一次协调动作。2018 年的轮换是**根 KSK 自 2010 年根区签名以来的首次更换**，其意义不在密码学，而在验证[RFC 5011] 设计的自动化滚动机制能不能在真实世界跑通。

### 关键条文与事实

可核验的锚数据来自 IANA 的 `root-anchors.xml`：KeyTag **19036**（2010 年起的初始锚，其 `validUntil` 为 2019-01-11）与 KeyTag **20326**（`validFrom` 为 2017-02-02），两者均为算法 8 / 摘要类型 2。新锚提前一年多发布并进入 [RFC 5011] 的观察期，正是 16.4 讲的 hold-down 机制在根这一层的实例。

轮换过程中还配套处理了"根区应答变大"的工程问题：新 KSK 引入期间根 DNSKEY 应答尺寸上升，触发了对 TCP 回退、EDNS 载荷与分片路径的再检查。这与第 15 章 [RFC 6891] 的逐跳载荷协商是同一条线。

### 对实现的约束

- 验证器必须**持久化 [RFC 5011] 状态**并在轮换窗口内正常运行；长期关机或只读锚文件的实例，可能错过观察期。
- 静态写死旧锚、又不启用自动滚动的配置，在旧锚失效后会进入大面积 SERVFAIL。
- 这次事件把"信任锚不是一次性配置、而是一个随时间演化的状态机"变成了运维常识。

### 常见误读

**误读一：轮换是"换一把更长的密钥"。** 关键不是密钥强度，而是全球验证器能否在不停机的情况下同步更换起点。

**误读二：2018 年之后根锚就固定了。** 不是。`root-anchors.xml` 里还有更晚 `validFrom` 的条目，说明锚集合继续演化；具体实现与当前状态以 IANA 数据与所用版本的官方手册为准。

## 条文之间的因果链

把本卷的 RFC 按"为什么需要下一份"重排，逻辑比编号列表清楚：

1. [RFC 4033]/[RFC 4034]/[RFC 4035] 定义信任链、四种状态与三种标志位，确立 **Bogus → SERVFAIL** 的基本契约。
2. 契约一旦确立，"能否被绕过"就成了主要攻击面：16.2 与 16.3 分别从 [RFC 4033] 的 Insecure 定义、[RFC 4035] 的 AD 位规则、[RFC 6840] 的一系列澄清里推导出 **fail-closed** 与 **剥签名即降级**。
3. 信任锚不能是静态常量，于是有 [RFC 5011] 的自动滚动；滚动在真实世界的检验是 2018 年根 KSK 轮换。
4. 算法会老化，于是有 [RFC 6975] 的覆盖率信号与 [RFC 8624] 的实现要求表；应答会变大，于是回到 [RFC 6891] 的载荷与 MTU 约束。
5. 否认存在的证明有额外复杂度与参数误区，于是有 [RFC 7129] 的机理说明与 [RFC 9276] 的 0 迭代要求。
6. 日常运维的时序问题由 [RFC 6781] / [RFC 7583] 收编；根未签名时代的过渡方案 DLV 完成使命后退役。

这里给出的都是"开关为什么存在"。

## 一个设计哲学的代价：算法复杂度攻击

把本章的条文串起来会看到一条不太舒适的事实：[RFC 4035] 要求验证器尝试可用的密钥，[RFC 6840] 进一步要求尝试所有签名组合 —— 这是为了在密钥轮换、算法轮换、多签名者场景下「尽量验证成功」，是 Postel 律在 DNSSEC 里的体现。但「尽力」没有上限时，就成了攻击者可以单向放大的算力入口：构造大量碰撞 key 与无效签名，让验证器做平方级无用功。这就是第 10 章 KeyTrap / NSEC3 两个 CVE 的协议根因，[RFC 9276] 对 NSEC3 迭代参数的限制也是同一类修正。

因此补丁的形态不是改协议，而是**给实现加工作量上限**：限制 key 碰撞数、每 RRSET 验证次数、NSEC3 哈希次数，并让验证过程可挂起。这也解释了为什么 Unbound 的加固史一以贯之是「限额 + 让出 CPU + fail-closed」，而不是增加更多验证尝试。理论层要记住的结论是：**安全协议的可用性也是安全属性**；一个能被单包拖垮的验证器，与一个不验证的验证器同样危险。

## 本章要点

- DNSSECbis 三份文档（[RFC 4033]/[RFC 4034]/[RFC 4035]，2005）废弃 [RFC 2535] 系列，定义 DNSKEY / RRSIG / DS / NSEC 与 Secure / Insecure / Bogus / Indeterminate 四态；**RRSIG 签的是 RRset**，源自第 15 章 [RFC 2181] 的原子单位定义。
- **验证器必须 fail-closed**：[RFC 4033] 规定 Bogus 以 SERVFAIL 通知，[RFC 4035] 规定 AD 位只在全部数据判定为真时置位。无锚 = 透传、permissive = 记日志放行，都不提供保护；`harden-dnssec-stripped: no` 在有锚时主动制造降级漏洞。
- **被剥离签名等于降级**：Insecure 要求父区**带签名的 DS 不存在证明**，"没看到签名"与"证明未签名"必须严格分开。[RFC 6840] §4/§5 多处堵的正是"少一条证据就滑向放行"。
- 加密传输防剥签名但不替代 DNSSEC；DNSSEC 保护数据与来源、DoT/DoH/DoQ 保护传输隐私、[RFC 8767] 补可用性，四者互不替代。
- [RFC 5011] 让信任锚成为可持久化的状态机（观察期 / 撤销期），2018 年根 KSK 首次轮换（旧锚 KeyTag 19036 → 新锚 20326）是它在全球规模上的验证；静态锚或错过观察期的实例会大面积 SERVFAIL。
- [RFC 8624] 的算法表刻意让"签名侧 NOT RECOMMENDED、验证侧 MUST"并存；[RFC 9276] 要求 NSEC3 迭代次数取 **0**，堆高迭代缺乏安全收益却放大 CPU 与 DoS 面。
- [RFC 6781]/[RFC 7583] 把 KSK/ZSK 分工与滚动时序写成可计算的时间线；DLV（[RFC 4431]/[RFC 5074]）是根未签名时代的 Informational 过渡机制，已随根签名完成而退役。
- 转发器无法自己完成信任锚 priming，因此"转发器"与"验证器"在架构上二选一；这是 [RFC 4035] 验证流程的推论，不是软件缺陷。
